Crypto Basics for Bug Bounty

BB で頻出する暗号の誤用パターンを理解する。暗号学の深い数学は不要だが、「何が壊れるか」を知る必要がある。

Theory Case Study Practice

Hash Functions

任意長の入力を固定長の出力に変換する一方向関数。元のデータを復元できない (preimage resistance)。 パスワード保存、データ完全性検証、デジタル署名に使用。

Hash アルゴリズムの比較

AlgorithmOutputStatusBB での出現
MD5128-bit非推奨 (collision 可能)レガシーシステムのパスワード、ファイルチェックサム
SHA-1160-bit非推奨 (collision 実証済み)Git commit hash, 古い証明書
SHA-256256-bit安全HMAC, JWT signature, integrity check
bcrypt184-bit安全 (パスワード用)パスワード保存の標準
argon2可変最強 (パスワード用)最新アプリのパスワード保存

パスワードハッシュの脆弱性

# 脆弱: plain MD5/SHA (rainbow table で即破れる)
password_hash = md5("password123")
# → 482c811da5d5b4bc6d497ffa98491e38

# 脆弱: salt なし (同じパスワード = 同じハッシュ)
# → rainbow table / precomputed dictionary で攻撃可能

# 安全: bcrypt (adaptive cost + salt built-in)
$2b$12$LJ3m4/rUfNpVOmQGfGAqaeGrFbFNXFzVe8DcNUE3pM9L4YcXZQKHm
# $2b$ = bcrypt, $12$ = cost factor, 22文字 = salt, 残り = hash

# 安全: argon2id (memory-hard, GPU resistant)
$argon2id$v=19$m=65536,t=3,p=4$salt$hash
BB視点: Hash で狙うポイント

(1) パスワードリセットトークンが MD5(email + timestamp) → 予測可能
(2) API key が SHA256(user_id + creation_date) → 構造が分かれば再計算可能
(3) HMAC secret が推測可能 → 任意のトークン生成が可能
トークン生成に使われる hash の入力材料が推測可能かどうかを常にチェック。

Symmetric Encryption (対称暗号)

同じ鍵で暗号化と復号を行う。高速だが鍵の配布が課題。AES が事実上の標準。

AES のモード (Mode of Operation)

Mode特徴脆弱性
ECB 各ブロックを独立に暗号化 同一平文 = 同一暗号文。パターン漏洩。ペンギン問題。
CBC 前ブロックの暗号文を XOR Padding Oracle Attack。IV 再利用で情報漏洩。
GCM 認証付き暗号 (AEAD) Nonce 再利用で鍵回復可能。正しく使えば安全。

ECB Mode の問題 (パターン漏洩)

# ECB mode: 同じ平文ブロック → 同じ暗号文ブロック
# ユーザープロフィールの暗号化 (16-byte ブロック)

plaintext:  email=user@evil. | com&role=user&xx | xxxxxxxxxxxxxxxx
            email=user@evil. | com&role=admin&x | xxxxxxxxxxxxxxxx

# ECB では各ブロックが独立 → "role=admin" のブロックを
# 別のリクエストから取得して差し替え可能 (cut-and-paste attack)

CBC Padding Oracle Attack

CBC モードでは PKCS#7 padding が使われる。サーバーが「padding 不正」と「復号成功だがデータ不正」で 異なるエラーを返す場合、1 byte ずつ平文を復元できる。 

# PKCS#7 Padding (ブロックサイズ 16-byte の場合)
# 最終ブロックの空き部分を埋める
# 1 byte 空き → 0x01
# 2 byte 空き → 0x02 0x02
# 3 byte 空き → 0x03 0x03 0x03

# 攻撃:
# C1 (前ブロック暗号文) の最終byte を 0x00～0xFF で変化させる
# サーバーが "valid padding" を返す値 → P2 の最終byte が判明
# → 全 byte を繰り返して平文全体を復元
BB視点: Padding Oracle の見つけ方

暗号化された Cookie やトークンの1byte を変更してレスポンスの差異を観察。 「500 Internal Server Error」vs「403 Forbidden」のような差があれば Oracle の可能性。 PadBuster ツールで自動化可能。 PortSwigger WSA にも Lab がある。

Asymmetric Encryption (非対称暗号)

公開鍵で暗号化、秘密鍵で復号 (または秘密鍵で署名、公開鍵で検証)。 TLS, JWT (RS256/ES256), SSH で使用。

RSA

  • 鍵サイズ: 2048-bit 以上が必須 (1024-bit は危険)
  • Padding: PKCS#1 v1.5 は Bleichenbacher 攻撃に脆弱。OAEP を使う
  • BB での出現: JWT RS256 の公開鍵露出 → Algorithm Confusion 攻撃

ECDSA (Elliptic Curve Digital Signature Algorithm)

  • RSA より短い鍵で同等のセキュリティ (256-bit ECDSA ≈ 3072-bit RSA)
  • 致命的な弱点: nonce (k値) の再利用で秘密鍵が回復される (PlayStation 3 hack)
  • BB での出現: JWT ES256, WebAuthn の署名検証

Digital Signatures

データの真正性と完全性を保証する。秘密鍵で署名、公開鍵で検証。 BB では「署名検証のバイパス」が主な攻撃対象。

署名検証のバイパスパターン

Attack原因影響
Algorithm None (JWT)alg:none を受け入れる署名なしで任意の claim
Key Confusion (JWT)RSA public key を HMAC secret として使用公開鍵で偽造可能
Signature not checked検証ロジックのバグ任意のデータを正当と見なす
Length extensionMD5/SHA-1 の構造的弱点元のメッセージ不要でMAC を延長

HMAC (Hash-based Message Authentication Code)

共有秘密鍵を用いてメッセージの完全性と認証を保証する。 HMAC(key, message) = H((key XOR opad) || H((key XOR ipad) || message)) 

# Python での HMAC 計算
import hmac
import hashlib

secret = b"my-secret-key"
message = b"user_id=123&role=admin"

signature = hmac.new(secret, message, hashlib.sha256).hexdigest()
# → "a1b2c3d4..."

# 検証
hmac.compare_digest(expected_sig, computed_sig)  # timing-safe comparison

HMAC の攻撃パターン

  • Weak secret: 短い/辞書にある secret は brute force 可能
  • Timing attack: == で比較すると文字ごとの応答時間差で signature を特定
  • Length extension: HMAC ではなく H(key || message) を使っている場合に攻撃可能
BB視点: Timing Attack の現実性

ローカル環境ではナノ秒の差を観測可能だが、ネットワーク越しでは通常困難。 ただし同一データセンター内 (同じクラウドリージョン) や、大量の統計処理で成功した事例がある。 BB では「constant-time comparison を使っていない」こと自体を報告する (Low/Informational)。

Predictable IV / Nonce

CBC の IV (Initialization Vector) や GCM の Nonce が予測可能だと暗号の安全性が崩壊する。 

# 脆弱: IV がカウンターや固定値
iv = b'\x00' * 16  # 固定 IV → 同じ平文 = 同じ暗号文 (ECB と同等)
iv = int.to_bytes(counter, 16)  # 予測可能 → chosen-plaintext attack

# 安全: ランダム IV (各暗号化ごとに CSPRNG で生成)
import os
iv = os.urandom(16)

# GCM の Nonce 再利用は致命的
# 同一 nonce + 同一 key で 2 つの異なる平文を暗号化 → key stream が回復される

Real-World Examples

  • PlayStation 3 ECDSA hack (2010): nonce 固定で秘密鍵復元 → ゲーム署名偽造
  • Padding Oracle (ASP.NET 2010): Microsoft の ScriptResource.axd で web.config 漏洩
  • JWT alg:none (Auth0 2015): ライブラリが none algorithm を受け入れ
  • Heroku JWT leak: 弱い secret で署名 → 管理者トークン偽造

Key Takeaways

  • ECB mode は同一平文で同一暗号文 → cut-and-paste 攻撃。暗号化 Cookie で発見可能。
  • Padding Oracle は暗号文1byte改ざんでエラー差異を観察。PadBuster で自動化。
  • HMAC weak secret は JWT に限らず、API 署名全般で hashcat/john でクラック試行。
  • トークン生成の材料が推測可能 (timestamp, user_id, sequential) なら予測攻撃が成立。
  • Timing attack はネットワーク越しでは困難だが、constant-time 不使用はレポート対象。
  • Nonce/IV 再利用は GCM で致命的。CBC でも chosen-plaintext に脆弱。
