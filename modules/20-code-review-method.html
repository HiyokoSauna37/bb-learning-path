Code Review Methodology

セキュリティ視点のソースコードレビュー手法。Sink-to-Source / Source-to-Sink / Feature-based の3アプローチと、Trust Boundary の特定技術。

Theory Hands-on

始める前に: コードを手に入れる

OSS のコードレビューを初めてやる場合、まず以下の手順でコードを入手し、構造を理解する:

  1. リポジトリを clone する: git clone https://github.com/org/repo && cd repo
  2. 言語とフレームワークを確認: package.json (Node.js) / requirements.txt (Python) / go.mod (Go) を見る
  3. エントリーポイントを探す: main スクリプト、server.js、app.py など — ここからアプリが起動する
  4. ルート定義を探す: routes/, controllers/, src/api/ — HTTP endpoint の定義場所
  5. 認証 middleware を探す: middleware/, auth.js, decorators.py — ここが壊れていれば auth bypass

この5ステップでアプリの「形」が掴めたら、以下の3つのアプローチで脆弱性を探す。

3つのアプローチ

1. Sink-to-Source (Dangerous Function Tracing)

最も効率的なアプローチ。危険な関数 (sink) を先に見つけ、そこに到達するユーザ入力 (source) を逆方向に追跡する。

  • まず codebase 全体から sink を grep で列挙
  • 各 sink に対して「ユーザ制御可能な入力が到達するか」を判定
  • sanitization / validation が途中に存在するか確認
huntr OSS 調査では最も高 ROI

大規模 codebase でもsinkの数は有限。全 route を読む必要がなく、高 severity な脆弱性に直接到達できる。

2. Source-to-Sink (Input Tracing)

ユーザ入力の entry point から始めて、データがどこまで到達するかを追跡する。

  • HTTP request handlers (req.body, req.params, req.query)
  • File uploads, WebSocket messages
  • 各入力がどの関数に渡されるか順に追跡
  • 途中の validation/sanitization の有無と強度を評価

3. Feature-based Review

機能単位で監査する。認証、ファイルアップロード、API キー管理など、高リスク機能を優先。

  • 認証/認可: auth middleware, role check, session management
  • ファイル操作: upload, download, path construction
  • 外部通信: webhook, SSRF-prone HTTP calls
  • Admin 機能: privilege escalation の起点

Trust Boundary の特定

Trust boundary = 信頼レベルが変わる境界。この境界を越えるデータフローに脆弱性が潜む。

境界概要典型的な脆弱性
Client → Server全 HTTP input は untrustedInjection, XSS, SSRF
User → AdminRole/権限の境界Privilege Escalation, IDOR
App → DBQuery 構築の境界SQL/NoSQL Injection
App → OSSystem command 実行Command Injection, Path Traversal
Service → ServiceInternal API 間通信SSRF, Token Leakage

Grep Patterns for Common Sinks

最初にこれらのパターンで codebase を sweep し、危険箇所を洗い出す。

# Command Injection sinks
rg -n "exec\(|execSync\(|spawn\(|system\(|popen\(" --type js
rg -n "child_process" --type js
rg -n "subprocess\.|os\.system\(|os\.popen\(" --type py

# Code Execution sinks
rg -n "eval\(|Function\(|setTimeout\(.*," --type js
rg -n "exec\(|compile\(" --type py
rg -n "vm\.runInNewContext\(" --type js

# SQL/NoSQL Injection sinks
rg -n "query\(.*\+" --type js
rg -n "\\\$where|\\\$regex|\\\$gt|\\\$ne" --type js
rg -n "raw\(|execute\(" --type py

# Deserialization sinks
rg -n "unserialize\(|deserialize\(" --type js
rg -n "pickle\.loads\(|yaml\.load\(" --type py
rg -n "Marshal\.load\(" --type ruby

# Path Traversal sinks
rg -n "path\.join\(.*req\.|readFileSync\(|createReadStream\(" --type js
rg -n "os\.path\.join\(.*request\." --type py

# XSS / Template Injection sinks
rg -n "innerHTML|dangerouslySetInnerHTML|v-html" --type js
rg -n "\.render\(|render_template_string\(" --type py
rg -n "<%[-=].*\|" --glob "*.ejs"
False Positive に注意

grep hit = 脆弱性ではない。hit した箇所の input が user-controlled かどうか、途中に sanitization があるかを必ず確認する。

Data Flow Tracing テクニック

手動トレーシング

  1. Entry point を特定 (route handler の引数)
  2. 変数の代入・変換を追跡 (rename, destructure, spread)
  3. 関数呼び出しを跨いで追跡 (caller → callee)
  4. Sink に到達するか判定
  5. 途中の validation/sanitization を bypass できるか検討

追跡を阻むパターン

  • Dynamic dispatch: obj[method]() — 実行時に決まる
  • Middleware chain: req object が複数 middleware で変更される
  • ORM abstraction: Raw query か parameterized か判別困難
  • Config-driven routing: route 定義がコードでなく設定ファイル

ツール

grep / ripgrep

最も基本的かつ強力。上記パターンでの sweep に使用。

Semgrep

# Semgrep rule 例: eval with user input
# semgrep --config "p/javascript" --config "p/security-audit" .
# Custom rule:
rules:
  - id: eval-user-input
    patterns:
      - pattern: eval($X)
      - pattern-not: eval("...")
    message: "Possible code injection via eval"
    severity: ERROR
    languages: [javascript]

CodeQL (概要)

  • GitHub が提供する semantic code analysis engine
  • Source-Sink のデータフローを自動追跡
  • GitHub Advanced Security で自動実行 or ローカル CLI
  • 学習コストは高いが、大規模 codebase での漏れ防止に有効

実践的 Workflow: OSS Target に対する初回 Audit

Step 1: Repository Structure 把握 (5分)

# プロジェクト構造の把握
find . -name "*.js" -o -name "*.py" -o -name "*.go" | head -50
cat package.json  # dependencies, scripts 確認
ls routes/ controllers/ middleware/ src/api/

Step 2: Sink Sweep (10分)

上記の grep patterns で全 sink を列挙。結果をファイルに保存。

rg -n "exec\(|eval\(|system\(|spawn\(" --type js > /tmp/sinks.txt
rg -n "\.query\(.*\+|\.raw\(" --type js >> /tmp/sinks.txt
rg -n "path\.join\(.*req\." --type js >> /tmp/sinks.txt
wc -l /tmp/sinks.txt  # hit 数を確認

Step 3: Auth Middleware 把握 (5分)

# auth middleware の名前と適用状況
rg -n "module\.exports" middleware/
rg -n "router\.(get|post|put|delete)" routes/ | grep -v authMiddleware

Step 4: 優先度付け (5分)

Hit 数が多い場合、以下の順で deep dive:

  1. Auth bypass (middleware 欠落) — 最も高 severity
  2. Injection (exec/eval + user input) — RCE 直結
  3. SSRF (HTTP client + user URL) — internal access
  4. Path Traversal (file ops + user input) — data leak
  5. IDOR (authorization check 欠如) — data access

Step 5: Deep Dive + PoC (残り時間)

優先度順に1つずつ data flow を trace し、exploitable か判定。PoC curl を作成。

Time Budget の目安

新規 target の初回 audit: 約 2-4 時間。Sink sweep + auth audit で 30 分、残りを deep dive に使う。1 session で finding 0 なら target を変える判断も重要。

Key Takeaways

  • Sink-to-Source が OSS audit で最も効率的 — 危険関数を grep で列挙し、逆方向にトレース
  • Trust Boundary を意識し、境界を越えるデータフローに集中する
  • grep sweep で全 sink を列挙してから深掘り (広く浅く → 狭く深く)
  • False Positive 排除: hit = vuln ではない。入力制御可能性 + sanitization 有無を必ず確認
  • ツールは補助。最終的にはコードを読む力が決め手
