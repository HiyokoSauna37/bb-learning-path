Incomplete Fix Variant Strategy

既存の Advisory / CVE のパッチが不完全なケースを見つける戦略。 huntr での最も確度の高い discovery method の1つ。

Theory Case Study

なぜ Incomplete Fix が狙い目なのか

  • Existence proof: 元の CVE/Advisory が「この場所に脆弱性がある」と証明済み
  • Patch scope が有限: 開発者はレポートされた箇所だけ直す傾向がある (sibling が残る)
  • Diff が読めれば勝ち: git log → commit → 変更ファイルの「直していない兄弟」を grep
  • Dup risk が比較的低い: 同じ advisory を見ている人は少ない（タイミング依存）
タイミングの話 (実践で報奨金を狙う段階向け)

実際に報奨金を得る段階では、advisory 公開から 3日以内が golden window。 30日超は原則 NOGO (他の hunter が既に見つけている可能性が高い)。 例外は非常にマイナーなプロジェクトのみ。

ただし、学習目的なら古い advisory で全く問題ない。 6ヶ月前の advisory でも「patch diff を読む → sibling を grep する」技術は同じ。 まずは古い advisory で練習し、スピードが付いてから新鮮な advisory をウォッチする流れがおすすめ。 (参照: feedback_bb_incomplete_fix_variant_strategy)

Step 1: Advisory の発見

  • GitHub Security Advisories (GHSA): bb-ghsa list <repo> で全件取得
  • huntr.com の公開 disclosure feed
  • NVD / CVE: 新規公開の CVE をウォッチ
  • news/09_bug-bounty: 日次ダイジェストで新規 advisory をキャッチ

Step 2: Patch Diff を読む

# Advisory に紐づく commit/PR を特定
git log --all --oneline --grep="CVE-2026-XXXXX"
git log --all --oneline --grep="GHSA-xxxx-xxxx-xxxx"

# Patch diff を確認
git show <commit-hash>

# 変更されたファイルを確認
git diff <parent>..<commit> --stat

Step 3: Sibling Detection (修正漏れ箇所の発見)

パッチが行ったことを理解し、同じパターンで修正されていない箇所を探す。

# パッチが追加した check の関数名を特定
# 例: パッチが validWorkspaceSlug middleware を追加した場合

# 同じ router で middleware が付いていない route を検索
grep -rn "router\.\(get\|post\|put\|delete\)" routes/ | grep -v "validWorkspaceSlug"

# bb-middleware-audit (Go middleware 用) で機械的に検出
bb-middleware-audit scan --pattern="authMiddleware" --missing

よくある Sibling パターン

パターン探し方実例
Middleware 追加漏れ 同じ router の他 route に同 middleware があるか grep AnythingLLM: parsed-files に middleware 追加、 suggested-messages / pfp に漏れ
HTTP Method 別の漏れ GET は修正されたが POST/PUT/DELETE は未修正 LibreChat: DELETE に user filter 追加、 GET に漏れ
Endpoint 別の漏れ 同じ controller/service の他 endpoint lobe-chat: chat route に auth追加、 tts/stt に漏れ
Check 条件の不完全さ パッチの if 文が一部条件を漏らしている wger: gym_id 比較が int型 vs None で bypass
別 caller からの呼び出し 修正された関数を呼ぶ上位関数が他にもある LiteLLM: global_spend routes は修正、 spend routes 未修正

Step 4: PoC 検証

  • 必ず 実 runtime で確認 (Docker image, latest release)
  • Positive test (脆弱性が刺さる) + Negative test (通常の認可が効く) の両方
  • パッチ適用後のバージョンで再現すること (=パッチが不完全な証拠)

Step 5: レポート作���

Incomplete fix variant の report は以下を必ず含める:

  1. 元の CVE/Advisory のリンク
  2. パッチが修正した箇所の説明
  3. パッチが修正し損ねた箇所の指摘
  4. 新たに発見した sink の PoC
  5. 提案する修正方法

Case Study: 実際の Incomplete Fix Variant

Case 1: AnythingLLM (huntr 提出済み)

2026-03: GHSA-p5rf-8p88-979c
parsed-files endpoint に IDOR。validWorkspaceSlug middleware が追加された。
2026-04-30: 発見
同じ router の suggested-messages GET と pfp GET には middleware が 未追加。
検証
Docker mintplexlabs/anythingllm:latest v1.12.1 + master HEAD で E2E PoC 確認。

発見手法: git diff で追加された middleware → 同 router の他 route を grep → 2 endpoint に middleware 不在を確認

Case 2: wger (GHSA 提出済み)

2026-04-26: CVE-2026-43948 / GHSA-mhc8-p3jx-84mm
パッチ commit e1d329ff で is_same_gym() helper 導入。
2026-05-08: 発見
user.py の 3 箇所 (delete, UserDeactivateView, UserActivateView) が旧来の raw-int 比較のまま。
検証
Docker wger/server:latest で positive ×3 + negative ×3 + revert test。Critical 9.9。

発見手法: パッチが導入した is_same_gym() を grep → 呼ばれていない箇所が 3 つ残存

Case 3: lobe-chat (GHSA 提出済み)

2026-04: GHSA-5mwj-v5jw-5c97 / PR #13535
checkAuth middleware が chat/models route に追加。
2026-05-03: 発見
/webapi/tts/openai と /webapi/stt/openai に checkAuth 未適用。OPENAI_API_KEY fallback でコスト発生。

発見手法: PR diff → 追加された middleware 名 → 適用されていない route を検索

Anti-patterns (やってはいけないこと)

Common Mistakes
  • 30日超の advisory に飛びつく → Dup 確率が跳ね上がる (default NOGO)
  • コードだけ見て report する → 必ず runtime で PoC 確認 (serializer の output ≠ HTTP response)
  • 「Missing feature」を variant と混同する → helper function が存在しない = feature request であって bug ではない
  • Advisory の wording を過大解釈する → ≥2通りの解釈がある場合、全解釈で violation でないなら submit 不可

ツール

ツール用途
bb-ghsa list <repo>リポジトリの全 advisory を一覧取得
bb-middleware-auditGo/Express middleware の追加漏れを機械検出
bb-advisory-age <advisory>Advisory 公開からの経過日数 → GO/NOGO 判定
bb-whitelist-auditWHITELIST_URLS auth-bypass anti-pattern の sibling 検出
git log --oneline --allPatch commit とその周辺変更の追跡

Key Takeaways

  • Patch diff を読む力が直接お金に変わる — 1つの advisory から複数の variant が見つかる
  • Sibling detection: パッチが「何をしたか」を理解し、「同じことをすべきだが していない箇所」を探す
  • Timing: Advisory 公開から 3日以内が golden window。30日超は原則 NOGO
  • Runtime verify 必須: コードレベルで脆弱に見えても、別のレイヤーで止まっていることがある
  • Negative test: パッチが効いている箇所で 403 が返ることを確認 → 修正漏れ箇所との対比を report に含める
