Race Conditions & TOCTOU

並行処理のタイミング差を悪用し、ビジネスロジックのチェックをbypassする攻撃。 Valve CD key duplicationで$20,000、limit bypassが頻出ターゲット。

Theory Hands-on WSA Labs

Core Concept

Race conditionは、2つ以上のリクエストが同時に処理される際、 チェック(Time-of-Check)と操作(Time-of-Use)の間にwindowが生じ、 本来許可されない操作が成功する脆弱性。

Thread A: [CHECK balance >= $100] -------- [DEDUCT $100] → Success Thread B: -------- [CHECK balance >= $100] -------- [DEDUCT $100] → Success ↑ both see $100 before either deducts Result: $100 balance → $200 spent (double-spend)

なぜ今 Race Condition が重要か

  • HTTP/2の普及: Single-packet attackが容易に (true simultaneity)
  • マイクロサービス化: サービス間のatomicity保証が困難
  • 報酬額が高い: ビジネスインパクト直結 (金銭的損害)
  • 自動テストで見つかりにくい: CI/CDのunit testでは再現困難

Single-Packet Attack (HTTP/2)

HTTP/2ではmultiple streamsが単一TCP接続上で多重化される。 複数リクエストを1つのTCPパケットに詰めて送信することで、 ネットワークjitterを完全排除し、サーバ側でtrue simultaneous processingを強制できる。

HTTP/1.1 vs HTTP/2 の違い

AspectHTTP/1.1 (Last-byte sync)HTTP/2 (Single-packet)
同時性数ms〜数十msのばらつきSub-microsecond precision
必要接続数リクエスト数分1本
Network jitter影響大きいゼロ
成功率試行回数が必要ほぼ確実

Attack Patterns

1. Limit Bypass (Coupon / Credit)

クーポン適用やポイント利用で「残り1回」のチェックをrace conditionでbypass:

// 正常フロー
POST /api/redeem-coupon  (coupon: SAVE50)
→ Check: coupon.uses_remaining > 0  ✓
→ Apply discount
→ Decrement: coupon.uses_remaining -= 1

// Race: 20リクエスト同時送信
// 全リクエストが uses_remaining=1 を見る → 全て成功
Real: Valve CD Key Duplication ($20,000)

Steam CD keyの有効化を同時に複数アカウントから実行。 1つのkeyが複数アカウントに適用されるduplicate状態を達成。

2. Balance Double-Spend

// Account balance: $500
// 同時に2つの$500送金リクエスト
POST /api/transfer { amount: 500, to: attacker1 }
POST /api/transfer { amount: 500, to: attacker2 }
// Both check balance >= 500: TRUE → Both succeed
// Result: $1000 transferred from $500 balance

3. State Machine Abuse

多段階プロセス（メール認証 → SMS認証 → アカウント作成）のステップをskip:

Normal: Step1(email verify) → Step2(sms verify) → Step3(create account) Attack: Send Step3 request WHILE Step1 is being processed Server sets state="email_verified" → Step3 checks state → passes (SMS verification never happened)

4. File Upload Race

// Upload → Validate → Delete if invalid
// Race window: between upload and validation

Thread A: Upload malicious.php → saved to /tmp/uploads/abc123.php
Thread B: GET /tmp/uploads/abc123.php → 200 OK (executed!)
          ↑ access BEFORE validation/deletion runs

5. TOCTOU in Access Control

// Permission check race
Thread A: Check user.role == "admin" → FALSE → but thread suspended
Thread B: UPDATE user SET role = "admin" (via another vuln)
Thread A: resumes → performs admin action with old check result

// Or the reverse:
Thread A: Check file permissions → OK
Thread B: Replace file with symlink to /etc/shadow
Thread A: Read file → reads /etc/shadow

Detection & Testing Methodology

識別パターン

  • 数量制限のあるリソース: クーポン、バウチャー、招待コード、ポイント
  • 一度きりのアクション: パスワードリセット、メール変更、2FA登録
  • 残高操作: 送金、購入、出金
  • 多段階フロー: 認証プロセス、KYC、承認ワークフロー
  • ファイル操作: アップロード後の処理、一時ファイル

テスト手順

  1. 対象endpoint特定 (limit/balance/state変更系)
  2. 正常フローを1回実行し、レスポンスを確認
  3. 同一リクエストを20-50本同時送信 (HTTP/2 single-packet)
  4. 成功レスポンス数をカウント (1以上なら脆弱)
  5. 実際のデータ変化を確認 (本当にdouble-spendしたか)
Testing Ethics

本番環境でのrace conditionテストは実データに影響を与える可能性がある。 テスト用アカウント間での操作に限定し、 成功したら即座にrevertして報告すること。

Python h2 Library Example

import h2.connection
import h2.config
import socket, ssl

# Single TCP connection, multiple streams
conn = h2.connection.H2Connection()
conn.initiate_connection()

# Queue multiple requests on different streams
for stream_id in range(1, 41, 2):  # 20 requests
    conn.send_headers(stream_id, headers)
    conn.send_data(stream_id, body, end_stream=True)

# Send ALL frames in one socket.send() call
sock.sendall(conn.data_to_send())  # Single packet!

Defense Mechanisms (攻撃者として知っておくべき)

  • Database-level locking: SELECT FOR UPDATE, advisory locks
  • Idempotency keys: 重複リクエスト検知
  • Optimistic locking: version番号チェック
  • Rate limiting per-operation: 同一操作の連続実行制限
  • Atomic operations: Redis DECRBY等でcheck+useを一体化

これらが実装されていない箇所がrace conditionの攻撃対象。
