Webペネトレーションテストとバグバウンティで、入力を探し、実行条件を確認し、修正まで説明する。

1. 診断の進め方を決める

WebPTでは合意した機能・ロール・ブラウザーを検査し、問題の再現と対策を報告する。バグバウンティでは、プログラムの対象範囲、受理する問題、テスト用アカウント、レートやBlind XSSの扱いを確認して着手する。両方に共通する記録単位は「入力欄」だけでなく「入力した人から閲覧する人への経路」。

  1. 通常操作を記録する。 プロキシの履歴で、機能を動かすリクエスト・応答・閲覧者のロールを押さえる。
  2. 固有の目印を入れる。 たとえば xss-note-7f3a。検索結果、詳細、編集、通知などに現れる場所を探す。
  3. 解釈先を分類する。 HTML本文、属性、URL、JavaScript、DOM APIのどれに渡るかを見る。
  4. 実行条件を絞る。 パーサー、引用符、イベント、必要な操作、CSP、サニタイザーの変換を一つずつ確認する。
  5. 別の閲覧者で再現する。 検査用アカウントBの通常操作で届くか確認し、実行した文書のoriginとロールを記録する。
  6. 最小の再現手順にする。 関係する入力・手順だけに絞り、証拠、修正案、再テスト条件を揃える。

途中の記録は次の形にする。「Aの投稿フォーム → POST本文 → 保存 → JSON API → Bの画面の描画処理 → innerHTML」。これなら、保存、通信、画面のどこを調べたかを追い直せる。

調査メモのひな形を開く 
機能と入力の位置    POST /notes の body.note
入力者と閲覧者      アカウントA → アカウントB
目印とデータID      xss-note-7f3a / note_id=42
応答と保存          POST後に保存、GET /api/notes/42 がJSONを返す
途中の変換          response.json → Markdown変換 → サニタイズ
表示先と文脈        コメント詳細のHTML断片
実行条件と証拠      操作、origin、実行マーカー、該当コード行
次の確認            一覧の抜粋と、保存済みデータの再表示

検査項目の体系は OWASP Web Security Testing Guide、XSSの全体像は PortSwigger XSSを参照。

2. 入力元と閲覧先を対にして探す

検索フォームだけを調べると、保存・再表示・別ロール向けの経路が抜けやすい。通常操作から次の表を埋め、目印が届いた画面ごとに解釈先を調べる。

入力元探す表示先追加の確認
クエリ、パス、検索フィルター検索見出し、パンくず、エラー画面正常時と入力エラー時で異なるテンプレートか。
プロフィール、表示名、組織名一覧、メンバー管理、招待、監査ログ本人以外が読む画面に同じ値が届くか。
コメント、チャット、チケット本文、プレビュー、引用、通知一覧の抜粋と詳細でレンダラーが違うか。
Markdown、リッチテキストHTMLプレビュー、保存後の本文、編集再開変換、サニタイズ、リンク化の順序。
ファイル名、説明、インポート項目ファイル一覧、処理失敗メッセージ、詳細ファイル本文とメタデータを別々に追う。
共有リンク、redirect先、戻り先リンクのhref、遷移処理、ログイン画面URLをブラウザーが最終的にどう解釈したか。
URLフラグメント、SPAルータークライアント側の検索、タブ、エラー表示初回表示と画面遷移時の両方を観察する。
APIの応答、連携サービスのデータフロントエンドが後から作るDOMJSONの解析後にどのフィールドがHTML化されるか。
localStorage、sessionStorage、Cookie設定復元、履歴、直前の入力の復元読み出し元を見つけたら、値を書ける実際の入口も探す。
postMessage、ポップアップ、iframe受信イベントから呼ばれる描画や遷移送信側の画面参照、受信側のorigin検査と型検査。
HTTPヘッダーに由来する記録アクセスログやサポート向け画面どのクライアントがそのヘッダーを設定できるか。
メール、Webhook、外部からの取込アプリ内のメール本文、連携履歴外部データが同一originの信頼済みデータとして扱われていないか。

localStorageを自分のDevToolsで直接編集した実験は、読み出し先の調査に使える。報告には、別の利用者のブラウザーへその値を届ける入口も必要になる。HTTPヘッダーも、プロキシで変更できた条件と、被害者の通常操作で送られる条件を記録する。

3. 何を観察すればXSSの証拠になるか

HTTP応答に目印がある、Elementsに要素が増えた、JavaScriptが動いた、という観察はそれぞれ示す範囲が違う。途中の結果を残しておくと、再現しない原因も説明できる。

観測確認できたこと次に確かめること
応答に入力文字列があるその応答まで値が届いた。Content-Type、前後の構文、エンコード、ブラウザーでの用途。
太字や新しい要素が出るマークアップとして解釈された。仕様の許可範囲と、実行可能な構造が作れるか。
サーバーに画像の読込が届くそのリソースが要求された。プレビュー生成器、クローラー、メールのプロキシ等による読込も考慮する。
入力を通じたコードが検査用の表示を出すその文書内でコードが実行された。origin、ブラウザー、CSP、閲覧ロール、必要な操作。
検査用Bの画面でも通常操作で再現するAからBに到達する実行経路がある。使える権限・データと、再認証などの追加条件。

ラボでは console.log('xss-proof', location.origin) や専用の表示マーカーで実行を確認できる。Consoleに自分で打って動かした結果と、入力欄から届いた値がアプリの処理で実行された結果は、再現手順に区別して記載する。alert() が見えない場合はフレームやブラウザーの制限、イベントの未発火、構文エラーも確認する。

HTMLだけを変えられる問題はHTML injection、DOMの名前解決を変える問題はDOM clobberingとして影響を評価できる。コード実行までの連鎖を示せたときは、その追加条件も説明する。

4. 出力コンテキストを読む

USER_INPUT の前後を観察する。入力が置かれた構文と、入力を読む次のパーサーを特定してから検査を組み立てる。

出力例構文上の着目点修正の方針
<p>USER_INPUT</p>通常のHTML本文としてタグが解釈されるか。テンプレートの自動エスケープ、通常要素のtextContent。
<input value="USER_INPUT">属性の引用符が保持されるか。属性値は実体参照がデコードされる。属性名を固定し、引用符で囲んで属性用エンコード。
<input value=USER_INPUT>空白やタグの終端も属性の構文に関係する。テンプレートで属性値を引用符で囲む。
<a href="USER_INPUT">URLスキーム、基準URL、クリックの必要性。URLを解析して用途に合うスキーム・originを許可する。
<script>const q = 'USER_INPUT';</script>HTMLのscript終端と、JS文字列の両方の構文がある。値をAPI等のデータとして受け取る。埋込みが必要ならテンプレートの専用機能を使う。
バッククォート内の文字列${...} がJSの式として解釈される場所か。外部入力をコード生成に連結せず、変数や関数引数にする。
<button onclick="USER_INPUT">HTML属性の解析後にJavaScriptが解析される。固定したイベントリスナーに関数を登録し、値をデータとして渡す。
<textarea>USER_INPUT</textarea>文字の読まれ方と、その要素の終了タグの扱い。サーバーではその文脈に対応するエンコード、DOMではvalueを使う。
CSSプロパティ、style要素許可した値の範囲、URL、HTML要素の終了境界。色などの値を限定する。任意のCSS全体を組み立てる設計を見直す。

ラボで試す基本例と成立条件

以下はローカルの演習やAcademyの指定ラボで、入力からコードが動く経路を観察する例。各例の前提は、該当する構文の区切りがそのまま届き、実行を許す文書であること。先に目印だけを送り、実際の表示先が表のどれかを確かめよう。

<!-- HTML本文として最初の文書を解析する場合 -->
<script>console.log('xss-proof', location.origin)</script>

<!-- HTML断片の挿入でイベントを観察する場合 -->
<img src="/missing-xss-proof" onerror="console.log('xss-proof', location.origin)">

<!-- ダブルクォートで囲まれた属性で、フォーカス操作を伴う場合 -->
" onfocus="console.log('xss-proof', location.origin)" data-note="

/* JSのシングルクォート文字列を閉じられる場合 */
'; console.log('xss-proof', location.origin); //

/* 文字列をテンプレートリテラルのソースに直接連結している場合 */
${console.log('xss-proof', location.origin)}

innerHTML で追加したscript要素は通常そのまま実行されない。最初の文書として解析されるHTMLと、JavaScriptで追加した断片を区別する。イベント付き要素も、リソースの失敗や利用者のフォーカス操作など、そのイベントの条件が必要になる。

5. デコードとパーサーの順序を書く

「エンコードしたから通る」と覚えると、どの段階で文字が変わったかを見失う。通信上の値、アプリ内の値、最終DOMを並べて記録する。

  1. %3Cb%3E をクエリ値として送る。クエリのパーサーでデコードされると <b> になる。
  2. サーバーがHTML本文用にエンコードすると、応答には &lt;b&gt; が入る。
  3. HTMLパーサーが読むと、本文のテキストノードに <b> の文字が入る。その文字が同じ解析で新しいタグとして読み直されるわけではない。
  4. 後からコードがそのtextContentを読み、別の要素のinnerHTMLに入れると、再びHTML解析が始まる。この2回目の解釈先まで追う。
処理行っていること確認する条件
URLデコード、URLSearchParamsURLで表した値を取り出す。フォーム型の空白・プラスや、アプリの追加デコード。
JSON.parse / response.jsonJSONを値・配列・オブジェクトとして読む。読んだ文字列が次にHTMLやコードへ渡されるか。
HTMLエンコード該当する文字をHTML上の実体参照にする。適用先が本文・属性・script内のどこか。
Base64バイト列を別の表現にする。復元後の値と、その使い方。
HTMLサニタイズ解析したHTMLに許可ポリシーを適用する。設定、バージョン、処理後の変更、最終DOM。

%253C は1回のURLデコード後に %3C になる。追加のデコードが観測される場合に、2段階目を調べる。入力の見た目だけから、サーバーが2回デコードすると仮定しない。

MDN URLSearchParams ／ OWASP DOM based XSS Prevention

テンプレート式を含む入力は、いつ評価される？

入力文字列に ${2 + 2} が含まれていても、通常の変数に入れて表示するだけなら、その中身を式として再評価しない。外部入力がテンプレートリテラルのソース自体に連結されたり、テンプレートエンジンへソースとして渡されたりする箇所を確認する。

6. Reflectedの調査をHTTPとブラウザーでつなぐ

  1. プロキシのHTTP履歴で、検索などの正常なリクエストを選び、メソッド・パス・本文形式・ログイン状態を保存する。
  2. Burp RepeaterやCaidoの再送機能で、1項目だけ目印に変える。応答中の全出現箇所を検索する。
  3. 各出現箇所について引用符やタグを含む前後の構文、エンコード後の文字、Content-Typeを記録する。
  4. ブラウザーの通常画面から同じ操作を行い、Networkの応答とElementsのDOMを比較する。初回表示だけでなくエラー表示や再検索も見る。
  5. 実行が確認できたら、新しいブラウザーセッションで再現し、必要なCookieやヘッダー、入力経路を確定する。

Repeaterで作ったリクエストを、被害者役のブラウザーでどう発生させるかが次の問いになる。GETの共有URL、通常のPOSTフォーム、API呼び出しでは条件が違う。OriginやRefererを手動変更した結果は、ブラウザーが実際に送れる値と照合する。フラグメントの # 以降はHTTPリクエストに送られないため、通常のHTTP再送だけで同じsourceを検査できない。

Content-Typeを変えたら挙動が違った

JSON、フォーム、multipartのどれでパラメーターを読み取るかはサーバー側の設定に依存する。ヘッダーだけを変えた場合と、本文も対応形式に変えた場合を分けて記録する。CORSプリフライトやCookieのSameSite条件もあるため、受け付ける本文形式だけでクロスサイトの実行経路を確定できない。

PortSwigger Reflected XSS ／ Body Formats ／ CSRF教材

7. Storedは保存から別の閲覧者まで追う

保存時の応答が安全でも、一覧、検索の抜粋、管理画面、通知の本文で出力処理が違う場合がある。検査用Aで投稿し、Bの別プロファイルで開く。別タブは同じCookieを共有するので、ロールの検査ではアカウントを分離する。

経路調べる条件記録する結果
Aの作成画面 → プレビュー一時表示のレンダラーと保存後のレンダラー。どの段階でHTMLが生成されたか。
Aの投稿 → Bの一覧・詳細共有範囲、閲覧権限、リンクや操作の必要性。Bが通常操作で実行したoriginと画面。
Aの編集 → Bの検索・通知元データとキャッシュや抜粋の更新。修正前の値が残る保存先。
Aの投稿 → 担当者の画面担当者権限と画面への到達方法。実測できた権限と、アクセスできず未確認の部分。
API保存 → JSON取得 → DOM描画APIの文字列を最後に使うJavaScript。StoredとDOM-basedの両方を示す経路。

Blind XSSを調べるとき

結果の画面を直接見られないケースでは、プログラムが認めるコールバックの扱いを確認する。発火時刻、テストID、関連リクエストを結び付ける。外部リソースへのアクセス1回だけでは、コード実行や管理者権限まで判断できない。検査用画面へのアクセスや、トリアージ側の確認で証拠を補う。Cookie・画面全体の収集が必要かは実証したい影響に合わせて判断する。

レポートには保存したデータのIDと除去方法を含める。再訪時の影響と、後述の修正後再テストに必要になる。

8. DOMの調査は呼び出し元まで戻る

まずElementsで目印の入ったノードを見つけ、DevToolsのDOM変更ブレークポイントで、値を挿入した行とコールスタックを見る。Sourcesの検索で innerHTML を見つけたら、呼び出し時の値、source、途中の変換をたどる。文字列検索のヒットだけでは脆弱性の成立を判断できない。

  1. NetworkでJSファイルとAPI応答を確認する。ソースマップが利用できる場合は、配信コードとの対応も確認する。
  2. 目印を入れ、画面遷移・編集・モーダル表示など、値を使う操作を行う。
  3. 対象ノードに「subtree modifications」等のブレークポイントを置き、もう一度同じ操作を行う。
  4. 停止した行で、渡された値とcall stackを記録する。早い初期描画の場合は呼び出し行にブレークポイントを置いて再読み込みする。
  5. sourceからsinkまでの変換を表にし、同じ実行経路を新しいセッションで確認する。
// 要件は検索語を文字で表示すること
const value = new URL(location.href).searchParams.get('q') ?? '';
const output = document.querySelector('#result');

// 調査対象になるHTMLの解釈先
output.innerHTML = value;

// 要件に合う修正
output.textContent = value;

この例では searchParams.get() が値を読む入口で、innerHTML のsetterがHTML解析を始める。JSON.parse()、decodeURIComponent()、Base64の復元処理は、前後にあってもHTMLサニタイザーとしては働かない。

BurpのDOM Invaderは、source・sinkの観察やpostMessage調査を補助する。自動検出後も、手動操作での到達、実際の呼び出し値、必要な操作を保存する。ライブラリのsink一覧は 基礎編と合わせて読む。

名前付きDOM参照も確認する

DOM clobberingでは、要素のidやnameが window などの名前付き参照に影響し、既存のコードが想定外の要素を設定値として読む場合がある。たとえば window.appConfig を参照するコードなら、その値がアプリ自身のオブジェクトであることをどこで保証するかを見る。HTMLを追加できることに加え、その名前を読むコードと、URLや実行先に使われる経路が成立条件になる。

9. postMessageは送信元と値の用途を両方調べる

message ハンドラーを見つけたら、「誰が受信側のWindowを参照できるか」「event.originとsourceを検査するか」「event.dataをどこに渡すか」を追う。origin検査が欠けていても、その後の処理が文字を表示するだけなら、それだけでXSSの成立までは示せない。

たとえば、信頼した埋込みウィジェットから検索語を受け取る画面なら、次のように契約を限定できる。originはアプリが設定する固定値にし、iframeもアプリが管理する。

const widget = document.querySelector('#trusted-widget');
const expectedOrigin = 'https://widget.example';

window.addEventListener('message', event => {
    if (event.origin !== expectedOrigin ||
        event.source !== widget.contentWindow) return;

    const message = event.data;
    if (!message || message.type !== 'search-label' ||
        typeof message.label !== 'string') return;

    document.querySelector('#label').textContent = message.label;
});

送信側も postMessage(message, expectedOrigin) と受信先を指定する。includes('example.com') のような文字列検査と、scheme・host・portを含むoriginの一致は扱いが異なる。受信したURLへ遷移する設計なら、メッセージの検査に加え、遷移先URLの許可も別に検証する。

event.source を確認しても、そのWindowが後でどこへ遷移したかまで固定されるわけではない。返信する場合も、確認した相手のoriginを指定する。sandbox等によりoriginが null になる設計は、信頼判定の条件を個別に見直す。

MDN postMessage security concerns ／ PortSwigger web message source

10. Sanitizerの前後にある処理まで検証する

リッチテキストでは「どのタグ・属性・URLを許可するか」が仕様になる。ライブラリ名だけで終えず、バージョン、ポリシー、呼び出し箇所、処理後に使うライブラリ、最終的な挿入先を記録する。

確認する箇所具体的な問い修正後の証拠
タグと属性strongやem以外を許す必要があるか。data属性やARIA属性の扱いは明示したか。許可した装飾は残り、除外した属性が最終DOMに存在しない。
リンクと画像href・srcを許す場合、URLスキームと読み込む相手をどう制限するか。許すURLが通り、用途外のURLは取り除かれる。
処理順序Markdown変換、リンク化、構文ハイライトがいつ動くか。全処理の終了後に許可条件が満たされている。
戻り値と再利用ノードとして使うか、文字列に戻して違う親へ再挿入するか。表示先のDOMとサニタイズ時のDOMの差が説明できる。
実行環境ブラウザー版とサーバー版でパーサーやDOM実装が違うか。両方の環境とバージョンを指定して再現する。
更新と古いデータ依存ライブラリの修正が入ったか。以前の加工済みHTMLやキャッシュが残るか。新規入力と既存保存データの両方で修正を確認する。

mXSSの検査で比較する3段階

  1. サニタイザーが解析したDOMと、許可・除外した構造。
  2. 処理後のHTML文字列と、その後の文字列加工。
  3. 表示先の要素・名前空間で再解析された最終DOMと実行結果。

ブラウザーがtbodyを補うような通常の構造変化だけでは、mXSS成立を判断できない。検査時には除外したはずの実行可能な構造が後から生じるかを確認する。過去のbypassを読む場合も、その時点のサニタイザー・設定・ブラウザーの条件を添える。対策は依存の更新に加え、処理済みの内容を後から無制限に加工する経路の見直しになる。

12. CSP・Trusted Types・sandboxを実測する

適用されるのは、実行する文書が受け取ったポリシー。検査したリクエストとレスポンス、ブラウザー、フレームを対応させて保存する。CSPが原因で実行されないのか、そもそも実行可能なDOMになっていないのかを分けて調べる。

機構確認すること判断するときの条件
Content-Security-Policy強制適用のヘッダー、違反したdirective、実際のDOM。複数のポリシーがあればすべて適用される。単に許可元を合算する読み方はできない。
Report-OnlyContent-Security-Policy-Report-Onlyと強制適用の有無。Report-Only単体のポリシーは違反を遮断しない。
nonce / hashどのスクリプトに許可が付いているか。nonceの生成・再利用。nonceは応答ごとに予測困難な値にする。実行を許された既存コードの使い方も対象になる。
strict-dynamic信頼されたコードが動的に読み込むscriptのURL。対応ブラウザーでは信頼が動的読込へ伝わる。URL生成を外部入力が左右するか確認する。
script-src 'self'同じoriginからどんなscriptが配信されるか。origin単位の許可であることを踏まえ、アプリのアップロードや既存の読込処理と照合する。
base-uri / object-src / connect-src基準URL、文書埋込み、通信の制限。それぞれのdirectiveが制御する処理を確認する。connect-srcだけから他の読込経路まで結論付けない。
Trusted Typesrequire-trusted-types-for、許可ポリシー、ポリシー内の処理。型を生成する処理が安全な変換を行うか。対象sinkとブラウザーの対応も必要。
iframe sandboxallow-scripts、allow-same-origin、フレームの実際のorigin。スクリプト実行、origin、フォーム等は別の権限。許可の組み合わせを記録する。

対策としては、不要なHTML解釈をなくす、許可したHTMLをサニタイズする、適切なCSPを強制する、対応環境でTrusted Typesを用いる、という各層を組み合わせる。入力からsinkまでの欠陥を修正し、CSPのブロックだけに結果が依存していないか再テストする。

13. ファイルやSVGは表示方法を記録する

アップロード時に送信するContent-Type、保存後に配信されるContent-Type、閲覧するブラウザーの文脈を別々に確認する。画像を受け付ける機能でも、ファイル名をHTMLで表示する一覧と、ファイルそのものを開く画面ではsourceもsinkも違う。

表示方法確認する条件
imgやCSSの画像としてSVGを読む画像コンテキストではスクリプトは無効。ファイル本文がそのモードで表示されているかを確認する。
SVGのURLを直接開く文書として配信するヘッダー、実際のorigin、CSP、認証Cookieの適用範囲。
iframe / object等で文書を埋め込む文書側と親側のorigin、sandbox、CSP、親の埋込み許可。
HTML本文へSVGをインライン挿入HTMLサニタイザーの設定、要素の名前空間、挿入経路と最終DOM。

ファイルが別originで実行されても、主アプリの権限を持つかは追加の確認が必要になる。cookieのDomain属性、親とのpostMessage、共有している信頼関係を調べる。Content-Dispositionがattachmentなら通常はダウンロードになるため、実際の閲覧方法も再現手順へ含める。

アップロード対策は、必要な形式だけを受理し、内容を検証し、配信時にも正しいContent-Typeと必要な制限を設定する。受け取ったファイル名や説明の出力エンコードも別に行う。SVGのContent-Typeを見ただけで主アプリ内のコード実行まで結論付けない。

14. 影響を確認し、再現できる報告にする

XSSの型だけからseverityや報奨金は決められない。実行したorigin、到達するユーザー、権限、扱えるデータ、必要な操作と追加認証を根拠にする。PoCは、まず検査用データと検査アカウントで観察できる最小の実行証拠を用意する。

影響の候補確認する条件残す証拠
他ユーザーの画面内で実行閲覧に必要な操作、攻撃者と閲覧者の関係。Aの保存要求、Bの再現操作、originと専用マーカー。
情報の読取そのoriginのスクリプトから読める検査データ。検査用の値を読めた画面と、その値の権限条件。
ユーザー権限での操作CSRF対策、再認証、MFA、権限チェック。検査用の表示名など、合意した操作の前後。
担当者・管理者への到達実際の担当者ロール、利用できる機能。確認したロールと操作。未検証の機能は未検証と記す。
セッションやトークンへの影響保存場所、HttpOnly、トークンの用途と有効期間。実測した読取可否や操作可否。秘密値は共有前に伏せる。
キャッシュ等で複数人へ到達キャッシュキー、有効期間、利用者の範囲。異なる検査セッションでの取得結果と対象応答。

HttpOnly・CSRF・SOPをどう読むか

HttpOnlyはJavaScriptによるCookie値の読取を制限する。条件が合うリクエストへのCookieの付与は続くので、同じoriginで実行できるコードは、その利用者の権限でAPIを呼べる場合がある。CSRFトークンを読めるか、重要操作に再認証があるかも調べる。

SOPはorigin間の読取を制限する。実行した場所が uploads.example.test なら、app.example.test のDOMや応答をそのまま読めるとは限らない。アカウント乗っ取りを報告する場合は、そのアカウントを継続して制御できる操作まで必要条件を説明する。

16. 調査の判断を練習する8問

各問で、入力元、途中の変換、表示先、次に観察する証拠、修正案を一行ずつ書いてから解答を開こう。実際に確認できたことと、追加の確認が必要なことも記録する。

1. 検索語がレスポンスに見つかった

検索語に <b>京都</b> を送ると、応答の本文に &lt;b&gt;京都&lt;/b&gt; があった。画面にもタグを含む文字が見える。この時点で何が分かり、次にどこを確認する？

解答と照合する

入力元は検索パラメーター。HTML エンコードされた値をブラウザーが本文の文字として表示している。次は Elements で生成されたノードと、JavaScript がこの値を読み戻す経路を確認する。後段の innerHTML への再代入があれば、そこで再評価する。本文表示の修正にはテンプレートの自動エンコードや textContent が適している。

2. 挿入した script が動かない

コードレビューで preview.innerHTML = input.value を見つけた。練習環境で script 要素を渡しても実行されなかった。この結果から何を判断し、調査をどう続ける？

解答と照合する

入力欄が source、代入時の HTML 解析が sink。innerHTML によって挿入した script 要素の通常の非実行は、この API の挙動と整合する。生成された要素・属性、CSP、必要なイベントまで追い、実行可能な経路を判断する。文字だけを表示する仕様なら textContent に変更し、タグが文字として残ることを確かめる。

3. 投稿本文は JSON にしか見つからない

利用者Aの投稿を利用者Bで開く。最初の HTML のリストは空で、後から取得した JSON に本文があり、JavaScript が list.insertAdjacentHTML() に渡していた。分類と修正の確認点は？

解答と照合する

source はAが保存した投稿で、JSON の解析後も投稿者が決めた値が残る。ブラウザー側の HTML 挿入が sink。実行可能性が確認できれば Stored DOM XSS と説明できる。Bの読み出しまで追い、文字表示なら textContent、装飾を許すなら表示仕様に合わせたサニタイズを適用し、最終 DOM を検証する。

4. message の送信元を部分一致で見ている

プレビュー画面は event.origin.includes('example.com') を通ったメッセージの data.html を HTML として挿入する。何を境界として確認し、どのように直す？

解答と照合する

source は message の data。部分一致では想定外のオリジンも通り得るため、許可した scheme・host・port の完全一致を確認する。固定の相手窓を持つ設計では event.source も照合し、データの型と構造を検証する。本文は仕様に従い textContent またはサニタイズ済みの構造を渡す。送信元の確認と出力処理を両方検証する。

5. HttpOnly と CSP が設定されている

セッション Cookie は HttpOnly、レスポンスには Content-Security-Policy-Report-Only がある。担当者は「この画面の XSS は影響を持たない」と考えた。証拠をどう整理する？

解答と照合する

入力から sink までの経路と実行結果を先に確かめる。HttpOnly の Cookie を JavaScript で読むことは制限されるが、同一オリジンへのリクエストには Cookie が送られ得る。Report-Only は違反の観測用。実際に適用される CSP、実行したオリジン、テスト利用者で確認できた読み取り・操作の範囲を記録し、根本の出力処理を直す。

6. アップロードした SVG は画像として見える

プロフィールでは SVG を img 要素で表示している。別の「原寸で開く」リンクはファイルを新しいタブで直接開く。アップロード機能の XSS を調べるとき、この2つで何を比べる？

解答と照合する

source はアップロードしたファイル。img の画像読み込みと、直接開く SVG 文書では実行の条件が異なる。各表示の URL・オリジン、Content-Type、Content-Disposition、CSP を記録し、アプリの権限に届く経路を確認する。修正案も表示方式に合わせ、画像変換や隔離配信、文書を表示する際の制限を検討する。

7. サニタイズ後に装飾ライブラリを通している

本文をサニタイズした直後には許可したタグだけが残る。その文字列を別のライブラリで装飾し、表示先に挿入すると DOM の構造が変わった。mXSS と判断するには何が必要？

解答と照合する

source は元の投稿、変換はサニタイズ・装飾・再解析、sink は最終挿入先。各段階の文字列と木を記録し、許可されていない実行可能な構造が生じるか確認する。装飾処理が元入力を連結する不具合と、解析差による mXSS は原因を追って区別する。表示直前までの処理順と文脈を見直し、最終 DOM を再テストする。

8. 新しい投稿だけ安全になった

修正後に投稿したテスト本文は正しく表示された。修正前の投稿、編集画面、管理者のプレビューはまだ確認していない。何を追加で試せば、再テスト結果を説明できる？

解答と照合する

保存済みの旧データも source に含め、一覧・詳細・編集・管理者プレビューの sink を確認する。新規入力だけの制限では既存値が残るため、読み出し時の処理も追う。修正前の再現手順と無害な正常値を同じ条件で試し、ブラウザー、役割、CSP、最終 DOM を記録する。既存投稿を含む表示処理の修正と機能維持を検証する。
