AI Slop Avoidance

AI-assisted な脆弱性報告が「実際には exploitable でない」パターンを認識し、 自分のレポートがそうならないための prevention framework。 mei-bb で 6件撤回した経験から体系化。

Case Study Theory

AI Slop とは

AI（LLM）を使って脆弱性調査を行った際に、コード上は脆弱に「見える」が実際には exploit できないパターンの報告。以下の特徴を持つ:

  • コードの静的分析だけで「脆弱性あり」と判断（動的検証なし）
  • Security impact を推測で主張（実証なし）
  • 環境依存を無視（OS, runtime, configuration の差異）
  • Product の design intent を理解せずに「バグ」と判断
  • Simulation のみで PoC とし、実 runtime でのテストを省略

BB platform (特に huntr) では AI slop 報告が急増しており、triage team の負荷が上がっている。これは hunter の信頼を損なう最大のリスク。

AI Slop の典型パターン

Pattern 1: Structural Evidence Only

コードに eval() や exec() がある → 「RCE 可能」と主張。しかし入力が sanitize されている、あるいは到達不可能なコードパス。

Pattern 2: Wrong OS/Environment

Windows でのみ再現する path traversal を Linux production に対して報告。DNS resolver の挙動が OS 依存なのに cross-platform claim。

Pattern 3: Simulation-Only PoC

Python script で「こういう入力を送ったらこういう結果になるはず」とシミュレーション。実 runtime でのテストなし。Mock/stub で通しただけ。

Pattern 4: Impact Speculation

「This could potentially lead to...」で始まる impact claim。「もし X が Y に使われていれば Z になる」。条件が多すぎて現実に成立しない。

Pattern 5: By-Feature (Design Intent)

Product の collaboration/sharing model から自然に導かれる behavior を「脆弱性」と報告。Shared view でユーザ一覧が見える = designed behavior。

Pattern 6: Admin/Debug Config Dependency

Admin override や debug flag を有効にした状態で PoC を作成。Production default では再現しない。

mei-bb 撤回事例

vercel/ai: trailing-dot DNS bypass

Windows の DNS resolver でのみ再現。Linux (production) では trailing dot は正常に resolve。Cross-OS verify を怠った。

Uber Firebase: test environment

テスト環境の Firebase rule が open だったが、production とは完全に分離。Production impact = 0。

Pyroscope: by-feature

Auth doc を読まずに auth bypass を主張。実際には bogus credential でもアクセスできる = auth が元々ない endpoint だった。

immich: design ambiguous

Shared album で photo metadata が見える。Privacy concern ではあるが、vendor が意図的に設計した behavior の可能性が高く、spec が曖昧。

vercel/workflow: predictable token

runId が predictable に「見えた」が、実際は CSPRNG 由来。Seed material の generator を確認せず「公開情報から予測可能」と主張。

NocoDB: shared-view users[]

Shared view でユーザリストが API response に含まれる。Product の collaboration model 上は自然な behavior。By-feature。

Prevention Framework

bb-aislop-gate scan

Submit 前に自動スキャン。HOLD = submit-block。25+ の weakness pattern (W1-W25) を機械的に検出。

  • W1: Speculation-based severity claim
  • W8: Trust model violation
  • W11: Severity escalation without verification
  • W13/W14: Primitive detection without sink demo
  • W19: Quality defect framed as security
  • W20: Intentional CORS design
  • W25: Advisory wording over-interpretation

bb-fp-detector

False positive detector。環境差異 (OS, config, runtime) による非再現を事前検出。

End-to-End Verification Rule

Sink で actual exploit demo するまで verified_poc と主張禁止。

  • Echo upstream / scope-check pass / raw forward 確認だけでは不十分
  • 「primitive を検出した」だけでは submit 不可
  • 最終的な impact (data leak, state change, code execution) を実機で示す

4-Axis Pre-Submit Audit

Submit 直前に以下の 4 軸で self-audit を実施:

  1. Trust Model: 脆弱性の前提が product の trust model と整合するか
  2. Spec Compliance: Report の claim が仕様に violation しているか (docs 未記載だけでは bug 認定禁止)
  3. Strictly Weaker: PoC 環境が production より strictly weaker な security posture でないか
  4. PoC Env Fidelity: PoC 環境が production default と一致するか (admin override / debug flag 依存チェック)

Intigriti AI Disclosure

Intigriti は 2026-03 の CoC 更新で AI 使用の disclosure を必須化:

  • When: どのフェーズで AI を使ったか (recon, analysis, PoC, report writing)
  • How: 具体的にどのツール/モデルをどのように使ったか
  • 違反 = report close / platform 除外
  • AI 使用自体は禁止されていない。透明性が求められる

AI Slop Self-Check Checklist

Submit 前に以下を自問。1つでも No なら submit しない:

  1. 実 runtime (Docker/VM/live instance) で PoC を実行したか？
  2. PoC の結果として actual impact (data leak, state change) を示せるか？
  3. Production default の設定で再現するか？ (admin flag / debug mode 依存でないか)
  4. Attack chain の各 step が attacker の base capability で実現可能か？
  5. Product の auth docs / design docs を読んだか？
  6. 同じ PoC を Linux production 環境で実行しても再現するか？
  7. 「by-feature」(設計上意図された動作) でないと確信があるか？
  8. Seed material / token の generator を確認したか？ (CSPRNG なら predictable ではない)
