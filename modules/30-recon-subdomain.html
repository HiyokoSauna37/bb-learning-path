Subdomain Enumeration

Attack surface の拡大は subdomain 発見から始まる。Passive と Active の両面から隠れた資産を洗い出す。

Theory Practice
Phase 2 → Phase 3: なぜ Blackbox Testing を学ぶのか

Phase 2 ではソースコードを読んで脆弱性を見つけた (Whitebox)。 しかし HackerOne / Intigriti / IssueHunt の多くのプログラムではソースコードは提供されない — 外部から動いているWebアプリをテストする。 Phase 2 で学んだ「どんなバグがあるか」の知識はそのまま使える。Phase 3 ではコードが見えない状態で同じバグを見つける方法を学ぶ。 「中身を知っている → 外から探す」の順番だから効率的に学べる。

なぜ Subdomain Enumeration が重要か

大企業のプログラムでは *.target.com がスコープになっていることが多い。 メインのドメインは堅牢でも、dev.target.com や staging.target.com のような 忘れ去られた subdomain には古いコード、デフォルト認証情報、未パッチの脆弱性が残っている。

Subdomain enumeration は recon の最初のステップであり、ここで得られる結果が 後続の content discovery, vulnerability scanning の全体の質を決定する。

Passive Enumeration

ターゲットに直接リクエストを送らずに subdomain を収集する手法。 検知リスクがゼロであり、最初に実行すべきステップ。

subfinder

ProjectDiscovery のツール。複数の passive source を並列クエリし、高速に結果を返す。

# 基本実行
subfinder -d target.com -o subdomains.txt

# 複数ソース＋再帰的
subfinder -d target.com -recursive -all -o subs_full.txt

# API key 設定 ($HOME/.config/subfinder/provider-config.yaml)
# SecurityTrails, Shodan, VirusTotal などの API key を設定すると結果が倍増

amass (Passive Mode)

OWASP プロジェクト。subfinder より多くのデータソースに対応するが、動作が重い。

# Passive only (Active brute force を行わない)
amass enum -passive -d target.com -o amass_passive.txt

# Config file で API key 管理
amass enum -passive -d target.com -config config.ini

Certificate Transparency (crt.sh)

SSL証明書の発行ログから subdomain を取得。無料で大量のデータが得られる。

# crt.sh API
curl -s "https://crt.sh/?q=%.target.com&output=json" | \
  jq -r '.[].name_value' | sort -u

# Wildcard 証明書も含めて取得
curl -s "https://crt.sh/?q=%.%.target.com&output=json" | \
  jq -r '.[].name_value' | sort -u

その他の Passive Source

  • SecurityTrails — 履歴DNS情報を含む、API 無料枠あり
  • VirusTotal — subdomain 関連情報を大量保持
  • Shodan — SSL証明書から逆引き
  • Censys — 証明書検索に強い
  • dnsdumpster.com — 無料のDNS情報可視化

Active Enumeration

DNS brute force でターゲットに直接クエリを送る。Passive で見つからない 内部的な命名規則の subdomain を発見できるが、検知リスクがある。

DNS Brute Force

# puredns - 高速かつ resolver validation 付き
puredns bruteforce wordlist.txt target.com \
  --resolvers resolvers.txt -o brute_results.txt

# shuffledns - massdns のラッパー
shuffledns -d target.com -w wordlist.txt \
  -r resolvers.txt -o shuffled_results.txt
Wordlist の選択が鍵
  • SecLists/Discovery/DNS/ — 汎用リスト
  • n0kovo_subdomains — 実際のサブドメインから生成された高品質リスト
  • all.txt (Jason Haddix) — 大規模ブルートフォース用
  • ターゲット固有のパターンを追加（社名, 製品名, 地域コード）

Permutation (変形生成)

既知の subdomain をベースに変形パターンを生成して追加発見を狙う。

# altdns - 既知サブドメインからpermutation生成
altdns -i known_subs.txt -o permuted.txt -w words.txt
puredns resolve permuted.txt --resolvers resolvers.txt

# gotator - より高速な permutation
gotator -sub known_subs.txt -perm permutations.txt -depth 1 | \
  puredns resolve --resolvers resolvers.txt

例: api.target.com が既知なら api-dev, api-staging, api2, api-v2 などを自動生成する。

Validation: Alive Check

DNS で解決できても HTTP サービスが稼働しているとは限らない。 実際にアクセス可能なホストだけをフィルタする。 

# httpx - 高速な HTTP probe (ProjectDiscovery)
cat all_subdomains.txt | httpx -o alive.txt \
  -status-code -title -tech-detect -follow-redirects

# httprobe - シンプルな alive check
cat all_subdomains.txt | httprobe -p http:80 -p https:443

# httpx で詳細情報取得
cat all_subdomains.txt | httpx -json -o detailed.json \
  -status-code -content-length -title -web-server -tech-detect
BB視点: httpx の -tech-detect

技術スタックの特定は脆弱性仮説の構築に直結する。 WordPress なら known plugin vuln、Laravel なら debug mode 露出、 といった次のアクションが見える。

Automation Pipeline

日常的な recon は pipeline として自動化する。新規 subdomain の発見を継続監視。

# 基本パイプライン
subfinder -d target.com -silent | \
  httpx -silent -status-code -title | \
  nuclei -t cves/ -t exposures/ -o findings.txt

# 定期実行で差分検知
subfinder -d target.com -silent | sort > today.txt
comm -13 yesterday.txt today.txt > new_subs.txt
cat new_subs.txt | httpx -silent | nuclei -t cves/

# notify で Slack/Discord に通知
cat new_subs.txt | httpx -silent | \
  nuclei -t cves/ -silent | notify -provider slack

Subdomain Takeover

DNS の CNAME レコードが指す先のサービスが解約されている場合、 攻撃者がそのサービスを claim して subdomain を乗っ取れる。

仕組み

  1. dev.target.com が CNAME で target.herokuapp.com を指す
  2. target が Heroku アプリを削除する
  3. DNS の CNAME は残ったまま (dangling CNAME)
  4. 攻撃者が Heroku で target.herokuapp.com を作成して claim
  5. dev.target.com へのアクセスが攻撃者のコンテンツを表示

検出方法

# subjack - 自動チェック
subjack -w subdomains.txt -t 100 -timeout 30 -o takeover.txt

# nuclei takeover templates
cat subdomains.txt | nuclei -t takeovers/

# 手動確認: CNAME 先のサービスが 404/not found を返すか
dig CNAME suspicious.target.com
curl -I suspicious.target.com
注意: False Positive に気をつける

CNAME 先が存在するが単に 404 を返しているケースは takeover ではない。 Fastly のように CNAME が *.fastly-edge.com を指していても、 そのドメインが実際に unregistered でなければ takeover は成立しない。 必ず vulnerable subdomain 自身に curl して確認すること。

Key Takeaways

  • Passive first — 検知リスクなしで大量の subdomain を収集
  • 複数ソースの組み合わせ — 1つのツールで全ては見つからない
  • Validation は必須 — DNS 解決だけでなく HTTP alive check まで行う
  • Permutation で追加発見 — 既知の命名規則から推測を広げる
  • 継続的な監視 — 新規 subdomain は新しい attack surface
  • Takeover は High severity — dangling CNAME の検出は低コストで高報酬
