Practice: bb-whitebox-01 演習

TaskFlow API (Express/Node.js) の whitebox security audit 演習。認証、タスク管理、チーム、ユーザー、Webhook、Admin の6つの route に埋め込まれた脆弱性を発見せよ。

Practice Hands-on

演習対象: TaskFlow API

場所: practice/bb-whitebox-01/

Express ベースの Task Management API。以下の route 構成:

Route File機能Auth Required
routes/auth.jsRegister, Login, Password ResetNo (public)
routes/tasks.jsCRUD for tasksYes
routes/teams.jsTeam creation, member managementYes
routes/users.jsProfile, avatar, settingsYes
routes/webhooks.jsWebhook registration, triggerYes
routes/admin.jsUser management, system configYes (admin)

Setup

cd practice/bb-whitebox-01
npm install
node server.js  # Port 3000

演習の進め方

  1. Phase 1: Sink Survey — 各ファイルを grep で sweep し、危険な sink を列挙
  2. Phase 2: Auth Audit — middleware 適用状況を確認、抜け漏れを探す
  3. Phase 3: Data Flow Trace — 各 sink に対して source (user input) が到達するか追跡
  4. Phase 4: PoC 作成 — 脆弱性を確認する curl コマンドを作成
  5. Phase 5: Report Draft — huntr 形式で報告書を作成 (練習)
目標: 5つ以上の脆弱性クラスを発見する

この演習には少なくとも以下のカテゴリの脆弱性が埋め込まれている: Auth Bypass (JWT), SQL Injection, Command Injection, IDOR, SSRF, Path Traversal。全て見つけられるか?

時間の目安とコツ

想定所要時間: 2〜4時間で5個以上の発見。4時間で3個未満なら Module 20〜24 を復習してから再挑戦。

詰まったら: 1つのカテゴリに30分以上悩んだら Hint を開き、それでも分からなければ次の route に移る。後で戻れば良い。

おすすめ順序: admin.js (auth bypass が最も見つけやすい) → tasks.js (SQLi の grep pattern が明確) → webhooks.js (SSRF は関数1つ確認するだけ)

Route ごとのヒント

auth.js

認証フローは全ての出発点。登録・ログイン・パスワードリセットの実装を確認。

password reset の token 生成を確認せよ。crypto.randomBytes のバイト数は十分か? 4 bytes = 32bit は brute-force 可能。token の有効期限チェックは?

登録時の入力バリデーションを確認。role フィールドは制御されているか? JWT の algorithms 設定 (alg: none) は?

tasks.js

タスクの CRUD 操作。最も機能が多い route。

task の search/filter 機能を確認。query パラメータが SQL 文に直接連結 (string interpolation) されていないか? sort_by パラメータも要確認。

task の export 機能を確認。ファイルパス構築に user input が使われていないか? path.join の引数を確認。

teams.js

チーム機能は authorization (認可) の実装が重要。

チームメンバーの追加/削除に owner チェックはあるか? 他人のチームを操作できないか? (IDOR)

invite 機能のトークン生成と検証を確認。timing attack は可能か?

users.js

ユーザープロファイルとアバター管理。

avatar upload のファイル名処理を確認。ユーザ指定のファイル名がそのまま保存パスに使われていないか?

profile update でどのフィールドが変更可能か? role や isAdmin など権限関連フィールドは保護されているか?

webhooks.js

Webhook は SSRF の典型的な sink。

webhook の URL 登録時に validation はあるか? http://127.0.0.1 や http://169.254.169.254 はブロックされるか?

webhook trigger 時の HTTP request に redirect follow はあるか? DNS rebinding 対策は?

admin.js

Admin route は最も高い privilege。認可チェックが正しいか?

admin middleware の適用を確認。全 route に admin check が付いているか? 一部 route は auth のみで admin check がないのでは?

system config の更新で eval や動的コード実行はないか? template rendering に user input は渡されていないか?

Grep Sweep テンプレート

まずはこれで全体を sweep:

# Sink survey
rg -n "exec\(|execSync\(|spawn\(" practice/bb-whitebox-01/
rg -n "eval\(|Function\(" practice/bb-whitebox-01/
rg -n "path\.join\(.*req\." practice/bb-whitebox-01/
rg -n "query.*\$\{|query.*\+" practice/bb-whitebox-01/
rg -n "db\.(run|get|all|prepare)" practice/bb-whitebox-01/
rg -n "axios\(|fetch\(|http\.get\(" practice/bb-whitebox-01/
rg -n "Math\.random\(\)" practice/bb-whitebox-01/

# Auth audit
rg -n "router\.(get|post|put|delete)" practice/bb-whitebox-01/routes/
rg -n "authMiddleware|requireAuth|isAdmin" practice/bb-whitebox-01/

Key Takeaways

  • Grep sweep first: 全 sink を機械的に列挙してから深掘りする
  • Auth audit: middleware 適用状況を route 一覧と突き合わせる
  • 1つ見つけたら sibling を探す: 同じパターンが他の route にもある
  • PoC は curl で完結: 再現性のある minimal PoC を作成する習慣
  • この演習の技術は huntr の実際の target にそのまま適用可能
