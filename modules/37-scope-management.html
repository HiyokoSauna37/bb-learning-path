Scope Management & Prioritization

限られた時間でどこを攻めるか。スコープの読み方、優先順位の付け方、 そして「いつ撤退するか」の判断基準。

Theory

Program Scope の読み方

In-Scope Assets

program page に明記された攻撃対象。ここだけをテストする。

  • *.target.com — Wildcard: 全 subdomain が対象
  • app.target.com — 単一ドメイン: そこだけ
  • Android/iOS App — モバイルアプリ + その API
  • API (api.target.com) — API endpoint のみ
  • GitHub repos — ソースコード + self-hosted instance

Out-of-Scope (OOS)

絶対に触れてはいけないもの。違反すると ban される。

  • DoS/DDoS — サービスの可用性を損なうテスト
  • Social Engineering — 従業員へのフィッシング
  • Physical Attacks — 物理アクセスが前提の攻撃
  • Third-party services — target が利用している外部サービス
  • MITM-required attacks — 中間者攻撃が前提の脆弱性
  • Self-XSS — 被害者の操作なしに再現できない XSS
OOS Rule と Attack Chain の突き合わせ

Submit 直前に、自分の attack chain の primary step が OOS rule に 抵触しないか必ず確認すること。 例: 「MITM-required attacks are out of scope」であれば、 MITM が前提のシナリオは severity に関わらず reject される。

Attack Surface Mapping

全 endpoint を列挙した後、どこが最も脆弱そうかを優先順位付けする。

High-Priority Targets

  • 認証・認可系 endpoint — /login, /register, /password-reset, /api/admin/*
  • ファイルアップロード — 任意のコンテンツを注入できる可能性
  • Payment / Financial — 金銭的影響 = 高 severity
  • User data endpoints — /users/{id}, /profile, /settings
  • Search / Filter — SQL injection, XSS の入口
  • Export / Download — SSRF, Path Traversal の可能性
  • 新機能 / Beta 機能 — テストが不十分な傾向

Low-Priority (but not zero)

  • Static content pages
  • Marketing / Blog (別ドメインの場合は特に)
  • Well-known frameworks のデフォルト endpoint

Time-Boxing: いつ撤退するか

1つのターゲットに無限に時間をかけてはいけない。 成果が出ないまま深追いすると、他の有望なターゲットを逃す。

Time-Boxing ルール

フェーズ 最大時間 判断基準
Initial recon 30 min Attack surface の広さを評価
Deep dive (1 target) 2-4 hours 具体的な仮説が立たなければ pivot
PoC development 1-2 hours 再現できなければ保留して次へ
Anti-bot wall detection 5 min 403 + 大 body = 即 pivot
Session Budget: Max 2 Pivots

1 セッションで program を切り替えるのは最大 2 回まで。 3 回目の pivot が必要な場合はセッションを終了し、 アカウント作成などの human step を挟んでから再開する。 散漫になることを防ぎ、各ターゲットに集中力を維持する。

Priority Matrix

ターゲット選択時の3軸評価:

軸 High Low
Impact Payment, PII, Admin access Info disclosure (non-sensitive)
Likelihood 新機能、複雑なロジック、legacy code 静的ページ、well-tested framework
Competition 新しい program、小さいスコープ 大手 program で大量の hunter が参加

理想的なターゲット: High Impact x High Likelihood x Low Competition。 新しく公開された program や、最近スコープが拡大された program が該当する。

Program Selection

Paid vs Unpaid

要素 Paid (Bounty) Unpaid (VDP)
報酬 金銭的報酬あり Reputation のみ
競争 激しい (dup リスク高) 比較的少ない
Response time 一般的に早い 遅いことが多い
初心者向き Signal 蓄積に有効 練習に最適

Large vs Small Scope

  • Large scope (*.target.com) — recon の余地が大きい、subdomain takeover を狙える、dup されにくい裏道がある
  • Small scope (app.target.com only) — deep dive が必要、logic bug に注力、競争が激しい

Program Precheck

調査開始前に確認すべきポイント:

  • Response time — 平均 triage 時間が長すぎる program は避ける
  • Bounty table — severity ごとの報酬額を確認
  • Past reports (disclosed) — どのレベルの bug が accept されているか
  • Program age — 新しい program は低hanging fruit が残っている
  • Anti-bot measures — automated recon が block されるか
  • Automation policy — 自動スキャンの許可/禁止
Anti-Bot Detection と即時 Pivot

Reddit, Shopify 等の大手は anti-bot で curl/automated recon を block する。 403 + 大きな response body が返ったら wall と判断し、5分以内に pivot する。 wall を突破しようとして時間を浪費しない。

Key Takeaways

  • OOS を最初に読む — 違反は ban、確認漏れは致命的
  • Time-box で散漫を防止 — 成果がなければ決断して pivot
  • Session budget は 2 pivot max — 3回目は撤退してリセット
  • Impact x Likelihood x Competition — 3軸で冷静に評価
  • 新 program は最高の機会 — 公開直後は低hanging fruit が豊富
  • Anti-bot wall は即 pivot — 突破に時間をかけない
