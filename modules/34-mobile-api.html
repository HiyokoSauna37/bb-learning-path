Mobile API Testing

モバイルアプリの通信を intercept し、Web UI には存在しない API endpoint や hardcoded secrets を発見する。

Theory Practice

なぜ Mobile API Testing が有効か

多くの企業は Web とモバイルで同じ backend API を共有するが、 モバイル固有の endpoint は Web frontend からは見えない。 これらの endpoint は往々にして認証・認可チェックが不十分。

  • Web UI には表示されない管理用 endpoint がモバイルアプリ経由でアクセス可能
  • モバイルアプリの binary にハードコードされた API key / secret
  • Certificate pinning を bypass すれば全通信が丸見え
  • 古いバージョンのアプリが古い(脆弱な) API を使い続けている

Traffic Interception (Proxy Setup)

Android

# 1. Burp の CA 証明書をエクスポート (DER形式)
# Burp → Proxy → Import/export CA certificate → Certificate in DER format

# 2. 証明書をシステムストアにインストール (Android 7+ は root 必要)
# 非root: ADB で user store に追加
adb push burp-cert.der /sdcard/
# Settings → Security → Install from storage

# 3. root 端末の場合: system store に直接配置
openssl x509 -inform DER -in burp-cert.der -out burp-cert.pem
hash=$(openssl x509 -inform PEM -subject_hash_old -in burp-cert.pem | head -1)
mv burp-cert.pem ${hash}.0
adb push ${hash}.0 /system/etc/security/cacerts/
adb shell chmod 644 /system/etc/security/cacerts/${hash}.0

# 4. WiFi proxy を Burp の IP:port に設定

iOS

# 1. Burp CA 証明書をブラウザからダウンロード
# http://burp (proxy経由でアクセス)

# 2. Settings → Profile Downloaded → Install
# 3. Settings → General → About → Certificate Trust Settings → Enable

# 4. WiFi 設定で HTTP Proxy を Manual に設定
# Server: Burp の IP, Port: 8080
Tips: Android Emulator

物理デバイスがない場合、Genymotion や Android Studio Emulator を使用。 Emulator なら root 権限が容易に取得でき、system CA 配置も簡単。 ただし一部アプリは emulator detection で動作しない。

Certificate Pinning Bypass

セキュアなアプリは特定の証明書のみを信頼する (pinning)。 これを bypass しないと proxy で通信を見ることができない。

Frida + objection

# objection: Frida ベースのランタイム操作ツール
# インストール
pip install objection

# アプリにアタッチして pinning を無効化
objection -g com.target.app explore
# objection シェル内で:
android sslpinning disable
ios sslpinning disable

# Frida スクリプトで手動 bypass
frida -U -f com.target.app -l ssl_pinning_bypass.js --no-pause

汎用的な Frida スクリプト

// Android SSL pinning bypass (Universal)
Java.perform(function() {
    var TrustManagerImpl = Java.use(
        'com.android.org.conscrypt.TrustManagerImpl');
    TrustManagerImpl.verifyChain.implementation = function() {
        return arguments[0]; // 全証明書を信頼
    };
});

// OkHttp CertificatePinner bypass
Java.perform(function() {
    var CertificatePinner = Java.use('okhttp3.CertificatePinner');
    CertificatePinner.check.overload('java.lang.String',
        'java.util.List').implementation = function() {
        // pinning チェックをスキップ
    };
});
注意: Root Detection

多くのアプリは root 検出も実装している。Frida で root detection bypass も 同時に必要になるケースが多い。Magisk の MagiskHide や Frida スクリプトで対応。

APK/IPA Reverse Engineering

Android (APK)

# jadx: APK → Java ソースコード (デコンパイル)
jadx -d output_dir/ target.apk

# apktool: リソース + smali 抽出
apktool d target.apk -o apk_extracted/

# jadx-gui: GUI でコードブラウジング
jadx-gui target.apk

# 探すべきもの:
grep -r "api_key\|secret\|password\|token" output_dir/
grep -r "https://\|http://" output_dir/ | grep -v "schema.org"
grep -r "firebase\|aws\|azure" output_dir/

iOS (IPA)

# IPA は実質 ZIP
unzip target.ipa -d extracted/

# class-dump (Objective-C)
class-dump extracted/Payload/App.app/App

# Hopper Disassembler / IDA Pro で解析
# Swift の場合は swift-demangle でシンボル復元

# strings で埋め込み文字列を抽出
strings extracted/Payload/App.app/App | grep -i "api\|key\|secret"

# Docker で MobSF を起動

Hardcoded Secrets in Mobile Apps

開発者がモバイルアプリにハードコードしがちな機密情報:

  • API keys — Google Maps, Firebase, AWS, Stripe
  • OAuth client secrets — client_id は公開だが client_secret はダメ
  • Firebase config — databaseURL, storageBucket が open rules だと致命的
  • Internal API endpoints — staging/dev 環境の URL
  • Encryption keys — ローカルストレージの暗号化キー
# nuclei mobile templates
nuclei -t mobile/ -target extracted_source/

# 手動検索パターン
grep -rn "AIza" .           # Google API Key
grep -rn "AKIA" .           # AWS Access Key
grep -rn "sk_live" .        # Stripe Secret Key
grep -rn "client_secret" .  # OAuth Secret
grep -rn "-----BEGIN" .     # Private Keys

Deep Link Abuse

Deep link (custom URL scheme / App Links) の実装ミスにより、 攻撃者のWebページから意図しないアプリ内動作を誘発できる。 

# AndroidManifest.xml から Deep Link スキーム抽出
grep -A5 "android.intent.action.VIEW" AndroidManifest.xml

# 典型的な脆弱パターン:
# target://callback?token=USER_TOKEN  → token leak via referer
# target://open?url=https://evil.com  → Open Redirect in app
# target://payment?amount=0.01        → 金額改ざん

# adb で Deep Link テスト
adb shell am start -a android.intent.action.VIEW \
  -d "target://callback?token=stolen"

# Safari で target:// を開く

Key Takeaways

  • Mobile は隠れた API の宝庫 — Web UI に存在しない endpoint が見つかる
  • Certificate pinning は bypass 可能 — Frida/objection で数分で突破
  • APK は難読化されていても読める — jadx で大部分のロジックが復元可能
  • Hardcoded secret は高確率で存在する — 特に Firebase, AWS key
  • Deep link は見落とされがち — Open Redirect, Token Leak の起点になる
  • 古いバージョンの APK を入手 — APKMirror 等で過去バージョンをダウンロードして比較
