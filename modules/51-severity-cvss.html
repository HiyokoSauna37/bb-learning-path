Severity Assessment & CVSS

CVSS スコアの正しい計算方法と、BB における severity 主張の戦略。 Over-claiming は信頼を失う。Under-claiming は bounty を減らす。正確さが最重要。

Theory Case Study

CVSS 3.1 Base Metrics

CVSS (Common Vulnerability Scoring System) は脆弱性の深刻度を数値化する標準。BB では Base Score のみ使用されることが多い。

Exploitability Metrics

Attack Vector (AV)

Network (N) / Adjacent (A) / Local (L) / Physical (P)

BB ではほぼ Network。Web アプリ = AV:N。ローカルファイル読み込みが必要 = AV:L。

Attack Complexity (AC)

Low (L) / High (H)

AC:L = 特殊条件なしで攻撃可能。AC:H = race condition、特定の設定が必要等。安易に AC:L を主張しない。

Privileges Required (PR)

None (N) / Low (L) / High (H)

PR:N = 認証不要。PR:L = 一般ユーザ。PR:H = admin。「無料登録可能」でも PR:L。

User Interaction (UI)

None (N) / Required (R)

UI:N = 被害者の操作不要。UI:R = リンクをクリックさせる必要あり（Reflected XSS 等）。

Impact Metrics

Scope (S)

Unchanged (U) / Changed (C)

S:C = 影響が脆弱コンポーネントの authority を超える（XSS from subdomain to main domain, sandbox escape 等）。判断が最も難しい指標。

Confidentiality (C)

None (N) / Low (L) / High (H)

H = 全データ漏洩可能。L = 一部データのみ。N = 情報漏洩なし。

Integrity (I)

None (N) / Low (L) / High (H)

H = 任意のデータ変更可能。L = 一部のみ変更可能。N = 改ざん不可。

Availability (A)

None (N) / Low (L) / High (H)

H = サービス完全停止可能。L = 一部機能の低下。DoS で安易に H を付けない。

CVSS 4.0 概要

2023年11月公開。3.1 からの主な変更点:

  • Attack Requirements (AT) が追加 — AC の細分化
  • Scope 廃止 — 代わりに Subsequent System Impact (VC/VI/VA + SC/SI/SA) で表現
  • Supplemental Metrics — Safety, Automatable, Recovery 等の付加情報
  • スコア計算が大幅に変更（同じ脆弱性でも 3.1 と異なるスコアになりうる）

現時点で HackerOne は 3.1 が主流。huntr/GHSA も 3.1。4.0 対応は platform 次第で移行中。

よくある間違い

Over-claiming

  • 「RCE の可能性がある」— 実証していないなら書かない
  • AC:L を安易に付ける — 特定設定が必要なら AC:H
  • S:C を安易に付ける — 同一 trust boundary 内なら S:U
  • C:H で「全データ漏洩」— 実際に取得できたデータ量で判断
  • Theoretical escalation で severity を上げる — 実証した範囲のみ

Under-claiming

  • IDOR で email のみ漏洩 → C:L だが、iteration で全件取得可能なら C:H
  • Admin panel access を PR:H にしがち → 一般ユーザから escalation できるなら PR:L

mei-bb Severity Rules

Rule: bb-cvss compute 必須

CVSS スコアの暗算は禁止。必ず bb-cvss compute ツールで計算する。暗算ミスで severity を間違えると信頼を失う。

Severity 3-Axis Gate

軸内容Cap
Verified実機で再現済み未検証 = Informative 以下
ChainAttack chain が物理的に成立Chain 不成立 = Low
Leak実際のデータ漏洩/変更を実証理論のみ = cap at Low

Speculation = cap at Low. 「could potentially」は severity claim の根拠にならない。

Precedent Citation

Severity 主張前に同プログラム・同 data class の prior advisory を bb-ghsa list で検索し、先例の severity を引用する。

  • 先例より高い severity を主張する場合、差分を明確に説明
  • 先例がない場合、類似プログラムの CVE を参考にする
  • Program-specific severity table がある場合はそれに従う（CVSS スコアより priority）

High/Critical を主張できる条件

Critical (9.0-10.0)

  • Pre-auth RCE (AV:N/AC:L/PR:N/UI:N)
  • Pre-auth full database access
  • Authentication bypass で admin takeover
  • いずれも 実機で完全に実証済み であること

High (7.0-8.9)

  • Auth bypass (non-admin scope)
  • IDOR with bulk data exfiltration
  • Stored XSS with session hijacking (実証済み)
  • SSRF with internal service access (実際のレスポンスを示す)

Conservative に判定すべきケース

  • 影響範囲が限定的（self-only XSS, informational leak）
  • Attack complexity が高い（race condition, 特定設定依存）
  • User interaction が必須（フィッシング前提）
  • Program の severity table で cap されている場合

CVSS 実例

Example 1: IDOR with email leak

GET /api/users/456/profile → returns {"email":"victim@example.com"}
Vector: AV:N/AC:L/PR:L/UI:N/S:U/C:L/I:N/A:N
Score: 4.3 (Medium)

理由: PR:L (認証必要), C:L (email のみ, 全データではない), I:N/A:N

Example 2: Pre-auth RCE via file upload

POST /upload → webshell execution → whoami returns "www-data"
Vector: AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
Score: 9.8 (Critical)

理由: PR:N (認証不要), 全 impact = H (任意コマンド実行)

Example 3: Stored XSS requiring click

Comment field → stored script → victim views page → cookie stolen
Vector: AV:N/AC:L/PR:L/UI:R/S:C/C:L/I:L/A:N
Score: 5.4 (Medium)

理由: UI:R (被害者がページを表示する必要), S:C (XSS は scope change)
