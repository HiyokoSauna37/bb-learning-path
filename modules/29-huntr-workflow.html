huntr Submission Workflow

huntr.com での OSS 脆弱性報告の全フロー。Target 選定から Report 作成、Triage、Bounty 受領まで。

Theory Case Study

huntr.com とは

  • OSS 特化の bug bounty プラットフォーム
  • GitHub リポジトリを直接対象として脆弱性を報告
  • 報告は maintainer + huntr triage team が review
  • Accepted されると CVE が発行され、bounty が支払われる
  • Bounty 金額: Critical $1,280 / High $512 / Medium $128 / Low $64 (目安)
huntr の特徴

Web アプリ BB (HackerOne/Bugcrowd) と異なり、ソースコードが完全公開されている。whitebox code review スキルが直結する。初心者が最初に取り組むべきプラットフォーム。

Target 選定

良いターゲットの条件

条件理由
Stars 1K-50Kactive maintenance + bounty 対象の可能性高い
Express/Flask/FastAPI ベースWeb 脆弱性の典型パターンが適用可能
最近のcommitActive project = triage が早い
Auth/API があるAuth bypass, IDOR, Injection の attack surface
dependency が多いsupply chain / vulnerable dep の可能性

Target 発見方法

  • GitHub Trending: 新規 popular project は audit が少ない
  • 既存 Advisory: GHSA がある project は incomplete fix variant の宝庫
  • huntr leaderboard: 他の hunter が報告した project を確認 (sibling あり)
  • Dependency-heavy projects: LLM ツール (LiteLLM, AnythingLLM, Flowise 等)
Phase 0.0: bb-target-precheck

Target 選定後、bb-target-precheck で huntr 登録状況・過去 advisory・dup zone を確認する。Phase 0.5 の OOS pre-audit も必須。

Submission フロー

1
脆弱性の発見と PoC 確認

コードレビューで sink を特定 → source からの到達確認 → Docker/local で PoC 確認。positive test + negative test の両方。

2
Dup Check

bb-ghsa list で既存 advisory 確認。GitHub Issues/PR も検索。同じ vulnerability が既に報告/修正されていないか。

3
Report 作成 (単一ファイル)

huntr 形式で Description / Impact / Occurrences を 1 ファイルに作成。

4
CVSS 計算

bb-cvss compute で正確に算出。暗算禁止。

5
Submit

URL: https://huntr.com/bounties/disclose (一般 form)。

6
Triage 待ち

通常 1-4 週間。maintainer + huntr team が review。追加質問が来る場合あり。

7
Accept / Reject / Duplicate

Accept → CVE 発行 → Bounty 支払い。Duplicate → Signal には影響なし。

Report Format (huntr)

huntr は単一ファイルでレポートを提出。フォームの各フィールドに対応するセクションを1ファイルに記述。

## Description

[脆弱性の技術的説明。何が起きているか、なぜ危険か。
コードの該当箇所を引用。ファイル名とLine番号を明記。]

## Proof of Concept

[再現手順。curl コマンドまたは Python script。
前提条件 (アカウント作成等) も含める。]

```bash
# Step 1: Create attacker account
curl -X POST http://localhost:3000/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"attacker","password":"pass123"}'

# Step 2: Exploit
curl -X GET http://localhost:3000/api/admin/users \
  -H "Authorization: Bearer $TOKEN"
```

## Impact

[CIA triad への影響。攻撃者が何をできるか。
影響を受けるユーザー/データの範囲。]

## Occurrences

[脆弱性が存在するファイルと行番号のリスト。
複数箇所ある場合は全て列挙。]

- https://github.com/owner/repo/blob/main/routes/admin.js#L42
- https://github.com/owner/repo/blob/main/routes/admin.js#L67
Report Quality Tips
  • PoC はコピペで再現できるレベルの具体性
  • impact は具体的なシナリオで示す (「全ユーザーのPIIが漏洩」等)
  • code reference は GitHub permalink (commit SHA 付き) を使用
  • severity claim に先例 (同 project の prior GHSA) を citation する

CVSS Scoring ガイダンス

Vector判断基準
Attack Vector (AV)Network (ほぼ全て Web)
Attack Complexity (AC)Low = 単純なHTTP request。High = race condition/timing依存
Privileges Required (PR)None = 無認証。Low = 通常ユーザー。High = admin
User Interaction (UI)None = 攻撃者単独。Required = 被害者のクリック等が必要
Scope (S)Changed = 別コンポーネントに影響 (SSRF→internal等)
CIA ImpactHigh = 全データ漏洩/変更/DoS。Low = 一部のみ
CVSS 計算は必ずツールで

bb-cvss compute を使用。暗算は誤りの元。severity claim に同 program の prior advisory を citation するとtriage が早い。

PoC 要件

  • 実 runtime で確認: Docker image (latest tag) or git clone + build で再現
  • Positive test: 脆弱性が刺さる (期待通りの exploit 結果)
  • Negative test: 正規のアクセスが制限される (auth が効いている箇所のデモ)
  • Minimal: 最小限の手順で再現。不要な手順は削除
  • Sink で actual exploit demo: raw forward 確認だけでは不十分。最終的な impact を示す
PoC なしの Report は Reject される

「コードを見ればわかる」は通用しない。必ず実行可能な PoC を添付すること。再現不可 = Reject。

よくある結果

  • Accepted: CVE 発行 + Bounty。Signal +7
  • Duplicate: 既に報告済み。Signal 計算から除外 (プラスもマイナスもなし)。HackerOne では Reputation に early +2 / late -5 の別計算あり
  • Informative: 脆弱性だが severity 不十分。Signal +2
  • Not Applicable: 脆弱性ではない。Signal -5

Submit 前の最終チェックリスト

  1. Dup check 完了? (bb-ghsa list + GitHub Issues/PR 検索)
  2. PoC が実 runtime で再現済み?
  3. Negative test 実施済み? (正規アクセスが制限されることの確認)
  4. CVSS を bb-cvss compute で計算済み?
  5. Report が huntr 形式 (1ファイル) で記述されている?
  6. Occurrences に GitHub permalink が含まれている?
  7. AI slop check 実施? (bb-aislop-gate scan)
  8. trust model / env fidelity 4軸 audit 完了?

Key Takeaways

  • huntr は OSS whitebox BB の入門に最適 — ソースコード完全公開、code review 直結
  • Target 選定: Stars 1K-50K + Express/Flask + recent commit + 既存 GHSA あり
  • Report は 1 ファイル: Description + PoC + Impact + Occurrences
  • PoC 必須: 実 runtime で positive + negative test
  • Submission URL: https://huntr.com/bounties/disclose
  • Dup check: advisory + PR + issues の 3 軸で確認
  • Incomplete fix variant が最も高 ROI の discovery method
