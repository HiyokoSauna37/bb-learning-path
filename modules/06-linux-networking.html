DNS (Domain Name System)

ドメイン名を IP アドレスに変換するシステム。BB では subdomain enumeration, DNS rebinding, subdomain takeover の基盤知識として必須。

DNS Resolution Flow

sequenceDiagram participant C as Your PC participant R as Recursive Resolver
(ISP/8.8.8.8) participant Root as Root Server participant TLD as .com TLD Server participant Auth as example.com
Authoritative C->>R: example.com の IP は? R->>Root: example.com は? Root->>R: .com は TLD Server に聞いて R->>TLD: example.com は? TLD->>R: example.com は Auth Server に聞いて R->>Auth: example.com の IP は? Auth->>R: 93.184.216.34 (TTL: 300s) R->>C: 93.184.216.34 Note over C,R: この結果は300秒キャッシュされる
→ DNS Rebinding はこのTTLを0にして
2回目の解決で別IPを返す 
# ユーザーが "app.example.com" にアクセス
1. Browser → OS Stub Resolver (hosts file, cache 確認)
2. Stub Resolver → Recursive Resolver (ISP/8.8.8.8/1.1.1.1)
3. Recursive Resolver → Root Name Server (. → .com の NS を返答)
4. Recursive Resolver → .com TLD Name Server (example.com の NS を返答)
5. Recursive Resolver → example.com Authoritative NS (app の A record を返答)
6. Recursive Resolver → Stub Resolver → Browser (IP address)

# TTL (Time To Live) でキャッシュ。TTL 0 = 毎回問い合わせ → DNS Rebinding に悪用

Subdomain Takeover

CNAME が指す先のサービスが削除されている場合、攻撃者がそのサービスを再登録して ドメインを乗っ取れる。 

# 発見方法
# 1. CNAME を確認
dig sub.target.com CNAME
# → sub.target.com CNAME target.herokuapp.com

# 2. CNAME 先にアクセス
curl https://sub.target.com
# → "There is no app configured at that hostname" (Heroku)
# → "NoSuchBucket" (S3)
# → "unknown domain" (Fastly)  ← 注: CNAME先ではなくvulnerable subdomain自体で確認

# 3. 攻撃者がサービスを登録して sub.target.com を制御

# 脆弱なサービスの signature
# Heroku: "There is no app configured at that hostname"
# AWS S3: "NoSuchBucket"
# GitHub Pages: "There isn't a GitHub Pages site here"
# Shopify: "Sorry, this shop is currently unavailable"
BB視点: Subdomain Takeover の注意点

(1) CNAME 先が unregistered なだけでは不十分。実際に claim できるか確認。
(2) Fastly の場合は CNAME 先 (*.fastly-edge.com) ではなく、vulnerable subdomain 自体に curl して "unknown domain" が返るかで判定する。
(3) 多くのプログラムで subdomain takeover は accepted だが、severity は Low-Medium が多い。

DNS Rebinding

SSRF フィルタをバイパスする高度なテクニック。DNS の応答を時間差で変更することで、 最初の検証時は外部 IP、実際のリクエスト時は内部 IP (127.0.0.1 等) を返す。 

# 攻撃フロー
1. 攻撃者が evil.com の DNS を制御
2. アプリに "http://evil.com/api" を fetch させる
3. アプリの SSRF フィルタ: evil.com を resolve → 1.2.3.4 (外部IP) → OK
4. DNS TTL = 0 なので即 cache expire
5. 実際の HTTP request: evil.com を再度 resolve → 127.0.0.1 (内部IP)
6. アプリは 127.0.0.1 にリクエストを送信 → 内部サービスにアクセス成功

# DNS Rebinding ツール
# - rbndr.us (テスト用サービス)
# - singularity (自前 DNS rebinding server)
# - 1u.ms (A.1u.ms は first query = A, second query = B を返す)

TCP/IP Basics

3-Way Handshake

# TCP 接続確立
Client → Server: SYN (seq=x)
Server → Client: SYN-ACK (seq=y, ack=x+1)
Client → Server: ACK (seq=x+1, ack=y+1)

# BB との関連: Race Condition
# 複数のリクエストを同時に到着させるには、TCP handshake を先に完了させてから
# 同時にデータを送信する (single-packet attack / last-byte sync)

Race Condition と TCP

PortSwigger の "single-packet attack" は、複数の HTTP request を1つの TCP パケットに 詰めることで、サーバー到着時刻の差をナノ秒レベルに縮める。 これにより race condition の exploitation が確実になる。 

# Burp Suite で Race Condition テスト
# Repeater → Group タブ → "Send group in parallel"
# 20-30 リクエストを同時送信して、状態変更の race を検出

# Python (requests + threading)
import threading
import requests

def send():
    requests.post('https://target.com/transfer',
                  json={'amount': 1000, 'to': 'attacker'},
                  cookies={'session': 'victim_session'})

threads = [threading.Thread(target=send) for _ in range(20)]
for t in threads: t.start()
for t in threads: t.join()

TLS/SSL

HTTP 通信の暗号化。証明書の検証、バージョン、cipher suite の設定が対象。

TLS Handshake の流れ

sequenceDiagram participant C as Client (Browser) participant S as Server C->>S: ClientHello (対応する暗号方式一覧) S->>C: ServerHello + 証明書 Note over C: 証明書を検証
(CA署名確認, 有効期限, ドメイン一致) C->>S: Pre-master secret (公開鍵で暗号化) Note over C,S: 両者が同じ session key を導出 C->>S: 暗号化通信開始 S->>C: 暗号化通信 Note over C,S: 以降の全HTTPは暗号化される
→ 中間者は内容を読めない
TLS 1.2 vs TLS 1.3

※ 上記は TLS 1.2 (RSA鍵交換) の例。TLS 1.3 では Ephemeral Diffie-Hellman のみを使用し、pre-master secret の暗号化送信は行わない。2026年現在、TLS 1.3 が主流。

Docker for PoC Environments

BB (特に OSS) では脆弱性の再現環境を Docker で構築して PoC を作成する。 安全に destructive テストを行うためにも必須。

基本コマンド

# イメージの取得と起動
docker pull vulnerable/app:latest
docker run -d -p 8080:80 --name target vulnerable/app

# コンテナ内でシェル
docker exec -it target /bin/bash

# docker-compose (複数サービス)
docker-compose up -d
docker-compose logs -f app
docker-compose down -v  # volume も削除

# PoC 用の典型パターン: アプリ + DB + attacker server
# docker-compose.yml
services:
  app:
    build: ./vulnerable-app
    ports: ["3000:3000"]
  db:
    image: postgres:15
  attacker:
    image: python:3.11-slim
    command: python -m http.server 9999
    ports: ["9999:9999"]
BB視点: Docker PoC の落とし穴

(1) production は外部 DB/Redis を使うが Docker は全てローカル → network 設定の差異に注意
(2) 環境変数のデフォルト値が debug mode → production との fidelity gap に注意
(3) volume の残骸が前回のテスト結果を汚染 → docker-compose down -v で毎回クリーン

Nmap

ネットワークスキャナ。BB ではターゲットの scope 内サービスの port discovery に使う。 ただし scope 外のスキャンは規約違反になるので注意。 

# 基本スキャン (top 1000 ports)
nmap -sV target.com

# 全ポートスキャン (時間がかかる)
nmap -p- target.com

# 特定ポートのバージョン検出
nmap -sV -p 80,443,8080,8443 target.com

# UDP スキャン (遅い)
nmap -sU --top-ports 20 target.com

# Script scan (脆弱性検出)
nmap --script=http-enum,http-headers -p 80,443 target.com

# BB で有用: 隠れた管理画面ポートの発見
# 8080, 8443, 9090, 3000, 4000, 5000, 6379(Redis), 27017(MongoDB)

Netcat

TCP/UDP の万能ツール。リバースシェル、ポートリスナー、バナーグラブに使用。 BB では主に PoC でのコールバック確認 (OOB interaction) に使う。 

# バナーグラブ (サービス特定)
nc -v target.com 80
HEAD / HTTP/1.1
Host: target.com

# リスナー (OOB callback 確認)
nc -lvnp 4444
# → SSRF/XXE/RCE の PoC で、ターゲットからのコールバックを受信

# ファイル転送
# 受信側
nc -lvnp 5555 > received_file
# 送信側
nc target.com 5555 < file_to_send

# ポートスキャン (簡易)
nc -zv target.com 20-100

Key Takeaways

  • DNS rebinding は SSRF IP-based filter の bypass に使える。TTL=0 の DNS を制御する。
  • Subdomain takeover は CNAME 先のサービス停止で発生。CNAME + error signature で判定。
  • Race condition: TCP single-packet attack (Burp "Send in parallel") で高精度にexploit。
  • SSRF bypass: IP 表記の変換 (hex/decimal/octal/IPv6 mapped) でフィルタを回避。
  • Cloud metadata (169.254.169.254) は SSRF の最重要ターゲット。credential 取得で Critical。
  • Docker は OSS BB の PoC 環境構築に必須。env var のデフォルトに注意。
  • nmap は scope 内限定。隠れた管理ポート (8080/8443/9090) の発見に有効。
