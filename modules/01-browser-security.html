Browser Security Model

ブラウザがどうやって「別サイトのデータを守っている」かを理解する。これが崩れると XSS, CSRF, CORS misconfig が刺さる。

Theory WSA Lab

Same-Origin Policy (SOP)

ブラウザの最も根本的なセキュリティモデル。同じ Origin (scheme + host + port) でないリソースへの読み取りを禁止する。

Origin の定義

URLOrigin同一?
https://app.example.com/page1https://app.example.com:443基準
https://app.example.com/page2https://app.example.com:443同一 (path は無関係)
http://app.example.com/page1http://app.example.com:80別 (scheme 違い)
https://api.example.com/page1https://api.example.com:443別 (host 違い)
https://app.example.com:8080/https://app.example.com:8080別 (port 違い)

SOP が許可/禁止するもの

操作Cross-Origin理由
iframe 埋め込み許可 (表示のみ)広告、埋め込みコンテンツ
iframe 内容の読み取り禁止データ漏洩防止
<img>, <script>, <link> 読み込み許可CDN、外部リソース
fetch/XHR の response body 読み取り禁止 (CORS なし時)データ漏洩防止
fetch/XHR の request 送信許可 (Simple Request)→ CSRF の原因
Cookie の送信条件付き (SameSite)認証の自動付与

SOPの動作イメージ

flowchart TD subgraph same["Same Origin (https://app.example.com)"] A[Page A] -->|"読み書き OK"| B[Page B] end subgraph cross["Cross Origin (https://evil.com)"] C[Evil Page] end C -->|"Response 読み取り禁止"| A C -->|"Request 送信は可能!"| A Note["送信できる = CSRF の原因"]
BB視点: SOP の「��」

SOP は response の読み取りを禁止 するが、request の送信は止められない。 この非対称性が CSRF の根本原因。また、CORS で SOP を緩和しすぎると cross-origin data leak が成立する。

CORS (Cross-Origin Resource Sharing)

SOP を「安全に」緩和する仕組み。サーバーが「このOriginからの読み取りは許可する」と明示する。

Simple Request vs Preflight

条件Simple RequestPreflight (OPTIONS) 必要
MethodGET, HEAD, POST のみPUT, DELETE, PATCH 等
HeadersAccept, Content-Type (form系のみ) 等Authorization, X-Custom-* 等
Content-Typeform-urlencoded, multipart, text/plainapplication/json 等

危険な CORS 設定パターン

Pattern 1: Origin Reflection

Access-Control-Allow-Origin: [攻撃者のOriginをそのまま反射]
Access-Control-Allow-Credentials: true

サーバーが Origin header の値をそのまま ACAO に返す。 credentials: true と組み合わさると、攻撃者サイトから被害者の認証済みデータを読み取れる。

Pattern 2: null Origin 許可

Access-Control-Allow-Origin: null
Access-Control-Allow-Credentials: true

Origin: null は sandboxed iframe (<iframe sandbox="allow-scripts">) から発生する。 攻撃者が sandbox iframe 経由でリクエストを送ると CORS チェックをパスできる。

Pattern 3: サブドメイン trust

// サーバー側の検証ロジック (脆弱)
if (origin.endsWith('.example.com')) {
    res.setHeader('ACAO', origin);
}

evil-example.com は .example.com で終わるので通る。 正しくは origin === 'https://app.example.com' のように完全一致で検証する。

mei-bb 実体験: CORS ≠ 自動的に脆弱

CORS が wide-open でも、認証が Bearer token (header-only) で Cookie を使わない場合は credentials: include しても意味がない（Cookie が自動送信されないため）。
BB で CORS を報告する前に「認証方式は Cookie ベースか?」を必ず確認すること。 (参照: feedback_bb_cors_audit_sop / Tapple F1 false-positive 撤回)

Cookie Attributes

属性効果不在時のリスク
HttpOnly JavaScript からの読み取りを禁止 XSS で document.cookie 経由のセッション窃取
Secure HTTPS 接続でのみ送信 HTTP ダウングレードでの盗聴
SameSite=Strict Cross-site request では一切送信しない —（最も安全）
SameSite=Lax Top-level navigation の GET のみ送信 POST CSRF は防げるが、GET ベースの state-changing 操作は守れない
SameSite=None Cross-site でも送信 (Secure 必須) CSRF 可能 (別途 CSRF token が必要)
Domain=.example.com 全サブドメインに送信 サブドメインの XSS で parent domain の Cookie 奪取
Path=/admin 指定パス以下でのみ送信 iframe で迂回可能 — セキュリティ目的には使えない

BB視点: SameSite の現状

Chrome 80 以降、SameSite 未指定時は Lax がデフォルト。 つまり「SameSite 属性がない = CSRF 可能」は古い知識。 現代の CSRF は SameSite bypass テクニック (method override, open redirect chain, cookie tossing) が必要。

Content Security Policy (CSP)

CSP の仕組み

サーバーが Content-Security-Policy header で「このページで実行を許可するリソースの出所」を宣言する。 XSS でスクリプトを注入しても、CSP が許可していない source からの実行はブラウザがブロックする。

主要な Directive

Directive制御対象例
default-src全リソースのフォールバック'self'
script-srcJavaScript'self' 'nonce-abc123'
style-srcCSS'self' 'unsafe-inline'
img-src画像* data:
connect-srcfetch/XHR/WebSocket'self' https://api.example.com
frame-ancestorsこの page を iframe で埋め込める親'none' (Clickjacking 防止)
base-uri<base> タグの href'self'

CSP Bypass テクニック (概要)

  • 'unsafe-inline' がある → 通常の XSS payload が動く
  • 'unsafe-eval' がある → eval(), setTimeout('code') が使える
  • Whitelisted domain に JSONP endpoint → <script src="trusted.com/jsonp?callback=alert(1)">
  • base-uri 未指定 → <base href="https://evil.com/"> で相対パスのスクリプト読み込みをハイジャック
  • Nonce reuse / Nonce leak → nonce が固定値 or response に漏れている

Referrer Policy

Referrer-Policy header がブラウザの Referer 送信動作を制御する。 URL に token が含まれる場合 (?token=secret)、 Referrer-Policy: no-referrer でないと外部リンクから token が漏洩する。

PolicyCross-origin で送る情報
no-referrer何も送らない
originOrigin のみ (path なし)
strict-origin-when-cross-origin同一origin = full URL, cross-origin = origin のみ (デフォルト)
unsafe-url常に full URL — 危険

Key Takeaways

  • SOP は「読み取り禁止」であって「送信禁止」ではない → CSRF の根本原因
  • CORS misconfig は「認証方式が Cookie ベース」かつ「credentials: true」のときだけ実質的な脅威
  • SameSite=Lax がデフォルト → 現代の CSRF は bypass テクニックが必須
  • CSP は万能ではない → unsafe-inline, JSONP whitelisted domain, base-uri 未指定 で bypass 可能
  • Cookie の Domain 属性 → サブドメイン XSS で全ドメインの session を奪える
