1. origin・site・Cookieは何を分けるか

アプリが https://app.example.test、アップロード先が https://files.example.test にあるとする。ファイル側でスクリプトが動いたとき、主アプリのデータに届くかを説明するには、URLとCookieを別々に読む必要がある。

2つのURLoriginschemeも考慮するsite
https://app.example.test/a
https://app.example.test/b		同じ。pathはoriginに含まれない。同じ。
https://app.example.test
https://files.example.test		hostが異なる。同じ。登録可能なドメインとschemeが共通。
https://app.example.test
https://app.example.test:8443		portが異なる。同じ。siteの判定にportは含まれない。
https://app.example.test
http://app.example.test		schemeが異なる。schemeを含める判定では異なる。

Originは通常scheme・host・portの組で、SOPによるDOMや応答の読取に関係する。SiteはCookieのSameSite等に使う区分で、登録可能なドメインとschemeが関係する。co.jp のような公開サフィックスもあるため、文字列を末尾から2語取るだけでsiteを求めることはできない。

CookieはDomain、Path、Secure、SameSite等で送信条件が決まる。Domainを省略したCookieは設定元hostに限定され、Domain属性を指定した場合は条件の合うサブドメインにも送られる。Cookieにはportを限定する属性がない。同じsiteであっても、別originのDOMを直接読む権限まで得るわけではない。

iframe内で動いた証拠をどう評価する？

<iframe sandbox="allow-scripts" srcdoc="..."></iframe>

このフレームはスクリプト実行を許し、allow-same-origin を付けていないのでopaque originとして扱われる。opaque originは通常のscheme・host・portで表せないoriginで、postMessageで届く event.origin は文字列 "null" になる。主アプリの画面と同じタブ内に見えることから、主アプリと同じ権限で実行したとは結論付けられない。

観察ではDevToolsの実行対象フレームを確認し、URL、sandbox属性、受信したメッセージのorigin、親DOMへのアクセス結果を組にする。about:srcdoc のような特殊URLは、表示URLだけから文書の実効originを決め付けない。ファイルを直接開く file: のoriginの扱いにもブラウザー差がある。

2. HTMLとJavaScriptが重なる場所を読む

次のボタンでは、HTML属性の中にJavaScriptがあり、その中に文字列がある。USER_INPUT に、引用符を含む氏名が入った場合を予想しよう。

<button onclick="showName('USER_INPUT')">名前を表示</button>
  1. HTMLパーサーがダブルクォートで囲まれた属性を読み、属性値の実体参照を解釈する。
  2. ボタンを操作したとき、イベントハンドラーのJavaScriptが実行される。
  3. JavaScriptはシングルクォートで囲まれた文字列の構文を解釈する。

HTML属性の境界を守るエンコードをしても、デコード後の引用符がJavaScript文字列の境界に関係する。逆に、JS用のエスケープだけでは、その外側のHTML属性の構文まで保証できない。レビューでは「何回エンコードしたか」に加え、各段階の文字列と、次に読む文法を記録する。

値の受け渡しをコードから外す

// ボタンと表示先はアプリが固定した要素
const button = document.querySelector('#show-name');
const output = document.querySelector('#name');
const personName = user.displayName;

button.addEventListener('click', () => {
    output.textContent = personName;
});

この実装では関数を登録し、名前は既存の変数として扱う。showName('...') というコード文字列を入力から生成する箇所が消える。修正後は、引用符、改行、日本語を含む氏名が原文どおり表示されることを確認する。

URLとHTML属性も2段階になる

<a href="/search?q=USER_INPUT"> のようにURL部品を埋める場合、まずクエリ値として表現し、そのURLをHTML属性へ埋める文脈も守る。DOM APIを使える場合は固定したURLを作り、searchParams.set() で値を設定し、固定したa要素のhrefへ渡す。

const link = document.querySelector('#search-link');
const url = new URL('/search', location.origin);
url.searchParams.set('q', userInput);
link.href = url.href;
link.textContent = 'この語で検索';

この例はアプリ内の検索リンクを作る仕様。入力としてURL全体を受け付ける仕様では、許可するschemeとoriginの検査が別に必要になる。

3. SSRの初期JSONは、誰が先に読むか

SSRでは初期表示用のデータをHTMLへ埋め、ブラウザー側でJSONとして読むことがある。次の文書を見て、JSONを読む前にHTMLの構造がどう作られるか予想しよう。

<script id="boot" type="application/json">
{"note":"</script><p id=proof>校正用</p>"}
</script>

ブラウザーはまずHTMLを解析する。script要素の内部では、JSONの文字列に入っているつもりの </script> もHTMLの終端として働く。このためデータブロックが途中で閉じ、p要素が外側に生成される。その後のJSON.parseでは、不完全になったJSONがエラーになる。

type="application/json" はその内容をJavaScriptとして実行する指定ではないが、HTMLパーサーの終端の扱いは考慮する必要がある。JSON.stringify() はJSONとしての引用符や改行を処理するため、HTMLへ埋める条件も扱うシリアライザーが必要になる。

埋込み時の文字列と、読み戻した値を比べる

// サーバーでHTML埋込み用のJSON文字列を作る例
// まずJSONとしてシリアライズし、その結果に残る < を表現し直す
const serialized = JSON.stringify(order).replaceAll('<', '\\u003c');

// HTMLには次のようなJSON文字列が入る
// {"note":"\u003c/script>\u003cp id=proof>校正用\u003c/p>"}

HTML中にscript終端を始める山括弧が残らなくなり、JSON.parseで読み戻すと元の文字に復元される。テンプレートへ渡すときは、フレームワークが用意するHTML埋込み用JSON機能を優先し、戻り値を何に挿入する設計かまで確認する。これはJSONのデータブロック向けの話で、イベント属性やJSのテンプレートソースへ流用する設計は別にレビューする。

独立した application/json のAPI応答から取得する構成も選べる。その場合も、復元したnoteを表示するsinkで適切に扱う。エンコードが保たれたかと、文字としての原文が保たれたかを両方テストする。

4. CSPを具体的なポリシーから読む

以下は読解用の例。実運用ではnonceを応答ごとに予測困難な値として生成し、ヘッダーと許可するscriptのnonce属性に同じ値を設定する。

Content-Security-Policy:
  default-src 'none';
  script-src 'nonce-EXAMPLE_RANDOM_VALUE' 'strict-dynamic';
  script-src-attr 'none';
  img-src 'self';
  connect-src 'self';
  style-src 'self';
  base-uri 'none';
  object-src 'none'

<script nonce="EXAMPLE_RANDOM_VALUE" src="/app.js"></script>

ヘッダーの改行は説明用。次の表は、この強制ポリシーを対応ブラウザーが受け取り、別のCSPを併用していない条件で読む。

処理この例での判断根拠
一致するnonceを持つapp.js読み込みと実行を許可する。script-srcのnonceに一致する。
パーサーが読むHTMLに埋め込まれたnonceのないscriptそのscriptの実行を拒否する。許可するnonceやhashを持たない。
onclick等のイベント属性実行を拒否する。script-src-attr 'none' が対象。要素にnonce属性を付けてもイベント属性の許可にはならない。
許可されたapp.jsがscript要素を作って追加strict-dynamicで信頼が伝わり得る。信頼されたscriptによる動的な読込。そこで使うURLが外部入力に左右されるかも調査する。
文字列を渡すevalやFunction実行を拒否する。この例には文字列評価を許可するunsafe-eval等がない。
他originへのfetchconnect-srcの制限で拒否する。同じoriginへの接続だけを許可している。

directiveが省略されていたら

イベント属性には script-src-attr、script要素には script-src-elem が使われる。各directiveがない場合は script-src、それもなければ default-src にフォールバックする。個別directiveに明示した制限と、フォールバック先の制限を単純に合算する読み方はできない。

上の例で script-src-attr 'none' を消しても、フォールバック先のscript-srcが通常のイベント属性を許可する条件を持たないため、そのイベントは実行されない。実際の診断では、対応ブラウザー、違反ログに出るdirective、配信されたヘッダーを照合する。

Report-Onlyと複数ポリシー

同じ内容を Content-Security-Policy-Report-Only で配信した場合は、そのポリシーの違反を理由に処理を遮断しない。一方、強制ポリシーを複数配信した場合は、それぞれの制約を満たす必要がある。Report-Onlyの通知と、強制ポリシーによるブロックのどちらを見ているかを切り分ける。Report-Onlyはmeta要素での指定に対応しないので、HTTPレスポンスヘッダーで検証する。

MDN script-src ／ MDN script-src-attr ／ MDN script-src-elem ／ MDN Report-Only

5. DOM clobberingは既存コードの参照先を追う

HTMLのidやnameから、WindowやDocumentに名前付きの参照が作られる場合がある。たとえば、次の要素が存在し、同じ名前のアプリ設定がまだ定義されていない場面を考える。

<a id="nextPage" href="/review">確認へ</a>

<script>
  const destination = window.nextPage || '/home';
  console.log(typeof destination, String(destination));
</script>

この条件では window.nextPage がa要素を指し、その要素を文字列に変換すると解決済みのhrefが得られる。コードが期待した「アプリが決めた文字列」と、実際に読んだ値の型がずれる。自分でHTMLを追加しても、該当する名前を使う既存コードがなければ、この経路は成立しない。

さらにその値を遷移先やscriptの読込先に使うコードがあれば、どこまで入力が影響するかを調べる。HTMLの追加、名前付き参照への影響、参照後の使い方を順に記録する。重複したidやform要素の参照では戻る値の形が変わることもあるため、実ブラウザーで型とプロパティを確認する。

設定をアプリの変数として管理する

// 外部から生成した要素名を設定の参照に使わない構成
const settings = Object.freeze({
    nextPath: '/review'
});
const destination = new URL(settings.nextPath, location.origin);

この変数はコードが持つ設定を参照する。HTMLを受け付ける仕様なら、サニタイザーでid・nameをどこまで許すかも見直す。DOMPurifyには、カスタム名を含む名前付きプロパティの衝突を抑える SANITIZE_NAMED_PROPS 設定がある。設定追加後は、本文内リンクやラベル参照など、idに依存していた正常機能も再テストする。

OWASP DOM Clobbering Prevention ／ PortSwigger DOM clobbering

6. Markdownやリンク化のURLポリシーを作る

コメントのMarkdownからリンクを作る場合、表示ラベル、URL全体、生成したHTML属性にそれぞれの要件がある。たとえば「相対URLとアプリ内のHTTPS URLを許し、ユーザー名・パスワードを含むURLは拒否する」と仕様を決める。

入力固定した基準URLからの解析この仕様での扱い
/docs?q=teaapp.example.test内のURL。許可する。
//files.example.test/docschemeを基準URLから受け継ぎ、hostはfiles.example.testになる。許可originと一致しないので拒否する。
https://app.example.test@other.test/dochostはother.test、app.example.testはusername。originと資格情報の条件で拒否する。
https://app.example.test:8443/doc既定portのアプリとは別origin。許可originと一致しないので拒否する。

解析した結果に仕様を適用する

function allowedCommentURL(raw) {
    const appOrigin = 'https://app.example.test';
    let url;
    try {
        url = new URL(raw, appOrigin + '/');
    } catch {
        return null;
    }
    if (url.protocol !== 'https:' || url.origin !== appOrigin) {
        return null;
    }
    if (url.username || url.password) {
        return null;
    }
    return url;
}

const url = allowedCommentURL(markdownLink.destination);
if (url) {
    const link = document.createElement('a');
    link.href = url.href;
    link.textContent = markdownLink.label;
    output.append(link);
}

基準URLをアプリが固定しているので、ページにあるbase要素や、コメント内の文字列で基準を変更されない。実装時には appOrigin を配信環境に合う設定へ置き換える。外部HTTPSリンクも許す仕様なら、許可originの条件をその仕様に合わせて設計する。

MarkdownライブラリのURL検査、生成したHTMLを処理するサニタイザー、クリック時にリンクを加工するコードまで追う。外部リンクを拒否する判定が、後段で別のURLへ置換されていないか確認する。表示ラベルをtextContentに入れると、ラベルに含むタグは文字として表示される。

MDN URLコンストラクター ／ MDN URLの各プロパティ ／ OWASP URL文脈

7. Shadow DOMとSPAは、描画経路を分けて調べる

カスタム要素のレビュー画面で、目印が document.querySelector() に見つからないとする。Shadow DOMはコンポーネント内の木を分ける仕組みなので、通常のdocumentのセレクターはその境界を越えて検索しない。Elementsでカスタム要素を開き、shadow rootやslotを確認する。

// openモードのshadow rootをアプリが作る例
const host = document.querySelector('review-card');
const root = host.attachShadow({ mode: 'open' });
const note = document.createElement('p');
note.textContent = userNote;
root.append(note);

同じoriginのコードから host.shadowRoot を参照できる。この中でもinnerHTML等を使えば値をHTMLとして解釈する。closedモードも同一origin内のカプセル化として扱う。コンポーネントの描画関数と受け取る値をレビューする。

操作確認する処理残す証拠
URLを直接開いて初期表示SSRのHTML、初期データ、hydration。最初のHTTP応答と、操作前のDOM。
一覧から詳細へ内部遷移ルーター、API取得、コンポーネントの描画。取得APIと挿入時のcall stack。
編集してプレビューへ切替ローカルのMarkdown変換や一時データ。保存前の値と、プレビューのDOM。
再読み込み・戻る・キャッシュから復元保存値、状態復元、キャッシュ済みHTML。値の復元元と、再び表示する処理。

同じ画面名でも、初期表示と内部遷移で異なるコードを通る場合がある。修正後は、問題が起きた遷移手順とURL直接表示を両方試し、入力の原文と許可した装飾が保たれるかを確認する。

8. 修正案をレビューする4問

解答を開く前に、仕様を満たす表示と、削除できた解釈段階を言葉にしよう。実装者が直した行だけでなく、値が届く経路も確認する。

① イベント属性の引用符をHTMLエンコードした

onclick="showName('USER_INPUT')" の入力をHTML属性用にエンコードした。属性を壊せなくなったので修正完了と判断した。追加で何を確認し、どう設計し直す？

解答と照合する

HTML解析後の属性値を、さらにJavaScriptが読む。イベント属性に残ったコードと、文字列の引用符を確認する。固定したaddEventListenerの関数へ値を変数として渡す構成にすれば、外部入力からコード文字列を作る段階を除ける。引用符を含む正常な名前も表示できるか再テストする。

② JSON.stringifyの結果をscript要素へ入れた

開発者は「JSONとして有効なら安全」と考えた。サーバーが作ったHTMLの初期データに </script> を含む文字列が届く。どのパーサーが先に動く？

解答と照合する

先にHTMLが解析され、文字列中のscript終端でも要素が閉じる場合がある。HTML埋込み用のJSONシリアライザーを使い、最初の文書のDOMと読み戻した値を確認する。独立したJSON応答を選ぶ方法もある。どちらでも、値を最終表示するsinkは別に検証する。

③ URLを正規表現で検査してからリンクにした

許可条件は「アプリ内のHTTPSリンク」。コードはURL文字列に app.example.test が含まれることを確認している。userinfo、port、相対URLを含む入力の期待結果をどう定める？

解答と照合する

固定した基準URLから解析し、protocolとoriginを仕様どおりに比較する。資格情報を持つURLを拒否し、相対URLを許すかを明示する。文字列中のアプリ名がhostを表すとは限らない。ラベルの表示もtextContent等で保護し、リンク作成後のURLプロパティを検証する。

④ CSPでイベント属性がブロックされた

入力の挿入先は引き続きinnerHTMLで、強制CSPがインラインハンドラーを拒否する。Report-Onlyへ移行したらどうなるか、修正が仕様を満たすかをどう確認する？

解答と照合する

Report-Only単体は同じポリシー違反を遮断しないため、HTML解釈先に残る実行可能な構造を再評価する。文字表示ならtextContent、装飾が必要なら許可したHTMLのサニタイズを適用する。最終DOM、通常の表示、実際に強制したポリシーをそれぞれ確認する。
