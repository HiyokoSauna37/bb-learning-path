Report Writing Mastery

再現性のある、事実に基づいた報告書の書き方。 Platform ごとのフォーマット差異を理解し、Triage 担当者に一発で伝わるレポートを書く。

Theory Hands-on

レポートの基本構造

どの platform でも共通するレポートの骨格。Triage 担当者は1日に数十件のレポートを読む。最初の3行で伝わらなければ後回しにされる。

Standard Structure

  1. Title — 脆弱性の種類 + 影響箇所を1行で（例: IDOR in /api/users/{id}/settings allows reading other users' email）
  2. Summary — 3行以内で What / Where / Impact を説明
  3. Impact — 実際に何ができるか。理論ではなく実証されたダメージ
  4. Steps to Reproduce — 番号付きの手順。環境情報を含む
  5. PoC — 最小限の再現コード/スクリーンショット/動画
  6. Fix Recommendation — 修正案（任意だが好印象）

Title の書き方

フォーマット: [Vuln Type] in [Component/Endpoint] allows [Actor] to [Action]

Good: Stored XSS in /api/comments via markdown image alt text allows session hijacking
Bad: XSS vulnerability found（どこで何が起きるか不明）

Platform 別フォーマット

HackerOne

Markdown 形式。Weakness (CWE) を選択、Asset を指定。Severity は自己申告 + CVSS calculator。Impact section を重視する文化。

## Summary
[1-2 sentences]

## Steps to Reproduce
1. Navigate to ...
2. Intercept request with ...
3. Modify parameter X to ...

## Impact
An attacker can ... resulting in ...

## Supporting Material
- [screenshot1.png]
- [poc.py]

Intigriti

フォーム入力 + Markdown body。AI使用の開示が必須（CoC 2026-03 更新）。Submission limits あり。

## Description
[What + Where + How]

## Proof of Concept
[Steps + Evidence]

## Impact
[Concrete damage]

## AI Disclosure
This report was prepared with assistance from [tool name].
AI was used for: [specific tasks, e.g., code analysis, PoC validation]

huntr (OSS)

重要: 1ファイルで完結。Description + Impact + Occurrences を split しない。/bounties/disclose のフォームに直接 paste する。

## Description
[Vulnerability explanation + root cause in code]

## Impact
[What an attacker can achieve]

## Occurrences
- https://github.com/org/repo/blob/main/src/file.py#L42-L55
- https://github.com/org/repo/blob/main/src/other.py#L100

GHSA (GitHub Security Advisory)

Private vulnerability reporting。Bounty はないが portfolio 構築に有効。CVE 自動採番可能。

## Summary
[Brief description]

## Details
[Technical root cause analysis with code references]

## PoC
[Minimal reproduction steps]

## Impact
[CIA impact + affected versions]

Good vs Bad Report

Clarity（明確さ）

Good: "The endpoint GET /api/v2/users/:id does not verify that the authenticated user owns the resource. By changing the id parameter from 123 (own) to 456 (victim), the full profile including email and phone is returned."
Bad: "I found that the API might be leaking user data. It seems like authorization is not properly implemented."

Reproducibility（再現性）

Good: curl コマンド、HTTP request/response の完全なログ、環境情報 (OS, version, config)
Bad: "I tested this in my browser and it worked"（再現不能）

No Speculation（推測禁止）

Good: "I verified that User B's email b@example.com is returned in the response body (see screenshot)."
Bad: "This could potentially lead to account takeover if combined with other vulnerabilities."（実証なし）

Impact の示し方

Impact は「理論上可能」ではなく「実際にやってみせた」で示す。

原則

  • Show, don't tell — "could allow" ではなく "I was able to"
  • Actual damage — 実際に取得したデータ、変更できた設定を見せる
  • Worst-case は実証した範囲内で — 実証していない escalation path は "potential" と明記
  • 他ユーザへの実害なし — 自分の test account 間でのみ実証

PoC ガイドライン

  • 最小限のコードで再現可能にする（依存ライブラリを減らす）
  • Safe: 他ユーザのデータを実際に読み取らない（自分のテストアカウント同士で）
  • Reproducible: 環境依存を明記（OS, Python version, 必要な config）
  • Cleanup: PoC 実行後の後片付け手順も含める

言語・文体

  • レポートは英語で書く（日本語 platform 以外）
  • 簡潔・事実的 (concise & factual)。文学的表現は不要
  • 受動態より能動態: "The server returns..." not "It was observed that..."
  • 1文1事実。複合文を避ける
  • Technical term は正確に（XSS, SSRF, IDOR 等を正しく使い分ける）

Submit 前チェックリスト

  • Title は vuln type + location + impact を含むか
  • Steps to Reproduce は初見の人が再現できるか
  • PoC は minimal & safe か
  • Impact は実証済みか（推測で severity を盛っていないか）
  • Scope 内のアセットか
  • huntr の場合: 1ファイルに収まっているか
  • Intigriti の場合: AI disclosure が含まれるか
