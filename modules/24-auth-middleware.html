Auth Middleware Patterns & Bypass

認証 Middleware の bypass パターンを体系化。Whitelist bypass, Route precedence, Path normalization 差異を中心に、実発見事例を交えて解説。

Theory Case Study Hands-on
なぜこのモジュールが重要か: huntr で最も多い finding class

Auth middleware bypass は huntr.com で最も報告数が多い脆弱性カテゴリ。 Flowise の WHITELIST_URLS パターンだけで 6件以上の finding が出た。 このモジュールを1つマスターすれば、ほぼ全ての Express / Go 製 Web アプリで再現可能な調査手法を手に入れられる。

Whitelist/Allowlist Bypass

認証 middleware (=リクエストが route handler に届く前にログイン済みか確認する処理) が 特定の path を skip する「ホワイトリスト」方式は、最も頻出する bypass ベクトル。

Pattern 1: Prefix Match の罠

// 危険: startsWith による prefix match
const WHITELIST = ['/api/v1/public', '/api/v1/verify', '/api/v1/health'];

function authMiddleware(req, res, next) {
    if (WHITELIST.some(url => req.path.startsWith(url))) {
        return next(); // auth skip!
    }
    // verify token...
}

// Bypass 1: /api/v1/public/../admin (path traversal)
// Bypass 2: /api/v1/publicXXX (prefix match で新 endpoint が意図せず skip)
// Bypass 3: /api/v1/public%2F..%2Fadmin (URL encoding)

Pattern 2: Exact Match の抜け

// route は /api/users/:id だが whitelist は /api/users
const WHITELIST = ['/api/users'];

// /api/users → skip (exact match)
// /api/users/123 → match しない → auth required
// /api/users/ → trailing slash で挙動が変わる？

Pattern 3: Regex の不備

// 危険: anchor なし regex
const skipAuth = /\/public\//;
// /evil/public/../../admin → match → auth skip

// 危険: . のエスケープ忘れ
const skipAuth = /\/api\/v1\/health.check/;
// /api/v1/healthXcheck → match

Route Precedence Issues

Router の route 登録順序や specificity ルールによって、意図しない handler が呼ばれる問題。

Express の場合

// Express は登録順に match (first match wins)
router.get('/api/:resource', publicHandler);     // 先に match
router.get('/api/admin', authMiddleware, admin); // 到達しない!

// 正しい順序: specific route を先に登録
router.get('/api/admin', authMiddleware, admin);
router.get('/api/:resource', publicHandler);

Go ServeMux の場合

// Go 1.22+ ServeMux: longer pattern wins (most specific)
mux.HandleFunc("/api/", publicHandler)      // /api/* に match
mux.HandleFunc("/api/admin", adminHandler)  // /api/admin に match (longer)

// 注意: trailing slash の有無
mux.HandleFunc("/api/admin", handler)  // exact match only
mux.HandleFunc("/api/admin/", handler) // subtree match (/api/admin/xxx)

Missing Middleware on Specific Routes

最も単純だが最も頻出する問題: 特定の route に auth middleware を付け忘れている。

// ファイル: routes/tasks.js
router.get('/tasks', authMiddleware, listTasks);
router.post('/tasks', authMiddleware, createTask);
router.get('/tasks/:id', authMiddleware, getTask);
router.put('/tasks/:id', authMiddleware, updateTask);
router.delete('/tasks/:id', deleteTask);  // authMiddleware 忘れ!

// 発見方法: 同一 router で middleware 有無を比較
// grep "router\.\(get\|post\|put\|delete\)" | grep -v "authMiddleware"

Method-Specific Gaps

// PUT/PATCH には auth があるが OPTIONS/HEAD にはない
app.put('/api/config', authMiddleware, updateConfig);
app.options('/api/config', corsHandler);  // auth なし → preflight 以外でも呼べる?

// HEAD method で情報漏洩
app.get('/api/secret', authMiddleware, getSecret);
// HEAD /api/secret → Express は GET handler を使うが、middleware chain は?

Path Normalization Differences

Router と Middleware で path 解釈が異なる場合、bypass が生まれる。

TechniqueMiddleware seesRouter seesResult
/api/admin/../public/api/admin/../public/api/public (resolved)Auth applied to wrong path
/api/admin%2F/api/admin/ (decoded)/api/admin%2F (raw)Route mismatch
//api/admin//api/admin/api/admin (normalized)Whitelist skip
/API/ADMIN/API/ADMIN (case sensitive)/api/admin (case insensitive)Bypass on case-insensitive routers
Normalization 差異の見つけ方

Middleware が req.path を見ているか req.url を見ているか、Router が pattern match する際に normalize するかどうか、この2点の差を探す。

Detection Tools

bb-middleware-audit

# Go/Express middleware の適用漏れを機械的に検出
bb-middleware-audit scan --pattern="authMiddleware" --missing
bb-middleware-audit scan --pattern="requireAuth" --router=routes/

# Output: middleware が適用されていない route 一覧

bb-whitelist-audit

# WHITELIST_URLS pattern の sibling endpoint を検出
bb-whitelist-audit scan --target=./src
# Whitelist に含まれる path の兄弟 endpoint で
# 認証が必要なのに whitelist に含まれてしまうものを検出

手動 grep アプローチ

# Step 1: Auth middleware の名前を特定
rg -n "module\.exports|export" middleware/auth*

# Step 2: Route 定義を全列挙
rg -n "router\.(get|post|put|delete|patch|all)\(" routes/

# Step 3: Auth middleware なしの route を抽出
rg -n "router\.(get|post|put|delete)" routes/ | rg -v "authMiddleware|requireAuth"

Real Cases

Case 1: Flowise WHITELIST_URLS (6+ sibling endpoints)

問題: startsWith による prefix match + path normalization なし。

影響: 6+ endpoint が無認証でアクセス可能。WHITELIST pattern を 1つ見つけたら、同 codebase に必ず sibling がある。

教訓: bb-whitelist-audit を Phase 0/1 で必ず実行する。

Case 2: lobe-chat checkAuth Missing on tts/stt

問題: PR #13535 で chat/models route に checkAuth 追加。しかし /webapi/tts/openai と /webapi/stt/openai は対象外。

影響: 無認証で OpenAI API key を使用した TTS/STT リクエストが可能。コスト不正利用。

発見方法: Incomplete fix pattern — PR diff で追加された middleware → 同 router の他 route を検索。

Case 3: AnythingLLM validWorkspaceSlug Missing

問題: GHSA-p5rf-8p88-979c の修正で validWorkspaceSlug middleware 追加。suggested-messages GET と pfp GET には未適用。

影響: Cross-workspace data access (IDOR)。

発見方法: git diff → middleware 追加行 → 同一 router で middleware 不在の route を grep。

Audit Workflow

  1. Auth middleware を特定: rg "module.exports" middleware/
  2. Whitelist/skip 条件を確認: middleware 内の if ... return next() パターン
  3. 全 route を列挙: rg "router\.(get|post|put|delete)" routes/
  4. Middleware 未適用 route を抽出: diff で auth middleware 名を除外
  5. 各 route の sensitivity を判定: データ操作/情報漏洩の可能性
  6. Path normalization テスト: ../, %2F, //, case variation

Key Takeaways

  • Whitelist bypass は huntr/OSS で最も頻出する脆弱性クラス
  • 1箇所見つけたら sibling を必ず探す — Flowise で 6+ endpoint が一度に見つかった
  • Incomplete fix と組み合わせる: patch で追加された middleware が他 route に漏れている
  • Path normalization: middleware と router の解釈差を突く
  • bb-middleware-audit / bb-whitelist-audit で Phase 0 の機械的検出を必ず実行
