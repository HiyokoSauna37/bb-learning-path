Source は値を読む入口。Sink は値が使われる出口。同じ文字列でも、通常の見出しの textContent はテキストノードを作り、innerHTML の setter は HTML パーサーを呼ぶ。監査で重要なのは API 名と、実際の呼び出し方・表示先の組み合わせ。

外部への HTTPS リンクURL として解析して protocol を検証し、固定した a 要素の href に設定する。リンクのラベルには textContent を使う。相対 URL と HTTP URL を拒否し、HTTPS URL は通る。自社サイト専用のリンクなら origin の制限も必要。
JavaScript に値を渡すJSON のレスポンスをデータとして読み、通常の関数引数として扱う。入力をインラインのコードやテンプレート式に連結しない。引用符を含む値でも元の文字列として読め、画面に出す段階ではその表示先に合う処理を使っている。

公式資料で深く学ぶ　1件の投稿を表示まで追う

注文の備考に <b>要冷蔵</b> と入力した人がいる。仕様では「一覧には入力した文字をそのまま表示し、詳細では太字だけを許す」。この備考が保存され、API から返り、2つの画面に届くまでを考えてみよう。

① JSON を読むと、文字列はどうなる？

API の Content-Type: application/json は HTTP 本文の読み方を示す。response.json() の後、備考フィールドは山括弧を含む文字列になる。ブラウザーがその値を次にどう使うかは別の判断だ。一覧のセルに cell.textContent = order.note と代入すれば、山括弧まで文字として表示される。Network の応答と Elements のセルを見比べよう。Body Formats の復習 ／ MDN 日本語版「文書コンテキスト」

② Stored と DOM-based が同時に当てはまるのはなぜ？

注文者が昨日書いた備考を、担当者が今日開く。ここで分かるのは保存と閲覧の経路。担当者の画面で最初の HTML に空のセルしかなく、後続の API 応答から JavaScript がセルを作るなら、表示先を決めるのはクライアント側だ。その処理が入力を実行可能な構造として解釈させた場合、Stored DOM XSS と説明できる。保存や反射を観察しただけでは、実行可能性までは判断できない。PortSwigger「DOM XSS combined with reflected and stored data」

③ React の通常表示とリッチテキストで、レビュー箇所はどう変わる？

一覧で <td>{order.note}</td> と書くと、文字列はテキストとして表示される。一方、詳細画面で dangerouslySetInnerHTML を使うと、その値を HTML として扱う。レビューでは、そのプロパティに渡す HTML をどこで作り、太字だけを許す設定をどこで適用したかまでたどる。React 日本語版「内部 HTML を危険な方法で設定する」

④ サニタイズした後、誰が最後に HTML を書き換える？

詳細画面に強調表示ライブラリを追加したら、サニタイザーの戻り値に加えて、そのライブラリが作った最終 DOM もテストする。たとえば太字と属性を持つ校正用サンプルを使い、「本文の文字が残る」「太字が残る」「許可していない属性が消える」を別々に確かめる。DOMPurify の README は処理後の書き換えと、サーバーで利用する場合の DOM 実装の更新にも触れている。DOMPurify の注意事項 ／ OWASP「HTML Sanitization」

⑤ チーム全体で HTML の扱いを揃えるには？

Trusted Types を強制すると、対応ブラウザーでは innerHTML などの対象 sink で型が検査される。ポリシーでサニタイザーを呼び出して TrustedHTML を作れば、HTML を許可する判断を一か所にまとめられる。入力をそのまま返すポリシーでも型は作れてしまうので、レビュー対象は型の名前だけでなくポリシーの中身だ。MDN 日本語版「信頼型 API」

導入前の調査に使う Content-Security-Policy-Report-Only はポリシー違反を観測するためのヘッダーで、そのポリシー自体は動作を遮断しない。違反レポートを受け取ったときは、実際に配信したヘッダーと、該当画面の最終 DOM を併せて確認する。MDN 日本語版「Content-Security-Policy-Report-Only」

理解度チェック　備考が詳細画面だけで太字になった。これで XSS と言える？

この仕様では太字は期待した表示。確認できたのは、一覧と詳細で解釈が異なることまで。次は詳細の最終 DOM に許可外の要素・属性が残るか、どの処理がそれを作ったかを確認する。許可外の装飾が残る場合も、表示要件の不具合とスクリプトの実行可能性は個別に評価する。

保存した値と API 応答を見比べる ／ 許可設定と最終 DOM を見比べる

まず体感する: 30秒で分かる XSS

ブラウザの DevTools コンソール (F12 → Console) を開いて、以下を入力してみよう:

document.body.innerHTML = '<h1>ページを書き換えた!</h1>';

ページの内容が書き変わったはず。これが JavaScript でできること。 XSS とは、攻撃者がこのような JavaScript を、他人のブラウザ上で実行させる攻撃だ。

ここで使った innerHTML は DOM (Document Object Model = ブラウザがHTMLをJavaScriptで操作するためのツリー構造) を直接操作するプロパティ。 これが攻撃の「出口」(Sink) になる。

XSS の原理

外部から届いた値が、本来表示したかったデータの境界を越え、そのオリジンで実行できるコードとしてブラウザーに解釈されると、 攻撃者が注入したスクリプトが被害者のブラウザで実行される。

結果として: セッションの窃取、フィッシング、キーロギング、他ユーザーへのアクション実行（アカウント乗っ取り）が可能になる。

sequenceDiagram participant Attacker as 攻撃者 participant Victim as 被害者 participant Server as 脆弱サーバー Attacker->>Victim: 悪意あるURL/ページを送付 Victim->>Server: リクエスト (payload含む) Server->>Victim: レスポンス (スクリプト反射/保存) Note over Victim: 対象originでJS実行 Victim->>Victim: テスト用マーカーを表示 Note over Victim,Server: 検査アカウントで到達可能なデータと操作を確認
XSS の Impact (BB 観点)

実行を確認した後は、どの利用者の権限で、どのデータや操作に届くかを記録する。重要度は実際の影響と到達条件、対象プログラムの評価基準で判断する。

  • 実行時の origin と、閲覧する検査アカウントの権限
  • 閲覧に必要なクリック、ログイン、投稿・共有の条件
  • 同一 origin の読み取り・操作で確認できた影響と、追加認証などの制約

XSS の種類

1. Reflected XSS

ユーザーの入力がリクエスト内に含まれ、レスポンスにそのまま反射 (reflect) される。 入力を含むリクエストへの応答で問題が生じる。検索リンクはその一例。 

// 脆弱なサーバー側コード (Express)
app.get('/search', (req, res) => {
    res.send(`<h1>検索結果: ${req.query.q}</h1>`);
});

// Attack URL
https://example.com/search?q=%3Cscript%3Ealert(location.origin)%3C%2Fscript%3E

2. Stored XSS (Persistent XSS)

攻撃者の入力がサーバーに保存され、他のユーザーがそのページを表示するたびにスクリプトが実行される。 閲覧者の範囲、権限、必要な操作によって影響が変わる。 

// プロフィール表示 (脆弱)
<div class="bio">${user.bio}</div>

// 攻撃者が bio に設定
<img src=x onerror="alert(location.origin)">

3. DOM-based XSS

クライアントサイドの JavaScript が値をどの sink に渡すかで決まる。URL のフラグメントは HTTP リクエストに含まれない。一方、検索 API の応答や保存済みコメントも DOM-based XSS の source になり得る。 

// 脆弱な JS コード
const value = new URLSearchParams(location.hash.slice(1)).get('q') ?? '';
document.getElementById('output').innerHTML = value;

// Attack URL
https://example.com/page#q=%3Cimg%20src%3Dx%20onerror%3Dalert(location.origin)%3E

URLSearchParams が q を URL デコードしてから HTML の sink に渡す構成。ブラウザーの location.hash は山括弧などをエンコードした値を返す場合があるので、実際に渡った文字列を DevTools で確認する。このサンプルのインラインイベント処理は CSP が許す場合に実行できる。

Source は値を取り込む場所、Sink はその値を HTML・コード・URL などとして解釈する場所。たとえば検索語を検索結果の見出しに表示するときは、URL から読み取った値が、途中で加工・保存された後も最後までテキストとして扱われるかを追う。

4. Mutation XSS (mXSS)

サニタイザーが検査した DOM と、ブラウザーが最終的に解釈する DOM が異なり、その差で実行可能な構造が生じる場合を mXSS と呼ぶ。確認すべきなのは、検査した木、シリアライズした文字列、実際の表示先で再解析した木の3つ。

XSS の検出方法

Step 1　入力が現れる場所を見つける

  1. 全ての入力ポイントに一意のプローブ文字列を送る (例: xss123test)
  2. レスポンス内でプローブがどこに出力されるか確認
  3. 出力コンテキストを特定: HTML body? 属性内? JavaScript 内? URL 内?

Step 3　フィルターとデコードの差を確かめる

  • 1項目ずつ比較する。元の入力と、タグ名の大文字・小文字、属性、引用符などを一つ変えた入力で、応答と最終 DOM を比べる。
  • デコードの順序を記録する。URL エンコード、HTML 実体参照、JSON のエスケープが、どこで元の文字になるかを追う。二重デコードの存在は、その層で読んだ実際の値から判断する。
  • 制限のある文脈を切り分ける。許可タグ・属性、イベントが発生する操作、入力長、CSP の有無を分けて記録する。
  • 応答を変えた層を確認する。WAF の拒否、アプリ側の検証、サニタイザーによる変更、ブラウザーの正規化を、HTTP 応答と Elements の違いから調べる。

防御手法と検証する条件

HTML Encoding

< → &lt;, > → &gt;, " → &quot; 等。 正しく実装されていれば HTML body context の XSS は防げる。

インラインの script 内やイベント属性では、HTML と JavaScript の解析規則が重なる。使っているエンコーダーがどの文脈を対象にするかを確認する。API の JSON をデータとして読み、関数の引数や textContent に渡す設計にすると、コードへ文字列を連結する箇所を減らせる。

Blocklist フィルター

<script> や alert をブロック。

特定の単語の削除では、HTML パーサーが解釈できる他の要素や属性を覆いきれない。本文表示なら文脈に合う出力エンコード、装飾を許すなら許可ポリシーを持つ HTML サニタイザーを適用する。

WAF (Web Application Firewall)

HTTP 通信を検査して、規則に一致した要求や応答を遮断する追加の防御。CDN・WAF・アプリで正規化の方法が違うかを、実際の要求と応答で確かめる。HTTP/2 や chunked 転送を使ったときも、検査層が読み取る値とアプリが処理する値を比較して判断する。

CSP (Content Security Policy)

ブラウザーで読み込み先や実行可能なコードを制限する追加の防御。実際に配信された強制ポリシーと Report-Only、フォールバックする directive、実行時の違反を確認する。複数の強制ポリシーがある場合はすべての制約が適用される。Browser Security と 実務編の CSP 調査で詳しく学ぶ。

実行と影響を段階的に確認する

実行を調べるときは、入力する検査アカウント A と、閲覧する検査アカウント B を用意する。B が通常の画面操作で入力を読み込み、実行が起きた origin と必要なクリックを記録する。Console への手入力はコードの挙動を確認する操作なので、報告には画面からそのコードへ届く経路を示す。

確認するもの前提として確かめること残す最小限の証拠
別利用者の閲覧時の実行A の入力を B が閲覧でき、対象文脈と CSP で実行が可能入力の保存・共有手順、B の通常の閲覧操作、テスト用マーカーと location.origin
同一 origin のデータ読み取りB のセッションで対象 API を読める。HttpOnly は JavaScript による Cookie の直接参照を制限する検査用データだけを使った API 応答と、読み取れた項目
権限を使う操作対象操作の権限、再認証・現在のパスワード・MFA の要求、必要なトークン検査アカウントに対する可逆な操作の前後と、成立した範囲
別 origin・sandbox の制約実行中の frame、sandbox 属性、文書の origin、親画面へのアクセス条件対象文書の URL と設定。到達を確認したデータと到達条件

同じコードでも、ログイン状態・ブラウザー・frame・クリック条件で結果が変わる。ポップアップの可否だけに依存せず、DevTools の実行結果と通常の閲覧経路を併せて残す。実務編の影響評価と報告で、前提条件を含む記録例を確認できる。

Real-World Reports (HackerOne 実例解析)

公開レポートの要約から、入力が通る機能と調査の観点を整理する。各リンクの原文で報告時の前提条件、修正、再テストまで確認しよう。タイトルや要約で確認できる範囲をここに記載した。

Case 1　PayPal のキャッシュされたリダイレクト

公開要約では、フロントエンドとキャッシュサーバーの構成により、request smuggling でページ要求をキャッシュされたリダイレクトに変換できた。そのリダイレクトを利用者が開くと、要求したページに代わり攻撃者のコンテンツが表示される。#488147 ／ 再修正に関する #510152

調査では、キャッシュキー、汚染される応答、保存期間、影響するリクエストの条件を分けて記録する。Web Cache Poisoningでキャッシュの仕組みを復習できる。

Case 2　Reddit の Apple Sign-In とアカウント乗っ取り

タイトルでは response-type の切り替えと、www.redditmedia.com の XSS へ href が漏れる経路を組み合わせたアカウント乗っ取りを報告している。公開要約では Apple Sign-In の code や access token を取得できると説明している。#1567186

フロー図を作り、各段階で文書の origin、state、応答に含まれる値、その値を次に読むコードを追う。OAuth Attacksで認証フローの前提を確認できる。

Case 3　GitLab Kroki の画像要素へ属性が入る経路

Kroki を有効にしている場合、細工した pre ブロックから生成される img タグに任意属性を注入できた。公開要約では、対象の code 要素を探すセレクターと、図の種類を選ぶ lang 属性の扱いに言及している。#1731349

レンダラーが入力のどの値から要素名・属性・URL を作るかを追う。外部ライブラリが生成した HTML にも出力先の文脈を確認する必要がある。

Case 4　Shopify の Jamf Pro にあった古い Swagger UI

公開要約によると、jamfpro.shopifycloud.com の /classicapi/doc/ で古い Swagger UI が公開され、細工した URL からアプリの文脈で XSS を実行できた。修正ではこのエンドポイントへのアクセスを除去している。#1444682

API ドキュメントの画面も調査対象になる。依存する UI のバージョン、URL から取り込む設定、読み込まれる外部定義、実行文書の origin を調べる。

Case 5　Valve の React 製 Steam チャット

タイトルは Steam の React チャットクライアントにおける XSS。公開要約の導入では、React の保護と危険な描画機能の利用を避けた構成、CSP に触れている。どの経路でその保護の外に入力が届いたかを原文で追う読書課題にできる。#409850

デスクトップアプリを調べる場合は、描画プロセスからアクセスできる API と、preload や IPC の権限境界を別に確認する。Electron では Node.js integration、context isolation、sandbox、IPC の検証などが影響範囲を左右する。Electron のセキュリティ指針

事例から調べる前提条件と証拠

調査する経路成立に必要な前提記録する証拠
保存した入力を管理画面が表示入力者から管理者の閲覧まで到達し、管理画面の origin で実行できる入力先と表示先、検査用の役割、保存から閲覧までの操作
認証フローの値を別の画面が読む漏れる値が認証に使え、その値を読める origin と経路がある値の種類、フロー、state の扱い、検査アカウントで確認した結果
キャッシュ経由で別の利用者へ表示汚染応答が共有され、対象条件の要求に再利用されるキャッシュキー、対象 URL、保持期間、独立した検査クライアントの応答
デスクトップの描画から特権 API へ到達利用可能なブリッジ、IPC、Node.js API に必要な操作権限があるアプリのバージョン、プロセスと権限の境界、実際に呼べた API
Blind XSS のコールバックを検知入力を後から別画面が処理し、コールバックの発信元を特定できる入力ごとの識別子、発生時刻、実行文書の情報。URL の取得だけならクローラー等の可能性も調べる

Self-XSS を調べるときも、入力者と閲覧者を分けた再現経路があるかを確認する。CSP の違反だけが見える場合は、配信されたポリシーと到達した sink を記録する。重要度と報奨金は、対象プログラムの基準と確認できた影響に基づいて評価する。

Key Takeaways

  • 出力コンテキストを必ず特定する — HTML body, 属性, JS 内, URL で payload が全く違う
  • DOM-based はブラウザー側の処理を追う — HTTP 応答の値も source になり得る
  • Impact を示す — 実行 origin、検査アカウントの権限、到達条件と確認できたデータ・操作を記録する
  • 影響範囲を記録する — 表示する人の権限、入力の残る期間、閲覧に必要な操作を区別する
  • CSP は defence-in-depth — 強制ポリシーと Report-Only、実行時の制約を確認して影響を評価する
  • mXSS — サニタイズ時と最終表示時の DOM の違いから、実行可能な構造が生じる条件を調べる
