Authentication & Session Management

認証と Session 管理の仕組みを理解し、JWT misconfiguration や OAuth の実装ミスを見抜く力を養う。

Theory Hands-on WSA Lab Case Study

Cookie-Based Session

最も古典的な認証方式。サーバーがランダムな Session ID を生成し、Set-Cookie header でブラウザに返す。 以降のリクエストで Cookie が自動送信され、サーバー側で Session Store と照合する。

Session ID の要件

  • 十分なエントロピー: 最低128bit のランダム値 (CSPRNG 由来)
  • 推測不可能性: 連番、タイムスタンプベース、MD5(username) は全て脆弱
  • 適切な Cookie 属性: HttpOnly, Secure, SameSite=Lax 以上
  • Session 有効期限: Idle timeout + Absolute timeout

Session Fixation

攻撃者が既知の Session ID を被害者に使わせる攻撃。ログイン後に Session ID を再生成しないと成立する。 

# 攻撃フロー
1. 攻撃者: サイトにアクセスして Session ID を取得 (sid=AAAA)
2. 攻撃者: 被害者に https://target.com/?sid=AAAA を踏ませる
3. 被害者: そのまま sid=AAAA でログイン
4. 攻撃者: sid=AAAA で被害者のセッションを乗っ取る
BB視点: Session 関連で狙うポイント

ログイン前後で Session ID が変わるか確認。パスワード変更・権限昇格後にも Session regeneration が必要。 また、logout 時にサーバー側で Session を無効化しているか (Cookie を消すだけでは不十分)。

JWT (JSON Web Token)

Stateless な認証トークン。Header.Payload.Signature の3パートを Base64url で結合した文字列。

JWT の構造

# Header
{
  "alg": "HS256",
  "typ": "JWT"
}

# Payload
{
  "sub": "1234567890",
  "name": "John Doe",
  "iat": 1516239022,
  "exp": 1516242622,
  "role": "user"
}

# Signature
HMACSHA256(base64url(header) + "." + base64url(payload), secret)

JWT の一般的な攻撃

1. Algorithm None Attack

"alg": "none" を指定すると署名なしで受け入れるライブラリが存在した。 Payload を改ざんして Signature 部を空にするだけで認証バイパスが成立する。 

# 攻撃: alg を none に変更、signature を削除
eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJzdWIiOiIxIiwicm9sZSI6ImFkbWluIn0.

2. Algorithm Confusion (RS256 → HS256)

サーバーが RS256 (RSA 公開鍵で検証) を使っている場合、攻撃者が alg を HS256 に変更し、 公開鍵を HMAC の secret として使って署名すると、検証をパスする場合がある。 

# 攻撃手順
1. サーバーの RSA public key を取得 (/jwks.json, /.well-known/jwks.json)
2. Header の alg を HS256 に変更
3. Payload を改ざん (role: admin 等)
4. Public key を secret として HMAC-SHA256 で署名
5. サーバーが「HS256 なら secret で検証」→ public key を secret として使い、検証通過

3. Weak Secret / Brute Force

HS256 で secret が弱い場合 (secret, password123 等)、hashcat で crack 可能。 

hashcat -a 0 -m 16500 jwt.txt /usr/share/wordlists/rockyou.txt

4. kid (Key ID) Injection

kid parameter が DB クエリやファイルパスに使われる場合、SQL Injection や Path Traversal が可能。 

# SQL Injection via kid
{"alg":"HS256","kid":"key1' UNION SELECT 'attacker-secret' -- "}

# Path Traversal via kid
{"alg":"HS256","kid":"../../dev/null"}
# /dev/null は空文字を返す → secret="" で署名すれば通る

5. 追加の JWT 脆弱性

  • exp 未検証: 期限切れトークンがそのまま受け入れられる
  • aud 未検証: 別サービス用のトークンが流用できる
  • jku/x5u spoofing: 攻撃者のサーバーから鍵を読み込ませる
BB視点: JWT は宝の山

BB で最も頻出するのは weak secret (hashcat で数分で crack) と expired token acceptance。 まず jwt.io でデコードして alg, exp, aud を確認。 JWKS endpoint があれば Algorithm Confusion の可能性も。 jwt_tool で自動チェックが効率的。

OAuth 2.0

第三者にリソースアクセスを委任するための認可フレームワーク。「認証」ではなく「認可」だが、 実質的にログイン機能として広く使われている。

主要な Grant Type

Grant Type用途セキュリティ
Authorization Code Server-side アプリ (最も一般的) 最も安全。code は一度だけ使用、client_secret でトークン交換
Authorization Code + PKCE SPA / Mobile アプリ code_verifier で code 横取り攻撃を防止
Implicit (非推奨) 旧 SPA 向け token が URL fragment に露出。現在は PKCE が推奨
Client Credentials Machine-to-Machine ユーザー不在。client_secret のみで認証

Authorization Code Flow

sequenceDiagram participant User as ユーザー participant App as クライアントアプリ participant AuthSrv as Authorization Server participant API as Resource Server User->>App: ログインボタン押下 App->>AuthSrv: /authorize?response_type=code&client_id=X&redirect_uri=Y&state=Z AuthSrv->>User: ログイン+同意画面表示 User->>AuthSrv: 許可 AuthSrv->>App: redirect_uri?code=AUTH_CODE&state=Z App->>AuthSrv: POST /token (code + client_secret) AuthSrv->>App: access_token + refresh_token App->>API: Authorization: Bearer access_token API->>App: Protected resource 
# 1. ユーザーを Authorization Server にリダイレクト
GET /authorize?
    response_type=code&
    client_id=CLIENT_ID&
    redirect_uri=https://app.example.com/callback&
    scope=openid profile&
    state=RANDOM_CSRF_TOKEN

# 2. ユーザーが許可 → redirect_uri に code が返る
GET /callback?code=AUTH_CODE&state=RANDOM_CSRF_TOKEN

# 3. Server-side で code を token に交換
POST /token
    grant_type=authorization_code&
    code=AUTH_CODE&
    redirect_uri=https://app.example.com/callback&
    client_id=CLIENT_ID&
    client_secret=CLIENT_SECRET

OAuth の一般的な脆弱性

  • Open Redirect via redirect_uri: 検証が甘いと code/token が攻撃者サイトに漏洩
  • state パラメータ未検証: CSRF で攻撃者のアカウントに被害者を紐付け
  • Scope 昇格: 追加 scope を勝手に要求して過剰な権限を得る
  • Token leakage via Referer: Implicit flow で fragment が Referer に乗る

PKCE (Proof Key for Code Exchange)

code_verifier (ランダム文字列) のハッシュを code_challenge として authorization request に含め、 token 交換時に code_verifier を送信。中間者が code を横取りしても token に交換できない。

OIDC (OpenID Connect)

OAuth 2.0 の上に「認証」レイヤーを追加した規格。id_token (JWT) でユーザー情報を返す。 scope=openid で OIDC が有効になる。nonce パラメータで replay attack を防止。

API Keys & Bearer Tokens

API Key

シンプルな文字列ベースの認証。Header (X-API-Key) または query parameter で送信。 通常は rate limiting と billing の識別に使われるが、認証にも流用される。

  • 漏洩リスク: URL に含まれるとサーバーログ、Referer、ブラウザ履歴に残る
  • 権限管理: key ごとの scope 制御が雑な実装が多い

Bearer Token

Authorization: Bearer eyJhbGciOiJSUzI1NiIs...

Token を持っていれば誰でも使える (bearer = 持参人)。盗まれたら即アカウント乗っ取り。 TLS 必須、保存場所 (localStorage vs httpOnly cookie) が議論になる。

MFA (Multi-Factor Authentication)

方式FactorBB で狙うポイント
TOTP (Google Authenticator)Something you haveRate limit 不在で brute force (6桁 = 1M通り)
SMS OTPSomething you haveSIM swap, SS7 attack (BB では通常 OOS)
WebAuthn/FIDO2Something you haveFallback 機構の脆弱性
Recovery CodesSomething you have生成時の情報漏洩、brute force
BB視点: MFA Bypass パターン

MFA のバイパスは BB で高額報酬の対象。よくあるパターン:
(1) MFA ステップ後の response を改ざん (200 OK に変更)
(2) 直接 authenticated endpoint にアクセス (MFA ステップをスキップ)
(3) Rate limit 不在で TOTP brute force
(4) Backup code の rate limit 不在
(5) OAuth login で MFA をスキップ

Key Takeaways

  • JWT alg:none と Algorithm Confusion は古いライブラリで今でも刺さる。jwt_tool で自動チェック。
  • JWT weak secret は hashcat 16500 モードで高速 crack。rockyou.txt で試す価値あり。
  • OAuth redirect_uri の検証不備は open redirect → token theft の王道チェーン。
  • state パラメータ がない OAuth は CSRF でアカウントリンク攻撃が成立する。
  • MFA bypass は response manipulation, step skipping, rate limit abuse が三大パターン。
  • Session fixation: ログイン前後で Session ID が再生成されるか必ず確認。
