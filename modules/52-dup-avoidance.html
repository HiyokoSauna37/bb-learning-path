Duplicate Avoidance Strategy

Dup は BB hunter の最大の敵。時間を投資した後に「既知」と返されるのを防ぐ戦略。 3軸チェックと timing 戦略で dup rate を下げる。

Theory Case Study

3-Axis Dup Check

Submit 前に 3 つの軸で既知かどうかを確認する。1つでも hit したら submit しない。

Axis 1: Advisory (GHSA / CVE / NVD)

  • bb-ghsa list {repo} で対象リポジトリの全 advisory を列挙
  • CVE description とキーワードマッチ（endpoint 名, パラメータ名, vuln class）
  • NVD で関連 CVE を検索
  • 重要: WebFetch/手動 gh api では漏れが発生する（5件抜けの実害あり）。bb-ghsa list を canonical 経路にする

Axis 2: PR / Commit

  • GitHub の commit history で fix keyword 検索: fix, patch, security, CVE
  • PR title/body での脆弱性修正の痕跡
  • Side-effect fix PR の検出: maintainer が advisory なしで修正するケースがある。diff を見て意図的な security fix か判断

Axis 3: Issue

  • GitHub Issues でセキュリティ関連の報告を検索
  • Close された issue にも security fix が含まれる
  • HackerOne disclosed reports の検索（公開済みレポートのみ）

Timing 戦略

Advisory 公開 3日以内 = Golden Window

Incomplete fix variant を発見できる最高のタイミング。パッチが不完全なケースが多い。即座に variant を探す。

3日 〜 30日 = Competitive Zone

他の hunter も同じ advisory を見ている。Variant は既に報告されている可能性が高い。深い分析が必要。

30日超 = NOGO (Default)

Incomplete-fix variant 戦略の default は deprioritize。例外は advisory 3日以内のみ GO。30日超は NOGO default (bb-advisory-age で判定)。

例外: GO になるケース

  • 明らかに未パッチの sibling endpoint が存在する（grep で確認可能）
  • パッチが helper function を追加したが、呼び出し箇所に propagate されていない
  • 新バージョンで regression が発生している

Dup Zone 管理

Program ごとに「この endpoint/パターンは dup zone」と記録し、同じ轍を踏まない。

mei-bb 実例: Known Dup Zones

GitLab — BulkImport 関連の authorization bypass。大量の prior report あり。新規 variant は非常に高い bar。
Nitro — isPathInScope path traversal。パッチ済み、variant は報告済み。
OPPO — OAuth state parameter の CSRF。既知パターン。
Grafana — registerOptions* 関連。複数の prior report で dup zone 確立。

Platform 別 Dup 挙動

HackerOne

  • Private report は他の hunter からは不可視 — dup かどうか submit するまでわからない
  • Dup 判定後に original report が disclosed されることがある → 学習機会
  • 同一 program で連続 dup は reputation には影響しないが、time waste

Intigriti

  • Dup は triage team が判定。original reporter の report は見えない
  • 部分的な dup（同じ root cause だが異なる endpoint）は accepted される場合がある

huntr (OSS)

  • OSS なので commit history が完全に公開 — 3-axis check が最も効果的
  • GHSA が private の場合もある（embargo 中）

Signal への影響

ResultSignal Impact備考
Resolved (Bounty)Positive (+7)理想
DuplicateExcluded (計算から除外)Signal にプラスもマイナスも影響なし。Reputation に +2 (early) / -5 (late) の別計算あり
Informative0Neutral
N/A-5避けるべき
Spam-10絶対避ける

Key insight: Dup は Signal 計算から除外される（プラスもマイナスもない）。N/A や Spam のほうが遥かにダメージが大きい。Dup を恐れて submit しないより、品質の低い報告を避けることが重要。

実践: Dup Check Workflow

Step-by-Step

  1. bb-ghsa list {owner}/{repo} を実行し、全 advisory を取得
  2. Finding の vuln class (XSS, IDOR, auth bypass等) で advisory をフィルタ
  3. 影響する endpoint / parameter 名で keyword 検索
  4. GitHub commit history で git log --grep="fix\|security\|CVE" 相当の検索
  5. PR の diff を確認し、side-effect fix がないか確認
  6. HackerOne Hacktivity で program の公開レポートを検索
  7. 全 axis clear → submit 可。1つでも hit → 精査 or abandon

Side-Effect Fix PR の見分け方

  • PR title に security keyword がないが、diff に auth check / validation 追加がある
  • Feature PR の中に紛れ込んだ security hardening
  • Dependencies update の中に含まれる security patch
  • 対策: endpoint に関連する全ての recent commits を diff で確認
