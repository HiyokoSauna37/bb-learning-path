Category 1: False Positive / AI Slop で撤回

AI (Claude Code) と協調して調査する際に、AI が「脆弱だ」と主張したが実際には exploit 不可能だったケース。 これが「AI Slop」と呼ばれるパターン。

X

vercel/ai: SSRF deny-list bypass (trailing-dot hostname)

validateDownloadUrl の deny-list を localhost. (trailing dot) で bypass できる。 Windows では localhost. が 127.0.0.1 に解決される — が、 production deploy target (Vercel Functions / Lambda / GCP) は全て Linux。 Linux glibc/musl では getaddrinfo('localhost.') が ENOTFOUND。
教訓: SSRF / network 系 PoC は production runtime OS (= Linux) で必ず再現確認。 Windows のみの verify は AI Slop signature。
→ 対策: bb-aislop-gate に cross-OS check 追加済み
X

Uber (gighub.uber.com): Firebase test phone bypass

Firebase Auth に test phone number (OTP=123456) が 10 個設定されていた。 認証 bypass + /tasks/ IDOR で cross-task data 読み取り — と claim したが: TESTER userType / Dummy User / 0-price test tasks / 個人名 project ID (-ritu) → test 環境の可能性が高い。Production 証明不能。
教訓: Production 立証は TESTER signal 排除が必須。 Java NPE は write capability の証拠にならない。 bb-aislop-gate が HOLD を返したら 強制 submit-block。
X

Grafana / Pyroscope: query-diagnostics unauth cross-tenant

Live exploit 再現可能 (unauth で tenant 間の diagnostic data 読み書き)。 しかし Grafana Labs は "no auth layer; use reverse proxy" と公式ドキュメントで明記。 これは by-feature (=設計上の意図) であって bug ではない。
教訓: Auth-bypass を claim する前に canonical auth doc を最初に読む。 bb-auth-doc-audit が CLOSED auth-by-operator を返したら即 pivot。 同一 vendor の design pattern は横展開される (Loki → Pyroscope → Mimir 全部同じ)。
X

immich: shared-link password gate scope gap

パスワード付き共有リンクの content endpoint にパスワードなしでアクセスできる。 実装 gap は real — だが album_id が UUIDv4 で enumerable でなく (AC:H)、 maintainer は「embedded link = URL-as-credential」設計を示唆。 Design intent が ambiguous で、Informative close のリスクが高い。
教訓: bb-auth-doc-audit が unclear を返したら AC:L は suspect by default。 Design ambiguity がある場合 framing は「complete bypass」ではなく「implementation gap with open question」。

Category 2: Duplicate で $0

D

GitLab: BulkImport DNS rebinding TOCTOU SSRF

3 pipeline の fetch_as_mirror に resolved_address 渡し漏れ。 提出当日 (2026-04-28) に dup 判定、先行 report #3565700 に集約済み。
教訓: GitLab のような大手プログラムでは「同じ root cause の variant」は 全て 1 report に consolidate される。encoding/placement の差異は「同じ bug」扱い。
Dup zone: BulkImport resolved_address 系は完全 redzone。
D

Nitro: routeRules proxy scope bypass (%2f..%2f)

GHSA-5w89-w975-hf9q のパッチ公開 2日後 に incomplete-fix variant を submit。 67% dup risk と予想していた通り dup。Triager が明確に 「encoding/placement variations = exploitation techniques of the same root cause」と consolidation 方針を示した。
教訓: parser differential 系は encoding variant を並べても同一 root cause 扱い。 別の sink (isPathInScope 以外の routing primitive) を狙う必要がある。 Dup risk 67% で「honest caveats 付きで submit」は signal 損失ゼロ (dup は signal 計算から除外) なので判断は正しかった。
D

OPPO: drp.myoppo.com open redirect via state param

OAuth callback の state パラメータが Location header に無検証で反射。 3 regional front (CN/SG/IN) 同一 defect。2ヶ月以上前の #3578822 が先行 — H1 の private non-disclosed report は外部から検知不可能。
教訓: HackerOne の非公開 prior report は hacktivity feed にも dashboard にも出ない。 bb-submission-status Layer 1/2/3 でも fully cover 不能。 大手プログラムの low-hanging fruit (open redirect 等) は latent dup が常に存在する前提で動く。
$20–$45 (Low row) 期待値で submit する判断自体は合理的 (signal loss = 0)。

Category 3: 有効な発見 (Pending/In Review)

O

Discourse: PostsController#revert array id bypass (In Review)

?id[]=ownX&id[]=victimY で PostRevision.find_by(post_id: array) が Y の row を返し、X に対する権限チェックを通過。Moderator が他者の revision history を抽出可能。 Pre-screen passed (2026-05-07)。同プログラムの prior CVE を citation して severity を正当化。
成功要因:
  • Precedent citation (CVE-2026-31805, CVE-2026-33394) で severity framing を固めた
  • E2E PoC (control 404 → bypass 201 → leak 200) で再現性を完全に示した
  • Program-specific severity table を参照して High にした (CVSS 5.5 だが policy override)
O

kotaemon: Pre-auth RCE via MCP server config (Critical 9.8)

Gradio UI の hidden handler が gradio_client から直接 invoke 可能。 MCP server config で任意コマンド実行。verified ×3 (Windows + Linux + Gradio toy)。
成功要因:
  • Gradio gr.update(visible=False) が server-side auth ではないことの深い理解
  • 3 環境での independent reproduction
  • Caveats & Limitations 7 項目の honest disclosure
  • 先行 GHSA (path traversal) との差異を明確にして dup risk を排除
O

wger: Sibling-unpatched gym=None authorization bypass (Critical 9.9)

CVE-2026-43948 のパッチが is_same_gym() を導入したが、3 call site に propagate されず。 gym=None ユーザーに対して delete/deactivate/activate が cross-tenant で可能。
成功要因:
  • Incomplete-fix variant strategy の教科書的な成功例
  • Positive ×3 + Negative ×3 + Symmetric revert で完璧な再現性
  • パッチ commit からわずか 12 日後に submit

メタ教訓 (全体を通して)

1. AI との協調で最も危険なのは「AI が確信を持って間違える」こと

AI (Claude Code) は structural evidence (コードの字面) だけで「脆弱です、submit しましょう」と言う。 runtime で刺さるかどうかは別問題。 End-to-end で sink での actual exploit demo を確認するまで verified 禁止。

2. 撤回は恥ではなく、submit の品質を上げる投資

6件の pre-submission withdrawal は「submit していたら N/A で signal -5 だった」ケース。 Self-audit gate (bb-aislop-gate, bb-fp-detector, bb-auth-doc-audit) を通すことで submit 精度が上がり、triage 側の信頼も得られる。

3. Timing > Skill (特に incomplete-fix variant)

Advisory 公開から 3日以内に variant を見つけて submit する speed が最も重要。 30日超は他の hunter が見つけている可能性が高すぎる。 bb-ghsa list の日次 watch → patch diff 即読み → sibling grep → PoC → submit のパイプライン化が鍵。

4. By-feature vs Bug の見極めが最大の time-saver

実装 gap が存在しても vendor が「それは仕様です」と言えるものは bug ではない。 Auth doc / maintainer comment / product design (マルチテナント? シングルテナント?) を コードを読む前に確認することで、false-positive 調査に費やす時間を 80% 削減できる。

5. 大手プログラムの low-hanging fruit は「見えない先行者」が常にいる

HackerOne の private report は外部から検知不可能。 GitLab / Uber / OPPO 等の大手で「簡単に見つかる」ものは latent dup の可能性が常にある。 戦略: (a) deep logic chain に pivot する、(b) マイナーな OSS で確実な finding を積む、 (c) dup risk を受容して signal loss = 0 で submit する (early dup は signal 計算除外)。
