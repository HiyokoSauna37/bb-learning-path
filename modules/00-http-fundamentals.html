HTTP Protocol Deep Dive

Webアプリケーションの全通信基盤。ここを理解しないと、あらゆる脆弱性の「なぜ刺さるか」が分からない。

Theory

なぜ HTTP を深く理解する必要があるか

Bug Bounty で見つかる脆弱性の大半は、HTTP通信の挙動を悪用したものだ。 SSRF (サーバーに内部リクエストを送らせる攻撃) は HTTP request の送信先を操作する。 CSRF (被害者のブラウザから意図しないリクエストを送らせる攻撃) は browser が自動付与する Cookie を悪用する。 Request Smuggling は HTTP parser (リクエストを解析するソフト) の差異を突く。 これらは全て後のモジュールで詳しく学ぶ。

HTTPの仕組みが頭に入っていれば「この header は誰が付けた？」「この response は cache (一時保存) される？」 といった問いが自然に浮かぶ。それがそのまま attack surface の発見につながる。

HTTP Request の構造

Request Line

GET /api/users?id=123 HTTP/1.1
POST /login HTTP/1.1
PUT /api/profile HTTP/1.1
DELETE /api/sessions/abc HTTP/1.1
BB視点

Method（GET, POST, PUT, DELETE, PATCH）を 変えるだけで認可チェックをbypassできることがある。
例: DELETE /api/user/123 は禁止だが POST /api/user/123 + _method=DELETE で通る（Method Override）。

Headers（重要なもの）

Header役割BB との関連
Host リクエスト先のドメインを指定 Host header injection, Password reset poisoning, Cache poisoning
Cookie セッション情報の送信 Session fixation, Cookie tossing, SameSite bypass
Authorization 認証情報 (Bearer token, Basic auth) Token leakage via Referer, Bearer vs Cookie の違い
Content-Type Body のフォーマット指定 CSRF bypass (application/json → multipart), XXE trigger
Origin / Referer リクエスト元の情報 CORS validation, CSRF token validation bypass
X-Forwarded-For Proxy経由の元IP IP制限bypass, Rate limit bypass, Admin panel access
Transfer-Encoding Body の転送方式 (chunked) HTTP Request Smuggling (CL.TE / TE.CL)

BB視点: Content-Type switching

CSRF 対策で application/json のみ受け付けるAPIが、 multipart/form-data や text/plain でも同じ処理を実行する場合がある。 Content-Type を変えてリクエストを送ってみることは基本テクニック。

application/json

{
  "username": "admin",
  "password": "hunter2",
  "role": "user"
}

REST API の標準。Mass Assignment（"role": "admin" を追加して権限昇格）の温床。

401 vs 403 の違い

401 = 「あなたは誰？」（Authentication 不足）
403 = 「あなたには権限がない」（Authorization 不足）
401 が返る endpoint は認証 bypass を探す。403 は認可 bypass（IDOR, Role escalation）を探す。

HTTP/2 と HTTP/3

HTTP/2 の特徴

  • Binary framing — テキストではなくバイナリフレーム。手動での改ざんが難しい
  • Multiplexing — 1つの TCP 接続で複数のリクエストを並行処理
  • Header compression (HPACK) — ヘッダの圧縮
  • Server Push — サーバーからのリソース先行送信
BB視点: H2 特有の攻撃
  • H2.CL Request Smuggling — HTTP/2 の :method, :path pseudo-headers と Content-Length の不整合を突く
  • H2C Smuggling — HTTP/2 cleartext upgrade を悪用して reverse proxy をバイパス
  • HPACK Bomb — 圧縮ヘッダの展開によるDoS

HTTP/3 (QUIC)

UDP ベースの QUIC プロトコル上で動作。TCP の Head-of-Line blocking を解消。 BB 視点では HTTP/3 特有の脆弱性はまだ少ないが、QUIC の UDP ベースという特性から amplification attack や protocol confusion のリサーチが進行中。

実践: リクエストの観察と改ざん

DevTools で観察する

  1. Chrome DevTools → Network タブを開く
  2. 任意のWebサイトを開いて通信を観察
  3. 各リクエストの Headers / Payload / Response を確認
  4. 特に注目: Set-Cookie の属性、Authorization header の有無

curl で手動リクエスト

# 基本的なGET
curl -v https://example.com/api/users

# POST with JSON body
curl -X POST https://example.com/api/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"test"}'

# Cookie付きリクエスト
curl -b "session=abc123" https://example.com/api/profile

# Header injection テスト
curl -H "X-Forwarded-For: 127.0.0.1" https://example.com/admin

# Method Override
curl -X POST https://example.com/api/user/123 \
  -H "X-HTTP-Method-Override: DELETE"

Burp Suite で改ざんする

  1. Proxy → Intercept ON にしてブラウザ操作
  2. Intercepted request の任意の部分を書き換え
  3. Repeater に送って繰り返しテスト
  4. Response の差異を観察（200 vs 403 vs 500）

Key Takeaways

  • 全ての脆弱性は HTTP通信の上で発生する — request/response の構造を完全に理解する
  • Header は attack surface — Host, X-Forwarded-For, Content-Type の操作は基本技
  • Status code は情報源 — 403 は「認可チェックがある」の証拠、500 は「入力がバックエンドに届いた」の証拠
  • HTTP/2 は新しい attack surface — H2.CL smuggling, H2C bypass は最新トレンド
  • Content-Type switching — 同じ endpoint でも Body format を変えると挙動が変わることがある
