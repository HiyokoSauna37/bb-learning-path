XSS のデータフロー実習

検索語に <b>京都</b> と入れたら、レスポンスに何が届き、画面には何が出るだろう？ 入力元、途中の処理、最後に値を解釈する場所を順に記録しよう。

検索と掲示板で、入力が届くリクエストを比べる

この2題では実際にHTTPを送受信する。リポジトリのルートで次を実行し、画面を開く。Python 3 の標準ライブラリだけで動く。

python3 labs/xss_http.py

ローカルの検索・掲示板を開く。開発者ツールの Network でログを保持し、各リクエストの Response と画面を見比べる。

1. Reflected の経路

検索語を送る。URL、レスポンスの samp 要素の中身、表示された文字を記録する。URL からクエリを消して再読込すると、どの値が消えるか？

観察結果と照合する

GET の q が source。サーバーが HTML 本文用にエンコードし、レスポンスに &lt;b&gt; が入る。ブラウザーは <b> の3文字をテキストとして表示する。入力を含まない次のリクエストに検索語は引き継がれない。入力の反射だけでは XSS の証拠にならない。

2. Stored の経路

同じ値を投稿する。POST と、その後の GET のどちらに入力欄の値が含まれるか？ 別タブで /notes を開き、検索と同じ操作で表示が消えるか比べよう。

観察結果と照合する

POST 本文から受け取った値をサーバーがメモリーに保存する。303 に続く GET には投稿本文が含まれないが、レスポンスには投稿が載る。出力時に HTML エンコードするので文字として読める。タブを閉じても残り、サーバーを停止すると消える。

比較課題　同じ投稿を JavaScript で読んだら？

投稿したあと、JSON 版の投稿一覧を開く。Network で /reader と /api/notes のどちらの応答に本文があるか予想し、Elements の li と比較する。

2つの投稿一覧で sink はどう変わった？

/notes の HTML 版はサーバーがエンコードして本文を返す。/reader の最初の HTML には空のリストがあり、投稿本文は別の JSON 応答にある。ブラウザーが response.json() で読み、各 li の textContent に代入する。データの保存場所は同じでも、最後に表示を作る場所が異なる。

なぜタグが消えても中の文字は残る？
DOMPurify に許可タグを指定し、属性・data 属性・ARIA 属性を許可しない設定で処理している。この原稿では許可外の装飾が外れ、中の文字は残る。HTML エンコードなら許可したタグも文字として表示される。URL の接続先や JavaScript としての安全性はこのポリシーの対象外。

5. Mutation XSS の前提になる再解析を観察する

        
校正済みの表を別の欄に転記する場面を考える。行を HTML 文字列に戻し、異なる親要素のもとで再解析したら、元の行と同じ DOM になるだろうか？

        
        
        

        
観察から何を判断できる？
tbody では行が残り、table では tbody が補われ、div ではセルの文字だけが残る。同じ文字列でもパーサーの文脈で DOM は変わる。この例で変化するのは表の構造だけ。mXSS と判断するには、再解析や正規化により、許可されていない実行可能な構造が生じることが条件になる。修正後は表示先の実際の DOM で許可タグ・属性を確認し、サニタイズ済みノードを文字列に戻す工程を減らす。
